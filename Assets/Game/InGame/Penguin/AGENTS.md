# InGame/Penguin — 3인칭 펭귄 캐릭터

## 카메라 암은 시야를 내릴수록 짧아진다 (2026-08-26)

`PenguinCameraOrbit`의 거리는 속도로만 정해졌다. 그래서 피치를 내리면 카메라가 **눈밭 아래로
파고들어 지면 밑면이 보였다.** 기하학이 그렇게 되어 있다 — 카메라 로컬 위치가 `back*d + up*h`
이고 피벗이 피치로 회전하므로, 피치가 음수면 `(orbit * back).y < 0`이라 **암이 길수록 카메라가
내려간다.** `_distanceHigh = 6.5`에서 피치 −30도면 6.5 x sin(−30) = **−3.25m**, 눈 한참 아래다.

두 단계로 막는다.

- **연출**: `_armShortenStartPitch`(10도) 아래부터 `_armShortenWhenLow`(0.5)만큼 암이 줄어든다.
- **보증**: 그래도 모자라면 잘라낸다. 카메라 높이는 암 길이에 대한 **1차식**(`y = base + d·rise`)
  이라 반복 탐색 없이 상한을 한 번에 푼다. `_minHeightAbovePivot`(0.3m) 아래로는 못 내려간다.

실측(암 기본 5.0m, 높이 0.7m): 피치 60도 → 5.00m, 10도 → 5.00m, 0도 → 4.38m, −15도 → 2.24m,
−30도 → 1.20m. 카메라 높이는 어느 피치에서도 0 아래로 가지 않는다.

**튜닝 값은 `PF_Penguin.prefab` 에 있다. C# 기본값을 고쳐도 아무 일도 일어나지 않는다.**
`_distanceLow` 같은 값은 프리팩에 이미 직렬화돼 있어 프리팩 값이 이긴다. 두 번 속았다.
`PrefabUtility.LoadPrefabContents` + `SerializedObject` + `SaveAsPrefabAsset` 로 써넣어야 한다.
측정 프레이밍(fov 60): 암 1.8m = 가슴 위(몸 70%), **2.4m = 상반신(44%)**, 3.5m = 전신(36%).

**얼굴을 보려면 조준점과 카메라를 같이 내려야 한다.** 피벗(`SnowHeightPivot`)은 머리보다 **위**에
있다 — 측정값으로 눈(`DEF-Eye.L`)이 피벗 기준 **-0.59m**다. 그래서 `_faceAimHeight` 와
`_zoomHeightOffset` 은 **음수**이며, 둘 중 하나만 적용하면 카메라만 내려가고 시선은 그대로여서
얼굴이 프레임 밖으로 밀린다. 현재 눈이 화면 (0.48, 0.48) 에 잡힌다.

**줄임 계수의 기준을 `_distanceHigh` 로 잡으면 안 된다.** 그 값이 같이 움직이는 순간
`InverseLerp` 가 1을 돌려줘 `zoom01` 이 0으로 고정되고, 얼굴 조준·높이가 통째로 죽는다.
절대 거리(`_zoomNearDistance` / `_zoomFarDistance`)로 재야 한다.

**암 축소 임계 피치는 평상 시선보다 확실히 낮아야 한다(`-12`).** 10도로 두었더니 가만히 서
있을 때도 피치가 -2.8 로 떨어져 암이 절반으로 줄고, 의도치 않게 얼굴 클로즈업이 됐다.

**길이는 목표값을 따라간다 — 대입하지 않는다.** 처음엔 매 프레임 계산한 길이를 그대로 넣었는데,
그러면 (1) 마우스 피치가 거리에 1:1로 썧혀 카메라가 튀고, (2) 기하학적 상한이 걸리는 순간
길이가 계단으로 뛴다. `_armFollowSeconds`(0.35초) `SmoothDamp` 로 따라가게 하고, 줄어드는 비율
자체도 smoothstep 을 먹인다. `OnEnable` 에서 0으로 재상해야 한다 — 직전 길이를 들고 있으면
씨 시작 순간 기어 들어온다(선회 킥과 같은 이유).

**Cinemachine으로 바꾸지 않았다.** 이 스크립트에는 슬라이딩 궤적 추적, 선회 FOV 킥, 렌더 직전
피벗 재고정(`HandleCameraPreCull`) 같은 실측으로 얻은 동작이 쌓여 있다. Cinemachine으로 옮기면
그게 전부 다시 만들 일이 된다.

## 설면 높이 추종 (2026-08-26)

`PF_Penguin`의 물리 루트와 캡슐은 단단한 지면 위에 그대로 두고, `SnowHeightPivot` 아래의
`BodyPivot`·`CameraRig`만 현재 접지점 눈 깊이의 **50%**만큼 올린다.
`PenguinSnowInteraction`이 실제 접촉 지면과 같은 높이에 있는 눈만 읽고 기본 0.18초 `SmoothDamp`로 따라가므로
눈 깊이가 달라져도 캐릭터·카메라가 함께 자연스럽게 이동한다. 공중에서는 마지막 높이를
유지하고 눈덩이 위 탑승 상태에서는 0으로 돌아간다. 물리 루트를 직접 올리지 않는 이유는 캡슐을
눈 메시 위로 띄워 접지·경사·충돌 계산과 싸우지 않게 하기 위해서다. 동일 XZ 아래에 눈이 있어도
현재 지지하는 비탈면이 눈보다 높으면 시각 오프셋과 발자국 제거에 사용하지 않는다.
`PenguinLocomotion`도 프리팹 참조가 비어 있으면 같은 씬의 `SnowCpuStage`를 자동으로 찾아, 테스트 씬과
실제 씬 모두 눈 위 일반 점프와 맨바닥 작은 점프가 같은 기준으로 갈린다.

같은 컴포넌트가 접지점과 캡슐 반지름을 `SnowCpuStage`에 제공한다. 걷기·달리기·슬라이딩·운반은
모두 동일한 펭귄 이동이므로 별도 상태 분기 없이 새로 밟은 셀의 눈을 50 mm씩 제거한다.

- E는 전방 눈덩이를 밀기 대상으로 선택하고 후보가 없으면 발밑 눈으로 새 공을 만든다. F는 방향과
  무관하게 가까운 눈덩이·선물을 고른다. 펭귄은 물체의 가장 가까운 면까지 걸어간 뒤 물체가 등 뒤에
  오도록 돌아서 적재하며, 기울어진 선물은 선택 순간 바닥 접촉 높이를 보존한 채 직립시킨다. 접근 중
  F는 취소하고 운반 중 F는 후방 바닥에 내려놓는다. 선택 뒤 W로
  밀고 A/D로 방향을 바꾼다. 눈덩이 옆 밀기 상태에서는 W 입력 여부와 무관하게 양 날개 접점을
  유지하며, Space 공 위 탑승은 현재 비활성화되어 입력을 무시한다.
- 눈덩이를 잡지 않은 좌클릭은 `Attack_Adelie`를 재생한다. 일반 물체의 기존 충격량은 유지하되,
  선물은 질량과 무관하게 속도 증가가 최대 3m/s가 되도록 충격량을 제한한다. 휠클릭 입력은 없다.
- 중간 충격은 `Damage_Adelie`와 충격 방향 몸통 킥을 재생한다. 큰 충격은 조작을 잠그고 루트
  Rigidbody의 회전 제약을 풀어 공중에서 물리적으로 회전시킨다. 정적 지면에 닿으면 충돌 캡슐은
  즉시 직립 고정하되 `BodyPivot`의 월드 자세를 보존하고, 출발 상태 길이에 영향받지 않는 고정
  0.28초 동안 14번 `Dead_Adelie`의 86% 누운 자세로 블렌딩한다. 그 자세를 2초 유지한 다음
  Actions 레이어 가중치를 0.45초 동안 1→0으로 내려 계속 재생 중인 Idle을 드러내며 조작을
  복구한다. 쓰러지는 구간을 0초부터 다시 재생하지 않으며 전역 Animator 속도는 멈추지 않는다.
- 프리팹의 물리는 루트 Rigidbody와 캡슐 하나뿐이다. 본 Rigidbody, `CharacterJoint`, 래그돌
  전환·복구 코드는 사용하지 않는다.

메인 플레이어 후보. 이동, 카메라, 슬라이딩, 애니메이션의 조작감을 검증한다. 눈덩이의
붙기·뭉치기·밀기·터뜨리기 같은 **실제 게임플레이**는 `PenguinSnowball`(E/Q, `../Snow/`의
`SnowBallCarrier`·`SnowCpuStage` 물리)이 소유한다 — 2026-08-21 `/main`에서 별도로 만들어진
것을 이 폴더로 옮겨 온 것이다. 이 폴더가 소유하는 것은 그 위에 얹는 **양 날개를 눈덩이
가장자리에 대는 시각 표현**이다(`PenguinSnowballPush`). 물리와 표현이 서로 다른
컴포넌트라 파일이 겹치지 않고, `PenguinSnowballPush`는 `PenguinSnowball.Held`(지금 붙잡은
`SnowBallCarrier`)를 읽기만 한다 — 눈덩이를 스스로 찾거나 소유하지 않는다.

**2026-08-21부터 `Cleanliness/Scenes/SinglePlay`의 실제 플레이 주체다.** 2026-08-31부터 씬 빌더는
`PF_Penguin`의 Variant인 `MomentumHandling/Prefabs/PF_Penguin_MomentumHandling`을 프리팹 연결
상태로 심는다. 기본 펭귄의 애니메이션·카메라·입력·눈덩이 변경을 상속하면서 관성 조작만 더한다.

## 멀티플레이 진입점 (2026-08-24)

싱글 프리팹(`Prefabs/PF_Penguin`)은 그대로 두고 **변형** `Resources/PF_PenguinNet` 을 따로 둔다.
변형이라 값을 상속하므로 **수치가 갈리지 않는다.**

| | |
|---|---|
| `PenguinLocomotion.Step(dt, in PenguinMoveInput)` | **본문 하나.** 걷기·점프·슬라이딩의 수치는 여기에만 있다 |
| `PenguinSnowball.StepActions / StepPush` | 같은 모양 |
| `FixedUpdate` (기존) | 런너가 없을 때만 돈다(`NetworkDriven` 가드) |
| `PenguinNetAvatar` (변형에만) | `FixedUpdateNetwork` 에서 확정된 서버 틱에 위를 부른다 |

`PenguinLocomotion` 자체를 `NetworkBehaviour` 로 만들지 않은 이유: 그러면 `PF_Penguin` 에
`NetworkObject` 가 필요한데 이 프로젝트에는 씬에 배치된 `NetworkObject` 가 하나도 없다.

**예측은 켜지 않았다.** 서버만 로코모션을 돌린다 — 서버에서는 `Runner.IsForward` 가 항상 참이라
재시뮬레이션 위험(위상 누적, 에지 래치, **되감기지 않는 `sharedMaterial` 스왑**)이 사라진다.
대가는 자기 입력 1 RTT 지연이고 되돌릴 수 있다.

**카메라 요를 입력으로 보낸다.** 데디 서버에는 원격 플레이어의 카메라가 없다. 완성된 방향 벡터를
보내면 `CameraRelativeDirection` 의 크기 클램프를 서버가 강제할 수 없다.

### ⚠ 연출은 복제한다 — 클라이언트에서는 `Step` 이 한 번도 돌지 않는다 (2026-08-25)

예측을 켜지 않았으므로 `PenguinLocomotion.Step` 은 **서버에서만** 돈다. 그래서 클라이언트의
로코모션은 `Speed` 도 `IsGrounded` 도 `IsSliding` 도 **영원히 기본값**이다. 몸은
`NetworkRigidbody` 보정으로 잘 움직이는데,

- 애니메이터는 선 자세로 미끄러지고 (`Speed`=0, `IsGrounded`=false 라 낙하 상태로 보인다)
- 몸통은 설면 기울기도 카빙 린도 다이브 피치도 안 잡고 (`PenguinBodyMotion`)
- 카메라의 속도 기반 거리·FOV·전방 여백이 죽는다 (`PenguinCameraOrbit`)

**남의 펭귄만이 아니라 클라이언트에 앉은 자기 펭귄도** 그렇다. 조작은 다 보내지는데 화면에서만
아무 일도 안 일어나므로, 증상이 네트워킹처럼 보이지 않는다.

`Step(dt, in PenguinMoveInput)` 이 입력을 인자로 받는 것과 같은 모양으로 **연출 상태도 인자로
받는다** — `PenguinPresentation`. 권위 피어는 `CapturePresentation()` 으로 꺼내 게시하고,
나머지는 `PenguinNetAvatar.Render()` 에서 `ApplyPresentation()` 으로 앉힌다. 본문 하나, 채우는
길 둘이다.

| 보내는 것 | 왜 |
|---|---|
| `Speed`·`HorizontalVelocityDirection` | 애니메이터와 카메라. 걷기의 `Speed` 는 **의도 속도**라 몸의 속도에서 못 구한다 |
| `GroundNormal`·`LateralGripAccel` | 몸통의 설면 기울기와 카빙 린 |
| `Grounded`·`Sliding`·`Diving` | 상태기의 결과. 규칙이 `Step` 안에만 있어 재유도할 수 없다 |
| `JumpCount` | **펄스가 아니라 계수기다.** 한 틱짜리 펄스는 그 틱을 못 본 피어가 통째로 놓친다 |
| `PushHeld` | 밀기 날개 자세. 남의 아바타에는 입력 리더가 꺼져 있어 로컬 입력으로는 못 그린다 |

보내지 않는 것도 이유가 있다. `CurrentSpeed01` 은 `Speed` 와 슬라이딩 여부에서 프리팹의 커브로
나오므로 각 피어가 스스로 구한다 — 보내면 같은 규칙이 두 곳에 산다.
`IsSnowballMounted`·`IsSnowballSideAttached` 는 연출이 아니라 이동 규칙이 읽는 값이라 비권위
피어에는 의미가 없다.

**⚠ `ApplyPresentation` 을 권위 피어에서 부르면 안 된다.** 그것이 앉히는 `_state` 는 서버에서는
다음 `Step` 이 읽는 상태기의 현재 위치다. 한 틱 늦은 복제본으로 덮으면 전이가 어긋난다.
`Render()` 가 `HasStateAuthority` 로 먼저 빠져나가는 이유가 그것이다.

**⚠ 밀기 자세는 로컬 입력을 읽지 않는다.** `PenguinSnowballPush` 는 예전에
`_input.PushSnowHeld` 와 `PenguinSnowball.Held` 를 읽었는데, 멀티에서는 둘 다 클라이언트에
없다 — 입력 리더는 남의 아바타에서 꺼져 있고 `Held` 는 붙기가 서버 일이라 항상 null 이다.
지금은 `IsPushHeld` 와 `HeldForPose` 를 읽는다. 루트 `AGENTS.md` 의 "연출은 복제된 상태로
그린다" 가 이 경우다.

### 같이 밀기 — 판정은 마커를 보는 쪽이 한다 (2026-08-24)

**서버는 타이밍을 다시 판정하지 않는다.** 마커는 각자의 화면에서 돌고, 서버 위상은 클라이언트가
본 위상이 아니다. 클라이언트가 초록 구간에서 눌렀는데 지연 때문에 실패로 처리되면 그것은 조작이
아니라 네트워크가 판정한 것이다. 그래서 흐름이 이렇게 나뉜다.

| 어디 | 무엇 |
|---|---|
| `PenguinNetAvatar.Update` (로컬만) | `HeldForPresentation` 의 위상으로 판정해 `CoopShoveInputRelay.Queue()` |
| `SessionLauncher.OnInput` (Core) | 릴레이의 0.2초 펄스를 `CoopShoveSuccess`/`Failure` 비트로 실어 보낸다 |
| `PenguinNetAvatar.FixedUpdateNetwork` (서버) | 비트 둘을 `CoopShovePressed` + `CoopShoveSuccess` 로 나눠 담는다 |
| `PenguinSnowball.StepActions` (본문) | 받은 판정을 그대로 `SubmitCoopTiming` 에 넘긴다 |

싱글은 마커를 보는 쪽이 곧 본문을 도는 쪽이라 `PenguinSnowball.Update` 가 같은 판정을 한다.

**⚠ 참가자 비트는 신원이 하나여야 한다.** `SnowBallCarrier.ParticipantBit` 은 넘겨받은 것이
`NetworkBehaviour` 면 `InputAuthority.PlayerId` 비트를, 아니면 자기 안의 로컬 슬롯을 준다.
`PenguinSnowball` 은 `MonoBehaviour` 라 서버가 슬롯 비트로 등록하는데 클라이언트 HUD 는 아바타로
조회해 PlayerId 비트를 묻는다 — 두 비트가 달라서 **클라이언트에게는 타이밍 창이 아예 열리지
않는다.** `PenguinSnowball.CoopIdentity` 를 진입점이 아바타로 세워 신원을 맞춘다.

**⚠ 클라이언트의 `PenguinSnowball.Held` 는 영원히 null 이다.** 붙기는 서버만 한다. 로컬 HUD 가
어느 공을 그려야 하는지는 `[Networked] PenguinNetAvatar.HeldBall` 로만 알 수 있다. HUD 는
`Awake` 가 아니라 진입점이 `HasInputAuthority` 일 때만 만든다 — 카메라·오디오 리스너와 같은 부류다.

레벨(에지 아님)로 읽어도 되는 이유: 릴레이 펄스는 0.2초인데 창이 끝나고 다시 열리기까지 최소
0.35초(`CoopStrainDelayHardSeconds`)가 걸린다. 그 상수를 줄이면 에지 판정이 필요해진다.

## 달리기 체력과 점프 쿨타임 (2026-08-26)

`PenguinStaminaState`(순수 struct) + `PenguinLocomotion`의 타이머 하나. 스펙은
`docs/specs/2026-08-26-penguin-stamina-jump-cooldown.md`.

**체력은 Shift 달리기만 제한한다.** 점프도 슬라이딩도 체력을 쓰지 않는다 — 원인이 겹치면
튜닝이 어려워진다. 다 쓰면 걷기로 내려가고, `ExhaustExit01`(기본 30%)을 넘어야 다시 달린다.
그 문턱이 없으면 0 근처에서 한 틱 달리고 끊기기를 반복하는 **딱딱이 달리기**가 된다.

**깎는 근거는 입력이 아니라 결과다.** `_sprintedLastStep` — 지난 스텝에 걷기 분기가 실제로
달리기 속도를 골랐는가 — 로 깎는다. Shift 를 쥐고 눈덩이에 올라타 있거나 슬라이딩 중일 때는
달리는 것이 아니라서, 입력으로 깎으면 아무 이득 없이 체력만 준다. 제자리에서 Shift 만 쥐고
있는 것도 달리기가 아니다(이동 입력이 있어야 깎인다). 한 스텝 지연은 눈에 보이지 않는다.

**거절당한 Shift 도 회복한다.** 탈진 중에 Shift 를 놓지 않으면 영영 못 회복하는 함정을
만들지 않기 위한 것이고, EditMode 테스트가 이것을 고정한다.

⚠ **실전에서 체력은 거의 깎이지 않는다 — 알고 남긴 것이다.** Shift 를 쥔 채 눈밭을 달리면
공중에 뜨는 순간 `!grounded && !IsSliding && SprintHeld → EnterSliding()` 로 **슬라이딩**에
들어가고, 움직이는 동안에는 자동 종료도 안 걸려 계속 거기 머문다. 슬라이딩은 걷기 분기를 안
거치므로 `_sprintedLastStep` 이 켜지지 않는다. 2026-08-26 실측:
`controlState=Sliding · grounded=False · speed=6.55m/s · stamina=1.00`. 평지에서도 같다.
체력을 실제로 체감시켜야 하면 (A) 슬라이딩도 체력을 쓰게 하거나 (B) 공중 Shift 자동 진입을
없애야 한다 — 둘 다 활강 필을 바꾸는 결정이라 이번에는 하지 않았다.

**점프 쿨타임은 4갈래가 공유한다.** `ApplyJump`(보행) · `Jump()`(운반 중 눈 위) ·
`JumpFromSlide()`(슬라이딩) · `BareHop()`(맨바닥)이 모두 `MarkJumped()` 를 지나며 거기서
타이머를 찍는다. **슬라이딩 점프에 자기 타이머를 주면 슬라이딩으로 우회해 연타된다** —
PlayMode 테스트가 이 우회를 막는다. UI 는 없다(내부 규칙이다).

**권위는 공짜로 따라온다.** 예측을 켜지 않아 `Step` 은 서버에서만 도므로 그 안에서 깎는 값은
그 자체로 서버가 정한 값이다. 바를 그리는 쪽은 `PenguinPresentation.Stamina01` → `[Networked]`
→ `ApplyPresentation` 이라 **모든 피어가 `PenguinLocomotion.Stamina01` 하나만 읽으면 맞고**,
HUD 에 싱글/멀티 분기가 없다. 로컬 바가 RTT 만큼 늦는 것은 의도된 결과다 — 자기 펭귄의
속도·접지도 이미 서버 값을 그리고 있어서, 체력만 앞서 그리면 그것만 어긋난다.

## 현행 조작과 슬라이딩 (2026-08-25)

이 절이 아래의 2026-08-22 Phase 3, 폐기된 ragdoll 실험 및 삭제된 CharacterController 기록보다 우선한다.
아래 2026-08-22의 동시 양발 킥과 공중 Shift 다이브 기록은 역사다. 현행은 교대 발 밀기와 정상 점프다.

키보드 입력은 `PenguinInputReader`의 `Gameplay` 맵 하나에서 읽는다. 입력 맵을 상태별로 나누는 대신
`PenguinControlState`가 상위 조작 상태를 하나만 유지하고, `PenguinLocomotion`·`PenguinSnowball`·
`PenguinActions`가 그 상태에서 허용된 입력만 소비한다. 상태를 중복 표현하는 로코모션 bool은 두지 않는다.

| 상태 | 입력과 결과 |
|---|---|
| 일반 이동 | WASD 이동, Shift를 누르는 동안 3.5→5.5m/s 달리기(**체력이 남아 있는 동안만**), Space 0.5m 점프(**0.35초 쿨타임**) |
| 공중 슬라이드 전환 | 지상 Shift+Space 또는 일반 점프 뒤 공중 Shift. 일반 Space와 같은 수직 속도를 유지한 채 즉시 슬라이딩 상태로 들어가고, Jump에서 슬라이딩 자세로 0.1초 블렌딩한다. 공중에서는 관성·조향을 쓰고 착지하면 지면 마찰·카빙이 그대로 이어진다 |
| 슬라이딩 | A/D는 지면 접선에서 카빙, W는 웅크려 항력·그립 감소. Shift는 좌우 발 교대 `AddForce` 추진 |
| 자동 종료 | 지면 접선 속도가 1.0m/s 이하로 0.2초 유지되면 일반 이동으로 복귀 |
| 슬라이드·운반 점프 | 눈 위 Space는 기존 일반 점프다. 맨바닥에서는 상태를 유지한 채 낮게 점프하며, 방향키가 없으면 수평 관성만 보존하고 WASD가 있으면 캐릭터 기준 해당 방향으로 같은 크기의 작은 속도를 더해 한 번에 약 0.5m 이동한다. 운반 질량으로 이 접근용 이동을 추가 감속하지 않으며 대각선은 정규화한다. 작은 점프 중에는 접지 레이의 0.15m 여유가 지면을 잡더라도 캡슐이 0.025m 안으로 실제 복귀할 때까지 공중으로 처리해 맨바닥 마찰이 이동을 즉시 지우지 않는다 |
| 운반 전진 마찰 | 운반은 슬라이딩 조향과 교대 발 밀기를 재사용하지만 발로 하중을 지탱하므로 지면 피복과 무관하게 `_carryForwardFrictionMu=0.05`를 쓴다. 맨바닥 마찰 0.5를 그대로 쓰면 평균 발 추진력보다 저항이 커 평지에서도 출발할 수 없다. 운반 충돌 프록시도 루트 캡슐과 같은 `PM_Frictionless`를 써야 프록시만 지면에 걸려 떨지 않는다 |
| 운반 저속 출발·조향 | 지면 접선 속도 0.5m/s 이하에서는 운반 질량별 발차기 배율을 `0.85→0.65`로 높이고 A/D가 차체 전방 기준 최대 60°를 먼저 가리킨다. 보조는 2m/s까지 부드럽게 사라져 이후에는 기존 운반 배율 `0.65→0.4`, 최대 슬립각 30°, 순항 목표 6.5→3.5m/s를 그대로 쓴다. Shift가 없으면 추진하지 않는다 |
| 외부 충돌 | 루트 캡슐이 계속 처리한다. 중간 충격은 Damage. 큰 충격은 조작과 X/Z 회전 제약을 풀어 단일 Rigidbody가 회전하며 날아가고, 정적 지면 착지 시 `BodyPivot`의 월드 자세를 보존한 채 고정 0.28초 동안 Dead 86% 누운 자세로 이어진다. 2초 유지 뒤 Actions 레이어를 0.45초 동안 0으로 내려 Idle로 확실히 복구한다 |

활강의 기본 속도는 Rigidbody 중력, 지면 접선, 전진 마찰, 공기 저항에서 나오고 Shift 발 밀기가
추가 힘을 보탠다. 힘은 11.7m/s에서 0으로 줄어 무한 가속을 막는다. Steep 계열의 무게감은 루트 물리를 설면 법선에 붙여 계산하고
`BodyPivot`만 최대 30°까지 지면에 맞춰 기울여 만든다. A/D는 차체를 무한 회전시키지 않고
속도 방향 기준 목표 슬립각을 만들며, 그립 한계에서만 옆 미끄러짐이 남는다. 이 때문에 고속일수록
선회 반경이 자연스럽게 커지고, 지형 굴곡이 진행 방향과 자세에 함께 드러난다.

Penguin PlayMode 테스트 38개가 단일 Rigidbody·골반 X/Z 잠금/무입력 요 감쇠/달리기/
비반복 점프 자세 유지·일반 점프와 Shift+Space의 동일 정점·공중 Shift 즉시 슬라이드 전환과 착지 연결/교대 발 추진/자동 정지/S 무효/W 무추진/고속 카빙/Space 점프의
관성·자세 안정/카메라 수직 감쇠와 상위 상태 전환·눈덩이 조작·공격 게이트를 고정한다.
최종 손맛은 `PF_Penguin`의 위 계수들을
한 번에 하나씩 조정하되, S 무효와 W 무추진 규칙은 바꾸지 않는다.

### 관성 조작 Variant와 SinglePlay 적용 (2026-08-29, 2026-08-31 적용)

`MomentumHandling/`은 S 브레이크와 누적 가속·조향을 검증하고 SinglePlay에 공급하는 Variant다.
`PF_Penguin`에는 새 컴포넌트가 없지만, 프로덕션 SinglePlay는 이 Variant를 사용하므로 S 브레이크와
관성 조작이 활성화된다. 기본 프리팹을 직접 쓰는 다른 씬의 S 무효 규칙은 그대로다.
`PF_Penguin`의 Variant인 `MomentumHandling/Prefabs/PF_Penguin_MomentumHandling`에만
`PenguinMomentumHandling`이 붙는다. 테스트 씬은
`MomentumHandling/Tests/Penguin_MomentumHandling_Test.unity`이며 Build Settings에는 넣지 않는다.

- 슬라이딩·운반 S는 지면 접선 속도의 반대 방향으로 최대 240N을 낸다. 정지에 필요한 힘으로
  잘라 속도 부호를 뒤집지 않는다. 힘이 고정이므로 운반물이 무거울수록 제동거리가 길다.
- 눈덩이 S는 참가자당 최대 7800N을 현재 접선 속도 반대로 제출한다. W 목표보다 이미 빠를 때는
  추진을 0으로 둘 뿐 역방향 힘을 만들지 않아, 경사 중력이 목표 속도를 넘길 수 있다.
- 누적 추진은 2.5초 동안 차고 S에서 0.3초로 빠르게 빠진다. 무거운 운반물·큰 눈덩이는 출발
  가속이 낮지만 최종 목표 속도는 더 높다. 목표는 속도 클램프가 아니라 양의 추진 상한이다.
- 같은 A/D를 유지하면 눈덩이 반지름에 따라 0.35~3초 동안 조향 권한이 쌓이고 방향을 뒤집으면
  0부터 다시 시작한다. 최대 Stage 4는 기준 최고속도에서 방향전환 직후 0%, 완전 누적 33%다.
  운반 질량과 눈덩이 성장도, 눈덩이의 실제 속도가 조향 권한을 추가로 낮춘다.
- Variant가 미는 눈덩이는 W/S 무입력에도 평지 강제 정지를 우회해 Rigidbody 감쇠·충돌·중력으로
  코스팅한다. SinglePlay도 이 경로를 사용하며, 기본 `PF_Penguin`을 쓰는 씬의 기존 정지는 그대로다.
- E로 밀기 상태를 해제한 공도 0.05m/s 아래로 느려질 때까지 같은 코스팅 저항을 유지한다. 공을
  다시 잡으면 해제 코스팅은 즉시 끝나므로 새 밀기 입력과 경쟁하지 않는다.

새 PlayMode 테스트 7개와 기존 `PenguinSlideHandlingTests`·`PenguinCarryTests`·
`PenguinSnowballPushTests` 회귀를 합쳐 **51/51 통과**했다. 수동 씬에는 5m 제동 마커,
슬라럼, 10°·20° 비탈, 가벼운/무거운 선물과 눈덩이가 있다.

## Rigidbody 재작성 (2026-08-22, 진행 중)

`PenguinLocomotion`의 `CharacterController`를 걷어내고 접촉 기반 `Rigidbody`로 전면 재작성하는
중이다. 슬라이딩은 손으로 짠 스칼라 장부(`_slideSpeed` 적분) 대신 **비등방 마찰**(날 방향은
미끄럽고 옆 방향은 잡힌다)로 다시 짰다. **진행 상황: Phase 1(물리 바디·걷기·점프·입력 래치)·
Phase 3(슬라이딩)·Phase 4(진짜 충돌·눈덩이)·Phase 5(연출 재배선)·Phase 6(테스트·문서) 전부
완료.** Phase 2는 별도 단계로 존재하지 않는다 — 걷기·점프가 이미 Phase 1에 함께 들어갔다.

`PF_Penguin`은 mass 30, capsule height 1.7/radius 0.4/center y 0.85인 **단일 Rigidbody**다.
평상시 X/Z 회전은 잠그고 요 회전만 토크로 열어 둔다. `PM_Frictionless`는 슬라이딩 중 루트
캡슐 하나에만 붙고, 슬라이드 이탈 시 다시 기본 재질로 돌아간다.

> 2026-08-23~24의 자유회전 루트·3-body·7-body ragdoll 기록은 실패한 실험의 근거로 아래에
> 남겨 둔다. 현행 프리팹과 코드에는 `PenguinPhysicalRig`나 `PhysicsRig` 자식이 없다.

### 왜 접촉 기반이고 "떠 있는 캡슐"이 아닌가

처음엔 콜라이더를 지면에서 살짝 띄우고 스프링으로 높이를 유지하는 구조(래이드-하이트 스프링)를
검토했으나 철회했다. 이유 둘 — (1) `SnowBallCarrier`가 이미 접촉 기반으로 잘 돌고 있어서(진짜
`Physics.gravity`, `SampleSupportNormal`은 법선만 읽고 높이는 안 건드림) 펭귄만 다른 문법을
쓸 이유가 없었고, (2) `stepOffset`이 사라지는 문제를 실측 없이 아키텍처로 미리 해결하려 한
것이 투기였다. `SinglePlay.unity`에 `Curb_`·`DoorLanding`·`CurbRamps`·`Bridge_*` 가 38곳
있지만 `CurbRamps`가 이미 있다는 것 자체가 램프로 우회 가능하다는 뜻이라, 실제로 못 넘는
지점이 나오면 그때 스피어캐스트 리프트 같은 걸 얹기로 했다 — 아직 그 측정을 안 했다.

### 중력을 더 이상 소유하지 않는다

예전 `_gravity = -20`("중력이 2배인 세계")은 펭귄이 `BlockNormal`/`IgnoreCollision`으로 다른
물리와 완전히 격리돼 있던 시절의 결정이었다. `SnowBallCarrier`가 이미 `Physics.gravity`
(−9.81)를 쓰고 있으므로, 이제 눈덩이와 진짜로 부딪히는 펭귄만 다른 중력을 쓸 이유가 없다.
`Rigidbody.useGravity = true`로 전환했고, `GravityMagnitude`는 `Physics.gravity.magnitude`를
그대로 반환한다. 각도로 표현되는 값(자연활강각 `atan(μ)`, 발질 한계각)은 g와 무관해 안
바뀌지만, 절대 속도(25° 램프 끝 속도 등)와 점프 체공시간은 영향을 받는다 — 체공시간이 늘어
"붕 뜨는" 느낌이면 하강 중력 배수보다 먼저 `_jumpHeight` 를 낮춰 볼 것(둘 다 g를 정직하게
유지한 채 손댈 수 있는 손잡이다).

### `PM_Frictionless`는 아직 붙이지 않았다

계획 문서는 `Vehicle/PM_Frictionless`(마찰 0/0, Combine=Minimum)를 `Core/`로 승격해 붙이는
것을 상정했지만, **그건 비등방 마찰 모델이 실제로 마찰을 소유하는 Phase 3의 일이다.** 지금은
전용 모델이 없으므로 물리 재질을 비워 두어(Unity 기본값, 대략 정적/동적 마찰 0.6) 걷기와
서기가 평범한 PhysX 마찰로 성립하게 했다 — 25° 램프에서 속도 0으로 정지 유지를 Play Mode로
실측 확인(아래 참고). 마찰 0을 붙이면 지금 당장은 아무 힘도 안 걸리는 25° 경사에서 그냥
미끄러져 내려간다.

### 걷기 — PD 가속도 힘 + 물리 요 모터

목표속도와 현재속도의 오차를 `ForceMode.Acceleration`으로 미는 P 제어이고, `_walkAccel`(기본
40 m/s²)로 상한을 걸어 순간 스냅이 아니라 짧은 시간에 크리스프하게 멈추게 한다. 회전은
`MoveRotation`으로 자세를 대입하지 않고, 목표 방향 오차를 목표 Y 각속도로 바꾼 뒤 별도의
`ForceMode.Acceleration` 요 토크로 따라간다. 그래서 충돌로 생긴 X/Z 기울기는 방향 전환 중에도
보존되고, 직립 모터와 방향 모터가 서로의 축을 덮지 않는다.

### 점프 — 대입이지 덧셈이 아니다

`v = √(2gh)`로 높이에서 속도를 계산해 `linearVelocity.y`에 **대입**한다(더하지 않는다) — 낙하
중에 뛰어도, g가 나중에 바뀌어도 항상 같은 높이가 나오게 하려면 기존 수직 속도를 지워야 한다.

### 입력 래치 — 왜 필요했는가

`PenguinLocomotion`이 `Update`에서 `FixedUpdate`로 내려가면서, `PenguinInputReader`가 래치
없이 `wasPressedThisFrame`을 매 `Update`마다 덮어쓰던 예전 방식은 문제가 된다 — 120fps 대
50Hz 물리 스텝 기준으로 점프 같은 순간 입력의 약 58%가 조용히 사라진다. 이제 `Update`에서
`_jumpPending` 등의 내부 플래그로 OR 누적하고, `FixedUpdate`에서 공개 프로퍼티로 한 번
승격한 뒤 즉시 비운다. `PenguinLocomotion`과 `PenguinSnowball`이 같은 물리 스텝에서 이 값을
읽어야 하므로, `PenguinInputReader`가 그 둘보다 먼저 실행돼야 한다 — `PenguinSnowball`이 이미
`[DefaultExecutionOrder(-100)]`이라 `PenguinInputReader`는 `-200`으로 확실히 앞선다.
**실측(Play Mode, 2026-08-22)**: 점프 플래그를 리플렉션으로 주입해 매번 정확히 1회씩
`Jumped` 이벤트가 발동함을 확인 — 빠지거나 중복되지 않는다. `MoveInput`·`SprintHeld`·
`PackSnowHeld`는 순간 이벤트가 아니라 "지금 눌려 있는가"이므로 래치하지 않는다.

### Phase 1이 건드린 다른 파일들 — 최소 이식이지 재설계가 아니다 (⚠ Phase 4에서 재설계 완료)

`PenguinLocomotion`과 한 GameObject에 있는 `PenguinSnowball`도 `[RequireComponent(typeof(
CharacterController))]`를 갖고 있어서, 이걸 안 바꾸면 에디터가 CC 제거 자체를 막는다
("다른 컴포넌트가 필요로 함"). 그래서 이 파일도 최소한으로 같이 손댔다 — 필드 타입만
`CapsuleCollider`/`Rigidbody`로 바꾸고 게임플레이 로직(밀기 판정, `BlockNormal`, 뭉치기)은
그대로 두었다(**당시엔.** `BlockNormal`은 Phase 4에서 삭제됐다 — 아래 "Phase 4" 절 참고).
`PenguinImpactRelay`도 `_controller.velocity` → `_rigidbody.linearVelocity`로 타입만
맞췄다(**이것도 Phase 4에서 `OnCollisionEnter` 기반으로 전면 재작성됐다**).

`PenguinSnowball.TickSideOrbit`이 `Update`에서 `Rigidbody.MovePosition`을 호출하던 임시방편도
Phase 4에서 `FixedUpdate`로 옮겨 해결했다.

### 제자리 회전 버그의 옛 수정과 2026-08-23 대체

Phase 1 체크인 직후 Play Mode 실측에서 **가만히 서 있어도 계속 도는** 증상이 나왔고, 당시에는
X/Z를 잠근 채 모든 각속도를 매 스텝 0으로 지워 고쳤다. 이 방식은 정지 안정성은 얻었지만 작은
충격까지 사라져 몸이 지나치게 뻣뻣했다.

2026-08-24의 7-body 리그는 골반과 흔들림을 분리했다. 평상시 골반 X/Z는 잠가 걷기 축을
보호하지만 요 회전은 토크로 감쇠하며 자유다. 큰 충격이나 명시적 물리 해제 때만 골반의 모든 회전 제약을
풀고, 몸통·머리는 평상시에도 항상 동적 Rigidbody로 남는다. 따라서 작은 충격은 관절 모터에 맞서
몸통·꼬리·발·날개가 흔들리고, 큰 충격은 골반까지 넘어뜨린다. 안정되면 기립 토크로 세운 뒤 X/Z를 재잠근다.

## Phase 3 — 슬라이딩 (2026-08-22, 현행 조작으로 대체됨)

`_slideSpeed` 적분 대신 **비등방 마찰**로 다시 짰다. 배 깔고 미끄러지는 몸은 방향에 따라
마찰이 다르다 — **날 방향(전진)은 미끄럽고 옆 방향(그립)은 잡힌다.** 이 하나에서 선회 감속·
선회반경·드리프트가 전부 창발한다. `TickSliding`(`PenguinLocomotion.cs`) 하나에 다 있다.

### 계수 — 물리 상수는 그대로, 튜닝 상수만 g 비율로 재조정

| 계수 | 값 | 왜 |
|---|---|---|
| `_snowFrictionMu` | 0.05 | 무차원 물리값(눈 위 매끄러운 물체). g 와 무관, 그대로 유지 |
| `_bareFrictionMu` | 0.5 | 무차원 물리값(바위·콘크리트). 그대로 유지 |
| `_lateralGripMu` | **1.2**(구 0.6) | 튜닝 상수 — g=20 시절 `_turnBySpeed` 곡선의 무릎(v=4.5 에서 150°/s)과 선회반경이 같도록 역산. g가 반 됐으니 두 배 |
| `_impulsePerKick`(`PenguinSlideKick`) | **발당 1.5**, 양발 합계 3.0/사이클(구 1.1) | 손맛 보강으로 36% 상승. 양발이 같은 위상으로 한 번에 밀며 한 프레임 임펄스가 아니라 회수 구간 전체에 분산 |
| `_airDragForceN` | 0.0168 | 힘 도메인(N/(m/s)²). 기존 가속도 계수(0.00056)×질량(30kg). g 와 무관 |
| `_brakeForceN` | 180 | 힘 도메인. 기존 제동 가속도(6 m/s²)×질량(30kg) |
| `_kickBiteSpeed` | 11.7(불변) | 속도값이라 g 와 무관. 최고 속도는 여전히 이게 정한다 |

**검산**: `μ_lat=1.2`, `g=9.81` → `v=4.5`에서 `ω = 1.2×9.81/4.5 = 262°/s`. 옛 곡선은 g=20
기준이었으니 절대 비교는 안 맞지만, **곡선 자체가 물리 상수 하나로 대체됐다**는 게 핵심이다.

### 경사 가속에 코드가 없다 — 공짜로 얻었다

CC 시절엔 지면 법선으로 중력의 접선 성분을 직접 계산해 진행 방향에 투영했다. 이제
`Rigidbody.useGravity=true`가 진짜 중력이라, 경사에서 PhysX가 알아서 굴려 내린다. 우리
코드는 날 방향 마찰(그리고 브레이크·항력)만 얹는다 — "경사가 직접 가속한다"는 문서의
오래된 요구사항이 삭제된 코드 없이 자동으로 성립한다.

### 마찰 재질 스왑 — 채널 하나에 주인 하나

`Vehicle/PM_Frictionless.physicMaterial`(마찰 0/0, Combine=Minimum)을 **두 번째 소비자**
자격으로 `Core/Physics/`로 승격했다(Unity MCP로 이동, GUID 보존 — `Vehicle`의 참조는 안
끊어졌다, 실측 확인). 이걸 슬라이딩 진입/이탈 시점에만 캡슐에 붙였다 뗀다:

- **슬라이딩 진입** → `_capsule.sharedMaterial = _slidingMaterial`(마찰 0). 비등방 마찰
  모델이 마찰을 전부 소유해야 하므로 PhysX 몫은 0이어야 한다.
- **슬라이딩 이탈** → `null`(기본 재질)로 되돌린다. 걷기는 여전히 PhysX 기본 마찰(~0.6)로
  슬로프 위에 선다 — Phase 1에서 내린 결정 그대로.

슬라이딩 진입은 **걷던 수평 관성을 그대로 보존**한다. 지상 Shift는 즉시 슬라이드가 되고,
공중 Shift는 아래의 별도 다이브 상태가 된다. 이탈 뒤에는 보행 가속도를 0.25초에 걸쳐
되돌려, 8m/s 관성을 한 물리 스텝에 3.5m/s로 잘라내지 않는다.
`IsSnowballMounted`/`IsSnowballSideAttached`로 전환될 때도 정리 로직을 거친다 — 안 거치면
슬라이딩 중 눈덩이를 잡았을 때 마찰 재질이 프리즈된 채 남는다.

### 공중 Shift — 다이브에서 착지 슬라이드로

공중에서 Shift를 누르면 `IsDiving=true`, `IsSliding=false`인 별도 상태로 들어간다. 기본 중력에
18m/s² 하강 가속도를 더하며, 최대 낙하 속도는 14m/s로 제한한다. A/D를 누르면 수평 **속력은
보존**한 채 궤적과 차체 방향을 최대 65°/s로 함께 돌린다. 입력이 없으면 기존 수평 관성은 그대로다.
공중 킥은 `AddSlideImpulse`의 `IsGrounded` 가드에 막혀 추진력을 만들지 않는다.

그림은 새 클립 없이 `Swim`을 그대로 재사용한다. `PenguinAnimatorDriver`가 다이브도 Animator의
`IsSliding` 파라미터로 보내고, `PenguinBodyMotion`이 그 자세 위에 28° 코다운 피치를 스프링으로
더한다. 카메라는 지상 슬라이드와 같은 실제 수평 궤적 추적을 유지한다. Shift를 잡은 채 지면에
닿으면 상태만 `IsDiving → IsSliding`으로 바뀌므로 자세·카메라·수평 관성이 끊기지 않는다.

### 슬라이드 중 Space — 수평 관성을 보존한 안정적인 점프 (2026-08-24)

Space 입력 순간 `PM_Frictionless`를 떼고 상태는 `Normal`로 돌아가며, 그 직전 수평 속도와
`v = √(2gh)` 점프 속도를 일곱 Rigidbody에 함께 대입한다. 루트 X/Z 회전 잠금과 물리 리그의
조작권은 유지하며 회전 임펄스를 주지 않는다. 공중에서는 보행 PD 제어를 0으로 유지해 슬라이딩의
수평 관성을 자르지 않고, 착지한 뒤에만 0.25초 동안 일반 이동 제어를 되돌린다.

`ReleaseSlideToPhysics`는 외부 충돌·복구 검증처럼 정말 물리에 조작권을 넘길 때만 남아 있다.
그 경로에서는 이동 힘과 요 토크에 `MovementAuthority01`의 0~1 배율이 곱해지고, 저속에서
`UprightAssist01`이 몸을 세운 뒤 골반 X/Z를 재잠근다. 캡슐이 누워도 접지를 찾도록 지면 레이는
`_capsule.bounds.center`와 월드 Y extents를 사용한다. 카메라 피벗은 루트 roll을
`Camera.onPreCull`에서 마지막으로 상쇄하고, 루트의 수직 접촉 진동은 0.08초 감쇠해 화면에
한 프레임 단위로 복사하지 않는다.

### 조향 — 무한 요 회전 대신 이동 방향 기준 목표 슬립각

A/D를 오래 누른 만큼 차체를 계속 돌리던 360°/s 자유 요 회전은 삭제했다. 이제 입력은 실제
수평 속도 방향에 대한 목표 슬립각(`±30°`)을 만들고, 그 목표는 0.12초로 부드럽게 따라간다.
차체 요 응답 상한은 0→9m/s에서 240→75°/s로 낮아져 고속일수록 묵직하다. 차체가 비스듬해져
생긴 옆속도를 아래 비등방 그립이 지우면서 **속도 벡터 자체를 끌고 오는 것**이 실제 선회다.
따라서 핸들을 오래 잡아도 빙글 돌지 않고, 그립이 못 따라오는 양만 실제 드리프트로 남는다.

단, **정지 상태에는 기준으로 삼을 이동 방향 자체가 없다.** 이때 A/D가 무반응이면 입력이
고장 난 것처럼 보이므로, 수평 속력이 거의 0일 때는 기존 저속 요 속도(240°/s)로 차체만 제자리
회전시킨다. 추진력은 만들지 않으며, 이동 속도가 생기는 즉시 위의 슬립각·그립 조향으로 넘어간다.

### 그립 — 이번 스텝에 완전히 지우는 힘을, 낼 수 있는 최대치로 자른다

```
desiredCancelForce = -lateralVel * mass / dt   // 옆 속도를 한 스텝에 완전히 지우는 데 필요한 힘
gripForce = ClampMagnitude(desiredCancelForce, μ_lat · N)
```

최대 그립력보다 필요한 힘이 크면(그립이 못 버티면) 옆 속도가 못 다 지워지고 남는다 — 이게
**드리프트**다. 따로 짜 넣은 코드가 없다.

### 자동화 검증의 한계 — 왜 훅을 썼는가

`PenguinInputReader`의 `SlideHeld`/`MoveInput`은 매 `Update`마다 **Input Action 상태로
덮어써진다**(래치하지 않는 레벨 신호라 의도된 설계다 — Phase 1 참고). 리플렉션으로 한 번
주입해도 실제 입력이 없으니 다음 `Update`가 곧바로 원래 값(false/zero)으로 되돌린다.
`Thread.Sleep`으로 대기하면 메인 스레드가 막혀 물리 자체가 안 돈다. `Physics.simulationMode
= Script` + `Physics.Simulate()` 수동 호출도 안 통했다 — `Physics.Simulate`는 물리 적분만
하지 스크립트의 `FixedUpdate`를 대신 불러 주지 않는다.

실제로 먹힌 방법은 `UnityEditor.EditorApplication.update`에 매 에디터 틱마다 원하는 입력을
재주입하는 콜백을 거는 것이다 — 이건 렌더 프레임의 `Update`와는 별개 이벤트라 값이 오래
살아남는다. **이 방법으로도 뜯어보니, 예전에 `MoveInput`을 직접 주입했던 걷기 테스트(Phase
1 실측)는 실은 운 좋게 한두 프레임 새는 값을 잡은 것**이었다 — 지속적인 홀드 검증은 이번이
처음이다. `SendMessage`/실제 키 입력 시뮬레이션 없이 자동화로 손맛까지 검증하는 데는 한계가
있다 — 조향·그립의 정확한 느낌은 사람이 직접 Play를 눌러 확인해야 한다.

## Phase 4 — 진짜 충돌 · 눈덩이 (2026-08-22)

CC 시절엔 CC가 눈덩이의 곡면을 타고 올라가는 문제(실측 접촉 106회, 밀기 0회) 때문에
`Physics.IgnoreCollision`으로 펭귄–공 충돌 자체를 꺼 두고, `PenguinLocomotion.BlockNormal`
로 "안 밀리는 공 앞에서 제자리걸음"을 손으로 흉내 냈다. `PenguinLocomotion`이 평범한
`CapsuleCollider`가 된 지금은 그 문제 자체가 없다 — **둘 다 삭제**했다.

### 삭제한 것

- `PenguinLocomotion.BlockNormal`, `PenguinLocomotion.ApplyImpactBrake` — 프로퍼티·메서드
  자체를 없앴다. 표면을 못 파고드는 것도, 벽에 붙었다 떨어질 때 속도가 실제로 주는 것도
  이제 솔버가 공짜로 한다.
- `PenguinSnowball`의 `SetIgnore`/`SetPassiveCollisionBall`/`TickPassiveSnowballCollision`/
  `_passiveCollisionBall` — 전부 "충돌을 꺼 둔 채 흉내 내기" 장치였다. 충돌이 진짜라 흉내가
  필요 없다.

### 남긴 것 — `SubmitPush`는 그대로다

`SnowBallCarrier.SubmitPush`는 그대로 유지했다. 이건 충돌 우회책이 아니라 **협동 밀기를
합산하는 게임플레이 규칙**이다 — 여러 펭귄의 힘을 한 물리 스텝에 모아 한 번에 적용해야
같은 방향은 더해지고 반대 방향은 상쇄되는 설계가 성립한다. 순수 접촉만으로는 이 합산이
안 나온다. `PlayerPushForceN`(7800N) 재보정은 **하지 않았다** — 이 힘은 `SubmitPush`
채널로 제출되는 값이라 충돌과 이미 분리돼 있고, 진짜 충돌로 생기는 힘(30kg 펭귄이 부딪혀서
미는 힘)은 눈덩이 질량 대비 작아 이중 계산으로 부풀 위험이 낮다고 판단했다. 실제 플레이해
보고 이상하면 여기가 다음 튜닝 대상이다.

### 탑승 중 `isKinematic`

`PenguinSnowball.LateUpdate`가 매 프레임 `transform.position`을 직접 대입해 공 꼭대기에
앵커링하는데, 논-키네마틱 상태로 두면 그 대입이 물리 시뮬레이션(중력·충돌)과 매 프레임
싸운다. `SetMountedOnTop(bool)` 하나로 탑승 상태 전환과 `_body.isKinematic` 토글을 같이
묶었다 — 탑승 중엔 물리 대신 이 대입이 전적으로 위치를 결정한다.

### `TickSideOrbit`을 `Update`에서 `FixedUpdate`로

물리 스텝 사이에 여러 번 부르면 마지막 호출만 적용되는 `Rigidbody.MovePosition`의 특성
때문에 Phase 1에선 컴파일만 맞추고 미뤄 둔 임시방편이었다. `FixedUpdate`는 스텝당 정확히
한 번만 돌기 때문에 옮기는 것만으로 문제 자체가 사라진다.

### `PenguinSnowballPushTests.cs` — 컴파일 에러 1곳만 최소 수정

`경사에서_좌클릭하지_않으면_몸으로_눈덩이를_밀지_않는다` 테스트가 `locomotion.BlockNormal`을
직접 참조해서 **컴파일 자체가 깨졌다**(CC 참조들은 조용히 런타임 실패였지만 이건 진짜
하드 에러). 이 테스트 전체가 지운 메커니즘(`IgnoreCollision`+`BlockNormal`)을 검증하던
것이라 전제가 무효라, `[Ignore(...)]`로 실행은 막고 컴파일만 맞췄다. 전체 재작성은 여전히

진짜 충돌 기준으로 새로 세워야 한다(지금 진짜 충돌에서는 스치기만 해도 약간은 밀리는 것이
정상이라, 옛 "거의 0" 문턱을 그대로 못 쓴다).

### ⚠ 자동화 검증에서 새로 배운 것 — `Update` 는 `EditorApplication.update` 훅으로도 못 뚫는다

Phase 3에서 `SlideHeld`(`FixedUpdate`에서 소비)는 훅으로 지속 홀드를 흉내 낼 수 있었지만,
`PackSnowHeld`(`PenguinSnowball.Update()`에서 소비)는 **안 됐다** — `PenguinInputReader`
(`DefaultExecutionOrder(-200)`)가 `PenguinSnowball`(`-100`)보다 반드시 먼저 실행되므로,
**같은 프레임 안에서 실제 입력이 항상 내 훅보다 나중에 이겨 버린다.** 훅이 `EditorApplication.
update`에서 아무리 먼저 값을 넣어도, 그 프레임의 `Update` 단계가 오면 진짜 `PenguinInputReader.
Update()`가 실제 키 상태(false)로 덮어쓴 **바로 다음에** `PenguinSnowball.Update()`가 그 값을
읽는다 — 순서가 결정적이라 도망칠 틈이 없다. `FixedUpdate`에서 소비되는 값은 물리 스텝이
렌더 프레임과 비동기라 훅이 이길 기회가 남지만, **같은 Update 단계 안에서 순서가 고정된
두 컴포넌트 사이에서는 훅이 원천적으로 못 이긴다.**

해결책은 **리플렉션으로 private 메서드(`TryGrabNearby`, `FixedUpdate`)를 직접, 같은 동기
블록 안에서 호출**하는 것이었다 — 이러면 실제 `Update` 루프가 끼어들 틈 자체가 없다. 여러
번의 `execute_code` 호출에 걸쳐 상태를 유지하려 하면 그 사이 실제 프레임이 돌면서 `Held`가
매번 `Release()`로 풀렸다 — **잡기와 확인은 반드시 한 호출 안에서 끝내야 한다.**

## Phase 5 — 연출 재배선 (2026-08-22)

기울기·카메라 급선회 킥이 읽던 **`v·ω`(원심가속도 추정)를 `TickSliding`이 실제로 낸
그립력으로 교체**했다. 계산이 아니라 물리 그 자체를 읽게 된 것이 이 단계의 전부다.

### 왜 `v·ω` 로는 부족했는가

`v·ω`는 순수 운동학적 추정이다 — 실제로 몸이 그 가속도를 낼 그립이 있는지는 안 본다.
목표 슬립각 제어의 속도별 요 응답은 **차체가 목표를 따라가는 속도**만 제한할 뿐, 그립이 그
방향 전환을 유지하기에 충분한지는 별개 문제다. 그립이 못 버텨 드리프트가 나는 순간에도
`v·ω`는 계속 커질 수 있어서, 몸이 물리적으로 낼 수 없는 각도까지 눕는 그림이 나올 수
있었다 — 순전히 계산상의 위험이었고 실측으로 잡아낸 버그는 아니다.

### `PenguinLocomotion.LateralGripAccel` — 새 소스

`TickSliding`의 그립 계산이 이미 `ClampMagnitude(desiredCancelForce, maxGripForce)`로
**실제로 적용된 힘**을 만들어 두고 있었다. 그 힘을 가속도로 환산해(`/mass`) 공개
프로퍼티로 노출했을 뿐이다 — 새 물리를 추가한 게 아니라 이미 있던 값을 밖으로 뺀 것.
그립이 포화하는 순간 이 값도 정확히 같은 순간에 포화한다(구조적으로, 같은 클램프에서
나오므로).

`PenguinBodyMotion.ComputeTargetLeanDeg`와 `PenguinCameraOrbit.ApplySpeedFraming`(급선회
FOV 킥) 둘 다 이 값을 읽도록 바꿨다 — **몸통 기울기와 카메라 킥이 이제 정확히 같은 순간에
포화한다.** 예전엔 둘 다 각자 `v·ω`를 따로 계산해서, 그립이 포화해도 몸과 카메라가 서로
다른 타이밍에 최대치를 찍을 수 있었다(같은 값을 두 번 계산하는 것 자체가 어긋남의 씨앗).

| 포화값 | 강제로 큰 횡속도(3 m/s)를 준 뒤 한 스텝 → `LateralGripAccel = -11.772`, 이론값 `μ_lat×g = 1.2×9.81 = 11.772`와 정확히 일치 |
| 부호 | 오른쪽(+X)으로 미끄러질 때 그립은 왼쪽으로 당긴다(`-11.772`) — 되돌리는 힘의 방향이 맞다 |
| 클램프 | `leanDeg`가 `atan(11.772/9.81)=50.2°`가 아니라 `_maxLeanDeg`(20°)에서 정확히 잘림 — 클램프 동작 확인 |
| 순수 조향(드리프트 없이) | 속도와 진행방향이 이미 일치하면(옆미끄럼 0) `LateralGripAccel=0` — 핸들만 꺾는다고 즉시 눕지 않는 게 맞다(드리프트는 실제 물리 스텝이 지나야 생긴다) |
| 컴파일 | 에러 0 |

### 아직 안 한 것

- **`_maxLeanDeg`(현재 20°) 재고 필요.** 새 물리 천장이 `atan(μ_lat·g/g) = atan(1.2) ≈ 50°`로
  올라갔다 — 예전(g=20 시절, 32°로 한 번 올렸다가 `cm undo`로 되돌린 값) 기준과 다르다.
  **의도적으로 안 올렸다** — "물리 천장이 몇 도인지"와 "그림이 몇 도까지 보기 좋은지"는
  다른 질문이고, 후자는 사람이 플레이해 봐야 안다.
- `_turnKickStartLateralAccel`(3)·`_turnKickFullLateralAccel`(8, 옛 실측 7.3 기준) 재측정 —
  새 천장(≈11.8)에 맞춰 다시 잴 것. 툴팁에 남겨 뒀다.
- 실제 조향 중 드리프트가 발생하는 과도 구간(핸들을 꺾은 뒤 몇 프레임 만에 그립이 포화하는지)
  은 자동화로 못 재봤다 — `Update` 실행 순서 문제와 달리 이번엔 도구 왕복 지연 때문에 매번
  전환 타이밍을 놓쳤다. 사람이 직접 Play로 확인할 부분.
- Phase 5 당시에는 `PenguinSlideKick`의 그림을 건드리지 않았다. 이후 슬라이딩 손맛 단계에서
  양발을 같은 위상으로 묶고 추진을 FixedUpdate 미는 구간에 분산했으며, 스트레치 세기는 각
  물리 스텝의 요청량 대비 실제 적용량(bite 이후)을 읽도록 맞췄다.

## Phase 6 — 테스트 정리, 그리고 실제로 테스트를 돌려서 나온 것 (2026-08-22)

Phase 1~5는 전부 Play Mode에서 손으로(또는 리플렉션으로) 검증했지만, **실제 NUnit PlayMode
테스트 스위트(`PenguinSnowballPushTests`, 8개)를 돌린 건 이번이 처음이다.** 그 결과 Phase
1~5와 무관한 사전 존재 버그 두 개가 드러났다 — 전부 CC 시절부터 있던 코드다.

### 테스트 파일 컴파일·런타임 정리

- `밀면_공이_움직이고_커지면_같이_느려진다`: `CharacterController` 진단 변수(`cc.enabled`,
  `cc.collisionFlags`)를 `Rigidbody` 기준으로 교체 — CC가 사라져 `null` 역참조로 죽던 것을
  고쳤다.
- `펭귄_몸은_눈덩이의_지지면이_아니다`: **손대지 않았다.** 펭귄 프리팹과 무관한 독립
  `CharacterController` 오브젝트로 `SnowBallCarrier.SampleSupportNormal`의 CC 필터 자체를
  검증하는 테스트라, 우리 Rigidbody 재작성과 상관없이 여전히 유효하다.
- Phase 4에서 `[Ignore]`했던 `경사에서_좌클릭하지_않으면_몸으로_눈덩이를_밀지_않는다`를
  `...의도적으로_밀지_않는다`로 다시 세웠다 — "델타가 거의 0"(옛 IgnoreCollision 시절 기준)
  대신 **"`SubmitPush`가 한 번도 안 나갔는가"**(`PenguinSnowball.DebugPushes`)를 본다. 진짜
  충돌에서는 스치면 물리적으로 정직하게 살짝 밀리므로 델타 자체는 참고용 상한(실측 0.33m에
  여유를 둔 0.7m)으로만 남긴다.

### 발견한 버그 1 — `TickSideOrbit`의 3D 구면 계산이 수직 오프셋에 무너진다

궤도 반지름을 `√(centerDistance² − vertical²)`로 구하던 옛 코드가, 캡슐 **중심**(지상
0.85m)과 작은 공 **중심**(지상 0.2~0.3m)의 수직차가 `centerDistance`(≈0.64m)보다 커지면
근호 안이 음수가 되어 최솟값 0.1m로 무너졌다(실측: 의도한 0.64m 대신 0.10m). 펭귄이 공
위로 거의 빨려 들어가 밀기 방향이 어긋났다.

**3D 구면 기하 자체가 불필요했다** — 둘레 돌기는 지면 위 원 운동이지 공을 감싸는 구면 위
이동이 아니다. `vertical`/`centerDistance` 계산을 통째로 없애고 순수 XZ 반지름(`공
반지름+몸 반지름`)으로 단순화했다 — 버그도 없어지고 코드도 짧아졌다.

### 발견한 버그 2 — 접촉 판정이 궤도와 다른 척도(3D)를 썼다

버그 1을 고친 뒤에도 밀기가 여전히 0회였다. 원인은 `FixedUpdate`의 접촉 간격(`gap`)
계산이 **3D 거리**(`Vector3.magnitude`)를 쓰고 있었던 것 — 궤도는 XZ 평면 반지름 0.64m로
정확히 맞춰 놨는데, 캡슐 중심과 공 중심의 수직차(≈0.67m)가 3D 거리에 그대로 섞여
`√(0.64²+0.67²)≈0.93m`로 부풀었고, 이는 `_contactSlackM`(0.22m)를 항상 넘겨 **붙어 있어도
영원히 못 미는 상태**가 됐다(실측). 궤도와 같은 척도(XZ 평면)로 통일해 고쳤다.

**두 버그 다 CC 시절부터 있던 코드이고, 캡슐 `center=(0,0.85,0)`도 CC와 동일한 값이다 —
Phase 1~5의 Rigidbody 재작성이 만든 버그가 아니라, 이번에 테스트를 처음 실행해서 드러난
사전 존재 버그다.** (사용자 확인 후 Phase 6 범위에 포함해 같이 수정)

|---|---|---|

### 진단에서 나온 부수 발견 — 자동화 훅의 또 다른 함정

이번 조사 중 자체 진단 스크립트에서 `EditorApplication.update` 훅에 `input.enabled=false`를
빼먹어 Phase 4에서 이미 문서화한 "`Update` 실행 순서 경쟁"을 또 재현했다(빠르게 알아채고
바로잡았다). **`PenguinInputReader`를 직접 조작하는 진단은 항상 `enabled=false`로 시작할
것** — 실제 NUnit 테스트들이 이미 그렇게 하는 이유가 이것이다.

또한 정지된 `SnowBallCarrier`는 실측으로 확인하지 못했지만 슬립 상태에 들어가면 `AddForce`
가 무시될 수 있다는 정황이 있었다(진단용 인스턴스에서 `sleepThreshold`를 안 낮춰서 발생) —
기존 `같은_방향의_두_힘은...` 테스트가 이미 `sleepThreshold=0f`로 대응해 둔 이유로 보인다.
새 테스트를 짤 때 참고할 것.

### Test Runner 캐시 — 강제 리컴파일이 필요할 때가 있다

`run_tests`가 `test_names` 필터로 방금 전까지 잡히던 테스트를 갑자기 0개로 돌려줄 때가
있었다(스크립트를 편집한 직후). `refresh_unity`를 `mode=force`로 다시 돌리면 해결됐다 —
증분 컴파일 이후 테스트 디스커버리 캐시가 갱신 안 되는 경우가 있는 듯하다.

## 눈덩이 밀기 — 날개를 가장자리에 대기

좌클릭을 누르는 동안 `DEF-Wing.L` / `DEF-Wing.R` **두 본만** 회전해 날개끝을 눈덩이 표면에
댄다. 클립도, 블렌드 트리도, Animation Rigging 도 쓰지 않는다.

### 왜 2본 IK 를 쓰지 않는가

`Wing.001 → Wing.002` 에 `TwoBoneIKConstraint` 를 걸면 **날개 전체가 제 축을 중심으로
뒤틀린다.** 날개는 팔꿈치가 없는 납작한 판인데, 2본 IK 는 체인의 롤을 힌트(폴 벡터)로
결정하기 때문에 폴이 조금만 흔들려도 판이 통째로 돌아간다. 리지드한 판에 2본 IK 를 쓴 것
자체가 잘못된 도구 선택이었다.

### 구·구 교집합으로 접점을 구한다

날개를 리지드하게 두면 날개끝이 갈 수 있는 자리는 **뿌리 중심 반지름 `L` 의 구면**이다.
접점은 그 구면과 눈덩이 구면의 교집합, 즉 **원** 위에 있다. 그 원에서 바깥쪽으로 가장 먼 점을
고른 것이 "가장자리"다 — 해석으로 정하지 않고 기하로 결정된다.

교집합 존재 조건은 부등식 하나다:

```
|L − r| ≤ d ≤ L + r          d = 날개뿌리 → 눈덩이중심
```

**닿을 수 없으면 접점을 만들지 않고 아무것도 하지 않는다.** 날개는 애니메이션 자세 그대로
남는다. 해가 없는 목표를 솔버에 밀어 넣던 이전 구현의 실패가 구조적으로 불가능해진다.
위쪽 조건(`d > L + r`, 멀어서 못 닿음)뿐 아니라 **아래쪽 조건(`d < |L − r|`, 눈덩이가 날개끝
구면 안으로 들어감)도 실패**라는 점에 주의 — 몸을 숙여 뿌리를 당길 때 지나치면 여기 걸린다.
"최대한 숙이기"가 아니라 구간 안에 맞추는 문제다.

### 비틀림이 0 인 것은 튜닝이 아니라 보장이다

회전을 `Quaternion.FromToRotation(현재 날개끝 방향, 목표 방향)` 으로 구한다. 이건 두 벡터를
잇는 **최소 호 회전**이라 회전축이 날개 방향과 반드시 수직이고, 따라서 날개 축을 중심으로 한
비틀림 성분이 **정확히 0** 이다. 실측으로도 `축 · 날개방향 = 0.000000` 이다.

부수 효과로 **날개의 롤은 애니메이션이 준 값을 그대로 유지한다** — 우리가 건드리지 않으므로
걷기·뭉치기 클립의 날개 표정이 살아있다.

### 실측값 (2026-08-21)

| 항목 | 값 |
|---|---|
| `DEF-Wing` → `Wing.001` / `001`→`002` / `002`→끝 | 0.2552 / 0.2392 / 0.2971m |
| `L` (뿌리→날개끝) | **0.779m** (편 자세 최대 0.792 — rest 가 이미 거의 곧다) |
| 날개 본의 뼈 축 | 전부 로컬 **+Y** (`002→tip = (0, 1, 0)`) |
| 날개 뿌리 위치 (루트 기준) | `(∓0.302, 1.106, -0.030)` |
| 좌우 대칭 | X 부호만 반전. `L` 은 양쪽 동일 |

`_tipOffsetM`(0.2971)은 `DEF-Wing.002` 원점에서 날개 끝까지의 거리다. 끝점용 빈 오브젝트를
자식으로 붙이지 않고 본의 로컬 +Y 로 뻗어서 잡는다 — 리그에 오브젝트를 추가하지 않기 위해서다.

### 어떤 눈덩이를 잡는가 (2026-08-21 배선)

**직접 고르지 않는다.** `_snowball`(`PenguinSnowball`)의 `Held` — E 로 지금 붙잡고 있는
`SnowBallCarrier` — 를 매 프레임 그대로 읽는다. `Held == null`(안 붙잡음)이면 좌클릭을
누르고 있어도 `CanPush` 가 서지 않는다.

`SnowBallCarrier`는 지름 1 짜리 구 메시를 중심 `(0,0,0)`, 반지름 `0.5` 인 `SphereCollider`로
감싸고 스케일만 바꾼다(`SnowBallCarrier.ApplySize`). 그래서 **트랜스폼 위치와 `RadiusM` 이
곧 구의 중심·반지름이다** — 콜라이더를 따로 읽지 않는다.

**트리거는 좌클릭 홀드, 대상은 `SnowBallCarrier` — 두 입력이 분리돼 있다.** E 로 붙잡는 것과
좌클릭으로 팔을 대는 것은 별개 동작이다. 붙잡은 채 걷기만 해도(좌클릭 없이) 물리적으로는
밀리지만, 팔이 표면에 닿는 시각 표현은 좌클릭을 누르고 있을 때만 나온다.

⚠ **예전엔 `TargetBall`(`SphereCollider`)을 좌클릭 순간 씬에서 자동으로 찾았다.** 그 필드와
탐색 로직(`FindBallInFront`, `_grabRadiusM`, `_grabLayers`)은 배선하면서 전부 지웠다 — 임의의
콜라이더를 스스로 찾는 게 아니라 게임플레이가 실제로 붙잡은 것만 따라가야 하기 때문이다.
과거에 이 필드가 인스펙터에 고정돼 있어서 "작은 눈덩이가 안 잡힌다"는 증상이 난 적이 있는데,
지금은 애초에 그 필드가 없다.

### 한쪽만 닿으면 밀지 않는다

옆으로 돌아선 채 좌클릭하면 한쪽 날개만 닿는다. `CanPush`(= 양쪽 다 닿음)가 그 판정이고,
눈덩이를 소유한 시스템이 이 값이 `false` 인 동안 눈덩이를 움직이지 않아야 한다.

**날개 조준도 같은 조건으로 묶여 있다.** 한쪽만 닿으면 양쪽 다 조준하지 않고 애니메이션
자세로 남는다. 판정과 표현을 따로 두면 "밀리지도 않는데 한 팔만 공에 붙어 있는" 상태가
생긴다. 그래서 `TrySolve` 로 양쪽을 먼저 다 풀어보고, 둘 다 성공했을 때만 `ApplyAim` 한다.

### 허리 숙임 — `DEF-spine.004` 하나

`_leanByRadius`(반지름 → 각도) 곡선으로 `DEF-spine.004` 를 로컬 **+X** 로 굽힌다. 절대각으로
덮어쓰지 않고 애니메이션 회전에 델타를 곱한다 — bind pose 가 0 이 아니고, 클립의 호흡·보행
흔들림을 지우면 안 되기 때문이다.

`spine.004` 를 고른 이유는 계층이다 — 발(`DEF-toe.L/R`)이 `spine.003` 의 자식이라 `spine.004`
의 **형제**다. 따라서 아무리 굽혀도 **발은 움직이지 않고** 상체(가슴·목·머리·양 날개)만 기운다.
`spine.003` 을 굽히면 발까지 딸려 가고, 그러면 보행 궤적이 깨진다.

**순서가 중요하다.** 숙임을 날개 조준보다 **먼저** 적용한다. 숙이면 날개 뿌리가 딸려
움직이므로, 숙이기 전 위치로 접점을 풀면 실제 닿는 자리와 어긋난다. 그리고 `CanPush` 가
`false` 면 **숙임도 되돌린다** — 밀지도 못하는데 숙임만 남으면 허공에 대고 절하는 자세가 된다.

#### 각도는 최소값이 아니라 **구간**이다

실패 조건이 둘이다 — `d > L + r`(멀다)와 `d < |L − r|`(눈덩이가 날개끝 구면 **안으로** 들어감).
"필요한 최소 각도"만 보고 곡선을 맞추면 **과도하게 숙여서 아래쪽 조건에 걸린다.** 실제로
`r=0.10` 에 80° 를 주었더니 `d=0.460` 인데 하한이 `0.684` 라 못 닿았다 — 더 숙일수록 나빠지는
구간이었다.

#### 실측 (2026-08-21, `PackSnow` 삭제 후 `Idle` 기준)

| r | 정지거리 | 유효 lean | 곡선값 | yaw 허용 |
|---|---|---|---|---|
| 0.10 | — | (타고 넘어감) | — | — |
| 0.20 | 0.52 | 0°~62° | 36° | ±50° |
| 0.30 | 0.70 | 0°~72° | 33° | ±61° |
| 0.40 | 0.80 | 0°~90° | 32° | ±77° |
| 0.50 | 0.90 | 0°~90° | 29° | ±85° |
| 0.70 | 1.14 | 0°~90° | 27° | ±85° |
| 1.00 | 1.44 | 0°~90° | 24° | ±84° |

**`PackSnow` 를 걷어내면서 구간이 통째로 넓어졌다.** 그 클립이 `spine.003` 을 26° 숙여
날개 뿌리를 0.19m 높이 올려두고 있었기 때문이다(`y` 1.106 → 0.913). 지금은 **모든 크기에서
lean 0° 도 닿으므로**, 이 곡선은 사실상 도달성이 아니라 **보기 좋으라고 고르는 값**이다.

보행 중에도 안정적이다 — `Walk` 주기 t=0/0.25/0.5/0.75 에서 유효 구간이 `r=0.30` 에
0°~69°~74°, 그 이상은 전부 0°~90° 로 거의 변하지 않는다.

⚠ **기준 클립이 바뀌면 이 표는 전부 무효다.** 같은 질문에 세 번 다른 답을 냈는데 원인이
매번 이것이었다(벤더 `Idle2` 기준 → `PackSnow` 기준 → 현행 `Idle` 기준). **재생 중인 클립을
기준으로, 실제로 걸어붙인 상태에서 재라.**

#### 정지거리를 `0.4 + r` 로 가정하지 말 것

**낮은 눈덩이는 `CharacterController` 캡슐의 아래쪽 구면에 닿아 `0.4 + r` 보다 가까이 붙고**
(`r=0.20` 에서 0.52), 큰 눈덩이는 `skinWidth` 만큼 더 멀리 선다(`r=1.00` 에서 1.44).
가정으로 넣으면 유효 구간이 통째로 어긋난다. **공마다 `cc.Move` 로 걸어붙여 정지 위치를 재라.**

#### `r ≈ 0.10` 은 밀 수 없다 — `stepOffset` 때문

`CharacterController.stepOffset` 이 0.3 인데 반지름 0.10m 눈덩이는 높이가 0.20m 라 **계단으로
인식해 그냥 타고 넘어간다.** 붙어 설 수가 없으니 밀기 판정 이전의 문제이고, 타고 넘은 뒤에는
눈덩이가 **뒤에** 있으므로 자동 선택에도 안 잡힌다. 반지름 0.15m 아래가 전부 여기 해당한다.
`stepOffset` 을 줄이면 해결되지만 지형 이동 전반에 영향을 주므로 로코모션 쪽에서 판단할 일이다.
**지금 밀 수 있는 최소 반지름은 사실상 0.15~0.20m 다.**

### 밀면서 걸으면 다리가 뒤뚱거린다

밀기는 Animator 를 전혀 쓰지 않는다 — `PenguinSnowballPush` 가 `LateUpdate` 에서 본 세 개를
직접 돌릴 뿐이다. 그래서 Base Layer 의 `Idle ↔ Walk` 가 `Speed` 를 따라 평소대로 돌아가고,
하반신은 손댈 필요 없이 그대로 따라온다.

이게 성립하는 이유는 밀기가 건드리는 본이 `spine.004` 와 양 `Wing` **셋뿐**이고, 그 셋 모두
다리와 무관하기 때문이다. 상체 마스크 레이어도, 별도 클립도 필요 없다.

검증: `r=0.50` 을 밀며 `Walk` 재생 중 `DEF-toe.L/R` 의 월드 좌표가 프레임마다 바뀌고
(`toeL.y` 0.102 → 0.068), 그 동안 `CanPush=True` 와 날개끝 표면오차 `0.0000` 이 유지된다.

## 폐기한 `PackSnow` 에서 남길 것 — 축 실측값

`Penguin_PackSnow.anim`(눈을 **뭉치는** 0.7초 루프)은 **2026-08-21 에 삭제했다.** 밀기와 같은
좌클릭에 물려 있었지만 둘은 다른 동작이고, 무엇보다 그 클립의 핵심이던 "좌우 팔 교대 스트로크"가
`PenguinSnowballPush` 의 날개 고정에 완전히 덮여 사라진 상태였다. 남는 것은 `spine.003` 숙임과
어깨 자세뿐이었고, 그걸 위해 상체 마스크 레이어를 세울 값어치가 없었다.

**삭제로 얻은 것: 하반신 애니메이션.** 밀기가 Base Layer 를 점유하지 않게 되면서
`Idle ↔ Walk` 가 그대로 돌아간다 — 밀면서 걸으면 다리가 평소처럼 뒤뚱거린다. PackSnow 는
본 7 개(상체)만 애니메이션했기 때문에, 그것이 Base Layer 의 단일 상태로 들어가 있는 동안
**다리를 애니메이션하는 클립이 하나도 없었던** 것이 다리가 굳던 원인이었다.

아래 축 표는 그 작업에서 나온 실측값이고 **여전히 유효하다.** 이 리그에 새 동작을 만들 때
반드시 먼저 볼 것 — 당시 세 번 연속 실패한 원인이 전부 **축과 rest pose 를 재지 않고 눈대중으로
값을 넣은 것**이었다.

### 축 실측값 — 추측하지 말 것

본을 ±로 돌려 부리·날개끝의 월드 좌표가 어디로 가는지 재면 한 번에 확정된다. 캐릭터 정면은 **+Z**.

| 본 · 축 | 효과 | 좌우 미러 |
|---|---|---|
| `spine.003` 로컬 **+X** | 앞으로 숙임 (부리 z 0.172 → 0.552). −X 면 뒤로 눕는다. **발이 이 본의 자식이라 밀기에서는 쓰지 않는다** | — |
| `spine.004` 로컬 **+X** | 앞으로 숙임. 발은 안 따라온다 — 밀기의 lean 은 이 축이다 | — |
| 어깨 로컬 **Y** | **앞으로 뻗기** — z 와 y 가 함께 증가 | **부호 반대** |
| 어깨 로컬 **Z** | 배 앞으로 쓸어내리기(모으되 **내려간다**) | **부호 반대** |
| 어깨 로컬 **X** | 팔의 비틀림에 가깝다. 앞뒤 이동에는 거의 기여하지 않는다 | **같은 부호** |
| `Wing.*` 로컬 **Z** | 팔꿈치 컬 — 안쪽으로 감고 끝을 **올린다** | **부호 반대** |

오른쪽 미러는 **X 만 같은 부호, Y·Z·wingZ 는 반전**이다(왼쪽 포즈의 좌우 대칭점과 오차 0.0007
로 일치 확인). 이 비대칭이 함정이라 반드시 양쪽을 따로 재야 한다.

### rest pose 는 0 이 아니다 — 오일러 절대값을 쓰지 말 것

| 본 | rest 로컬 오일러 |
|---|---|
| `DEF-spine.003` | **(79.1, 180, 180)** |
| `DEF-spine.004` | (351.7, 0, 360) |
| `DEF-spine.005` | (333.3, 0, 360) |
| `DEF-shoulder.L` | (19.4, **325.6**, **74.9**) |
| `DEF-shoulder.R` | (19.4, **34.4**, **285.1**) |

`spine.003.x` 를 79.1 → −30 으로 덮어썼다가 **109° 뒤로 젖혀져 드러누운** 사고가 있었다.
게다가 `clip.SetCurve(..., "localEulerAnglesRaw.x", ...)` 는 `.y`/`.z` 커브도 **0 으로** 같이
만들어버려서 어깨 방향까지 무너뜨린다. 오일러 커브는 `351.7 → 0` 같은 랩어라운드 문제도 있다.

**쿼터니언에 델타를 곱해라** — 클립 저작이면 `baseQ * AngleAxis(각도, 축)` 로 `localRotation`
4 커브를 쓰고 마지막에 `EnsureQuaternionContinuity()`. 런타임이면
`PenguinSnowballPush.ApplyLean` 이 같은 방식이다.

## 이 세션에서 한 것

**1차 세션(Bash 텍스트 편집)**: 순수 C# 스크립트 4개(`Scripts/`)만 — 루트 `AGENTS.md`가
`.prefab`/`.controller`/`.anim`/`.unity`(전부 YAML) 손편집을 금지하기 때문.

**2차 세션(Unity MCP)**: 나머지 전부를 Unity 에디터를 통해 만들었다 — Unity MCP 실행 코드로
직접 `AddComponent`/`SerializedObject`를 호출했다(`manage_components`의 `add` 액션이 이
브릿지에서 `NotImplementedException`을 던져 우회함).

- `Animations/AC_Penguin.controller` — **4파라미터**(`Speed` float·`IsGrounded` bool·
  `IsSliding` bool·`Jump` trigger). **블렌드트리가 아니라 단순 상태 전이다** — 계획에는
  `Idle2 ↔ Walk` 블렌드트리로 적었지만, `manage_animation` 툴의 API 표면이 상태·전이 생성
  위주라 더 신뢰성 있게 만들 수 있는 쪽으로 갔다. `Speed > 0.1`/`< 0.1` 조건의 `Idle ↔ Walk`
  전이라 크로스페이드(0.25초)로 섞이는 건 동일하다. `AnyState → Jump`(조건 `Jump`),
  `Jump → Idle`(exit time 0.9 + `IsGrounded`), `AnyState → Slide`(조건 `IsSliding`),
  `Slide → Idle`(조건 `IsSliding` false).
  **눈덩이 밀기 상태는 없다** — 2026-08-21 에 `PackSnow` 상태와 `IsPackingSnow` 파라미터를
  걷어냈다. 밀기는 Animator 를 거치지 않고 `PenguinSnowballPush` 가 본을 직접 돌린다.
- `Scripts/PenguinSnowballPush.cs` — 날개 표현 전부. `PenguinSnowball.Held` 를 읽어(직접
  고르지 않음) `DEF-spine.004` 를 굽히고 양 `DEF-Wing` 을 눈덩이 표면으로 겨눈다. 위
  "눈덩이 밀기" 절 참조. **이 폴더 소속이 아닌 `PenguinSnowball.cs`(`E`/`Q`, 붙기·뭉치기·
  터뜨리기 실제 게임플레이)에 의존한다** — 그쪽이 없으면 `_snowball` 이 비어 컴파일은 되지만
  아무것도 안 잡는다.
- `Prefabs/PF_Penguin.prefab` — 계층: `PF_Penguin`(`CharacterController`·
  `PenguinInputReader`·`PenguinLocomotion`·`PenguinSnowball`) → `Mesh`(벤더 프리팹 인스턴스,
  `Animator`+`PenguinAnimatorDriver`+`PenguinSnowballPush`) → `CameraRig`(`PenguinCameraOrbit`)
  → `Camera`(`Camera`+`AudioListener`). **`Animator`는 루트가 아니라 `Mesh`에 있다** — 저작 클립·벤더 클립의
  본 경로(`Armature/DEF-spine.003/...`)가 `Animator`가 붙은 오브젝트 기준 상대경로라, 벤더
  프리팹의 실제 루트(이름을 `Mesh`로 바꾼 그 오브젝트)와 일치해야 한다. 루트에 두면 `Mesh/
  Armature/...`가 되어 클립이 아무것도 못 찾는다. `PenguinAnimatorDriver`도 같이 `Mesh`에
  있다(`[RequireComponent(typeof(Animator))]`라 같은 오브젝트여야 한다) — `_locomotion`은
  루트의 `PenguinLocomotion`을 가리키도록 배선했다, 계층이 달라도 컴포넌트 참조는 상관없다.
  **실측**: 벤더 메시 바운드가 `size=(1.07, 1.71, 1.40)`, `min.y=-0.19`(피벗이 발밑이 아니라
  허리 근처) — 그래서 `Mesh`를 올려 발이 `y=0`에 오게 했고,
  `CharacterController`는 `height=1.7`·`radius=0.4`·`center=(0, 0.85, 0)`, 카메라는
  `CameraRig` 로컬 `(0, 1.3, 0)`(머리 높이)에서 뒤로 `3.5m`.

  ⚠ **위 `skinWidth` 보정 서술은 2026-08-21 기준으로 무효다 — `Mesh` 로컬 위치는 `(0,0,0)` 이다.**
  `/main` 쪽 작업에서 바뀐 것으로 보인다. 원래 서술은 "`skinWidth` 는 반지름의 10%(`0.04`)로
  낮췄고 메시를 `0.19 − 0.04 = 0.15` 로 내려 상쇄했다" 였다. **값을 만질 때 실측부터 하고,

`CharacterController.isGrounded = true`(Ground 위에 정상 접지), `Animator`가 `Idle` 상태로

## 왜 Cinemachine을 안 쓰고 직접 돈다

`PenguinCameraOrbit`은 자기 트랜스폼 회전만 계산하는 평범한 스크립트다. Cinemachine

Cinemachine으로 바꾸더라도 "피벗 회전, 캐릭터는 안 건드림"이라는 자리는 그대로 필요하므로
지금 스크립트가 버려지는 작업은 아니다. 카메라 자체(실제 `Camera`)는 이 피벗의 자식으로 두고
로컬 오프셋(거리)만 인스펙터에서 잡으면 된다.

## `Swim` 클립을 슬라이딩 자세로 쓴다

무료팩 5클립(`Idle2`·`Walk`·`Jump`·`Swim`·`Dead`) 전부 in-place(`m_HasGenericRootTransform: 0`,

`Idle2`/`Walk`/`Jump`/`Dead`는 전부 ~79°(직립)인데 `Swim`만 **-9°**(거의 수평)다 — 몸이

슬라이딩용 별도 클립을 만들지 않고 `Swim`을 재사용한다.

## 슬라이딩 — 발차기 추진과 마찰 (2026-08-21, ⚠ CC 시절 모델 — 코드는 삭제됨)

**이 절은 삭제된 CC 모델의 역사 기록이다.** `CharacterController` 기반 스칼라 장부
(`_slideSpeed` 적분)는 2026-08-22 Rigidbody 재작성으로 걷어냈다. 현행 동작과 값은 위
"Phase 3 — 슬라이딩" 절이 권위다. 아래 물리 유도값은 새 비등방 마찰 모델을 만들 때 사용한
검산 근거라 남겨 둔다.

**조작은 차량식이다.** A/D 가 방향이 아니라 **핸들**, W 가 **발차기**, S 가 **제동**이다.
걷기와 달리 카메라 기준이 아니므로 카메라와 진행 방향이 따로 놀 수 있다.
진입 시 속도는 항상 **0** 에서 시작한다 — 걷기 속도를 승계하지 않는다.

`_snowCpuStage`와 `_snowStage`는 선택 참조다. 둘 다 비우면 눈 덮임이 0(맨바닥)이므로 눈 없는
씬에서도 걷기/점프는 그대로 동작한다. 현행 SinglePlay는
`../Snow/HeightCpu/SnowCpuStage.HeightAtM`을 연결하고, 구형 눈 테스트 씬만
`../Snow/Scripts/SnowStage.DepthCmAtWorld`를 쓴다. 둘 다 있으면 CPU 눈을 우선한다.

### 최고 속도는 어디에도 적혀 있지 않다

속도를 계산하지 않고 **적분한다.** `AddSlideImpulse` 로 킥 한 번에 한 계단씩 오르고 매 프레임
마찰로 깎인다. 감속은 물리 두 항뿐이다 — 미끄럼 마찰 `μg`(속도 무관)와 공기 저항 `½ρC_dA/m`
(`v²` 비례).

**그런데 그 둘로는 상한이 안 생긴다.** 눈은 너무 미끄럽고 이 속도대의 공기 저항은 너무 작아서
(9 m/s 에서 0.045 m/s², 눈 마찰의 1/22) 항력 균형만으로는 최고 속도가 수십 m/s 로 발산한다.
실제 펭귄이 무한히 빨라지지 않는 이유는 공기가 아니라 **발이 지면보다 빨라지면 더 못 밀기
때문**이다:

```
임펄스(v) = 임펄스₀ × max(0, 1 − v / _kickBiteSpeed)
```

그래서 최고 속도는 `_kickBiteSpeed` — 애니메이션과 이어진 물리량 — 이 정한다. 항력 계수를
돌려 속도를 맞추던 이전 방식은 **실제 공기 저항의 45 배**를 넣고 있었다.

**맨바닥에서 못 나가는 것은 계수가 아니라 부등식이다.** 마찰(10)이 추진력(4.5)보다 커서 애초에
가속이 안 된다. 임펄스에 `_bareKickFactor` 를 곱해 결과를 맞추던 이전 구현은 물리가 아니라
눈속임이었고 삭제했다.

### 중력은 하나다 — 마찰을 g 에서 유도한다

`_gravity` 는 −20 으로 실제 9.81 이 아니다. 그런데 마찰만 실제 중력 기준(`μ×9.81`)으로 넣어
두었더니 **경사만 2배 세게 당기는 반쪽 모델**이 됐다. g 를 낮추는 대신 마찰을 같은 g 로 다시
유도했다 — μ 는 실제 값을 쓰되 곱하는 g 를 20 으로 맞춘 것이다. **"중력이 2배인 세계"** 로
두면 내적 일관성이 생기고 점프 손맛과 비탈의 박력을 잃지 않는다. g 만 9.81 로 낮췄다면 25°
내리막 끝 속도가 22.6 → 15.0 m/s 로 떨어져 미끄러지는 맛이 사라진다.

| 값 | 유도 |
|---|---|
| `_snowFriction` 1.0 | μ≈0.05(눈 위 매끄러운 물체) × 20 |
| `_bareFriction` 10.0 | μ≈0.5(바위·콘크리트) × 20 |
| `_airDrag` 0.00056 | 30kg·0.11m²·C_d 0.25·ρ1.225. **g 와 무관** |
| `_kickBiteSpeed` 11.7 | 마찰이 커진 만큼 올려 평지 최고속 유지 |

### 이 값들이 만드는 규칙 — 전부 유도된 것이지 박아 넣은 것이 아니다

| | |
|---|---|
| 저절로 미끄러지기 시작하는 각도 | **2.9°** = `atan(μ)` |
| 발질로 오를 수 있는 한계 | **10°** (오르막 감속 4.46 < 추진력 4.5) |
| 15° 이상 | **뒤로 밀린다** — 가속 붙여 관성으로 넘어야 한다 |
| 평지 최고속 | **9.2 m/s** (걷기 3.5 의 2.6배) |
| 25° 내리막 끝 | **22.6 m/s** — 상한을 뚫는다 |

"언덕은 달려서 넘는다"는 게임플레이가 추진력과 마찰의 부등식에서 공짜로 나온 것이다.

**순항의 톱니는 임펄스로 못 바꾼다.** 최고속에서는 bite 가 임펄스를 마찰과 균형 잡는 만큼만
남기므로, 순항 리듬은 언제나 `마찰 × 반주기` 다(실측 0.51). 톱니를 키우려면 마찰이나 케이던스를
만져야 한다. 임펄스를 키우면 **가속만 빨라지고 최고속은 거의 안 변한다** — 상한을
`_kickBiteSpeed` 가 쥐고 있기 때문이다.

### 경사 — 중력이 직접 가속한다

지면 법선으로 중력의 접선 성분을 구해 진행 방향에 투영한다. 마찰에는 `cos θ` 를 곱해 급한
비탈일수록 덜 잡히게 한다. 오르막에서 발질을 멈추면 **속도가 음수로 내려가 뒤로 미끄러진다**
— 0 에서 멈추지 않는다.

#### ⚠ `isGrounded` 로 경사 판정을 게이팅하지 마라

**`CharacterController.isGrounded` 는 비탈에서 심하게 떨린다 — 실측 660 프레임에 199 회
뒤집혔다.** `SampleGround` 가 `!IsGrounded` 일 때 법선을 `up` 으로 되돌리고 있었더니 프레임의
**80% 가 경사를 평지로 읽었고**(평지 371 / 경사 90), 경사 가속이 `5.00 ↔ 0` 으로 토글했다.
그 속도 떨림을 카메라가 `CurrentSpeed01` 로 읽어 **FOV 가 2.4°, 거리가 40cm 씩 맥동해 화면이
진동했다.** 속도 스무딩(0.4초)이 있었는데도 남은 이유는 이것이 고주파 노이즈가 아니라 수십
프레임 단위로 지속되는 **저주파 토글**이었기 때문이다.

레이캐스트 자체가 "지면이 발밑 사거리 안에 있는가" 를 이미 답한다. 게이트를 걷어내니 평지
오독 371 → **0**, 경사 가속 **5.00~5.00 으로 완전히 일정**, FOV 진동 2.4° → **0.011°** 가 됐다.
`_groundProbeDistance` 는 캡슐 **바닥** 기준이므로 길게 잡으면 점프 중에도 경사가 걸린다(0.5m).

`isGrounded` 자체는 고치지 않았다 — 애니메이터 파라미터와 점프 판정도 쓰는 값이라 별건이다.
**다른 곳에서 이 플래그로 무언가를 게이팅할 때 위 실측을 기억할 것.**

### 벽에 부딪히면 속도 장부도 깎아야 한다

`BlockNormal` 과 `CharacterController` 는 **이번 프레임의 이동**만 막을 뿐 `_slideSpeed` 를
건드리지 않는다. 그래서 벽에 붙어 있다가 떨어지면 **저장된 속도로 튀어나갔다.**
`PenguinImpactRelay` 가 `ApplyImpactBrake` 로 이것을 닫는다.

## 발차기 — 위상이 상태다 (`PenguinSlideKick`)

W 를 누르면 양 발(`DEF-toe.L/R`)이 교대로 노를 젓는다. **클립도 Animation Event 도 쓰지
않는다** — `Phase` float 하나가 힘(임펄스 시점)과 그림(발 각도)을 동시에 결정하므로 "발이
박히는 순간 밀린다"가 튜닝이 아니라 정의다. 위상은 그대로 `[Networked]` 가 되지만 Animation
Event 는 Animator 재생에 묶여 서버에서 신뢰할 수 없고, 루트 `AGENTS.md` 의 "원인을 복제하고
결과를 복제하지 마라"에도 어긋난다. 이 리그에 새 클립을 저작하는 작업은 이 폴더에서 세 번
실패했고, 네 번째에 성공한 방법이 `LateUpdate` 에서 본을 직접 돌리는 것이었다.

스트로크는 **rest 와 리치(찍기 150° + 뻗기 40°) 사이의 왕복**이다. 빠르게 뻗고 느리게
돌아오며, **돌아오는 길이 곧 바닥을 미는 구간**이다.

### ⚠ 발을 뒤로 보내는 회전은 존재하지 않는다

두 축을 전수 격자 탐색한 결과 발끝이 rest 보다 뒤로 갈 수 있는 최대치가 **0.022 m** 다 —
`Swim` 의 rest 자세가 이미 뒤쪽 극점이라 어느 축 어느 부호로 돌려도 앞으로만 간다. "뒤로 쓸기"
를 별도 축으로 만들려던 시도(두 축을 90° 위상차로 겹친 타원)는 뒤쓸기가 0.021 밖에 안 나왔다.
**뒤로 가는 유일한 방법은 앞으로 뻗었다가 돌아오는 것**이고, 그렇게 하니 0.150 이 나왔다(7배).

실측 회수 경로: 깊이 0.13~0.14 를 **유지한 채** 뒤로 0.10 쓸고 나서 올라온다.

### ⚠ `Swim` 자세에서 축 부호가 rest 와 반대다

| 축 | rest(직립) | `Swim`(슬라이딩) |
|---|---|---|
| `+X 90°` | 위로 0.119 | **아래로 0.139** |
| `−X 90°` | 아래로 0.082 | 위로 0.044 |

몸이 눕는 동안 다리 체인이 통째로 돌아가서 부호가 뒤집힌다. 슬라이딩용 축은 **`+X`** 이고
좌우 **같은 부호**라 미러 분기가 없다. 본 축은 로컬 **+Y**(날개와 같은 리그 규약).

**고립된 축 실측표는 두 축을 겹치면 성립하지 않는다.** 단독 실측 부호를 믿었다가 궤적이 통째로
뒤집혔다 — 합성한 궤적을 다시 재야 한다.

### 발은 지면에 닿지 않는다 — 스타일라이즈다

`+X` 로 아무리 돌려도 **120° 에서 `y=0.171` 이 최저**고 그 아래로는 다시 올라간다. 지면은 0 이다.
이 펭귄은 **허벅지·정강이 뼈가 없어서**(다리 체인이 `DEF-spine.003 → DEF-toe → DEF-toe.001`
뿐이고 발 길이가 10cm) 골반에서 지면까지 뻗을 방법이 뼈 회전에 없다.

게다가 `Swim` 자세는 렌더러 **`min.y = −0.278`** 로 몸이 이미 지면 아래로 박혀 있다. 접지는
슬라이딩 몸 자세 자체를 손대는 별건이라, 지금은 **공중에서 젓는 그림**으로 두고 추진력만
성립시킨다.

### 위상 0 은 "쉬는 중"이다

`StrokeProgress(0) = 0 < 1` 이라 스트로크로 읽힌다. `IsKicking` 을 함께 보는 가드가 없으면
**W 를 누른 적도 없이 걷는 내내 발을 젓는다.**

## 연출 — `BodyPivot` 계층과 Feel (2026-08-21)

`Vehicle/` 의 속도감 레이어를 이식했다. 구조 규약도 같이 따랐다 — **채널 하나에 주인 하나.**

```
PF_Penguin        CharacterController · Locomotion · InputReader · Snowball · ImpactRelay
└─ BodyPivot      PenguinBodyMotion 이 회전(기울기) + 위치(충돌 킥)
   └─ Mesh        Animator · AnimatorDriver · SnowballPush · SlideKick · MMF_Player(스케일)
└─ CameraRig      PenguinCameraOrbit
   └─ Camera      Camera · AudioListener · UniversalAdditionalCameraData
```

`Mesh` 위에 부모를 끼우는 것은 클립 본 경로에 영향이 없다 — 경로는 `Animator` 가 붙은
오브젝트 기준이고 그것은 `Mesh` 그대로다(`DEF-toe.L` 월드 좌표 오차 **0.00000000 m** 로 확인).

**우리 코드가 `Mesh` 스케일을 만지면 안 된다.** `MMF_SquashAndStretch` 가 `_initialScale` 을
캡처해 거기서 상대적으로 움직이므로, 덮으면 복귀 지점이 어긋나 누적된다.

### 연출의 단일 소스는 곡선이다 — `CurrentSpeed01`

평지 최고속은 9.2 인데 25° 내리막은 22.6 m/s 다. **9.2 로 나누면 가장 빠른 순간들이 전부 1 로
뭉개져** 내리막이 평지와 똑같이 보이고, 22 로 나누면 평지가 늘 0.4 에 머물러 밋밋하다. 곡선으로
평지 최고속을 **0.75** 에 두어 일상 주행에 충분한 연출을 주면서 내리막용 여유를 남겼다.

### ⚠ `VehicleCamera` 를 그대로 붙일 수 없다

저쪽은 **마우스를 읽지 않고** 카메라의 월드 위치를 직접 계산하며 yaw 를 차량 heading 에
고정한다. `PenguinCameraOrbit` 은 마우스 궤도 피벗이라 그걸 붙이면 시점이 사라진다. 그래서
거리·높이·FOV·전방 여백만 떼어 **자식 카메라의 로컬 오프셋과 FOV** 에 얹었다. 피벗의 회전은
건드리지 않는다.

**전방 여백을 카메라 *위치* 에 더하면 안 된다.** 로컬 +Z 로 미는 것이라 뒤로 뺀 거리를 그대로
상쇄한다 — 거리 5.75 를 계산해 놓고 여백 2.25 가 깎아 **3.50(= rest 그대로)** 이 나왔다.
여백은 "보는 지점"이므로 카메라 **로컬 회전**으로 준다.

### ⚠ 선회 FOV 킥을 선회각속도로 몰면 저속 전용이 된다

설계상 빠를수록 선회 곡선이 각속도를 깎는다 — 실측 **9.3 m/s 에서 45°/s, 2 m/s 에서 286°/s.**
속도감을 주려는 목적과 정반대다. 처음 문턱을 60°/s 로 잡았더니 고속에서 **아예 안 떴다**
(`Vehicle` 이 "모델이 안 내는 값까지 범위를 잡지 마라"로 남긴 함정의 반대편이다).
**원심 가속도(`v × ω`)** 로 몬다 — 기울기가 쓰는 값과 같으므로 소스도 하나다.

### 기울기는 입력이 아니라 결과에서 나온다

```
lean = atan(v · ω / g)
```

고속에서 선회 곡선이 각속도를 깎으면 기울기도 같이 줄어, "핸들은 꺾었는데 안 도는" 순간에
몸만 크게 기우는 일이 없다. `g` 는 실제 9.81 이 아니라 **이 컴포넌트의 중력(20)** 이다 — 같은
세계의 중력을 써야 한다. 저속 급선회는 물리적으로 더 크게 기우는 것이 맞지만 그림이 과해
`_maxLeanDeg`(20°)로 자른다. 실측 19.8° vs 이론 20.1°.

**가속 피치는 넣지 않았다.** 차량은 스로틀이 연속이라 피치가 읽히지만, 펭귄의 추진은 킥
임펄스라 같은 사건에 스쿼시와 **두 번 반응**하게 된다. `Vehicle` 이 클램프로 막았던 문제를
아예 만들지 않는 쪽을 택했다.

### ⚠ `MMF_SquashAndStretch` 의 `Axis` 기본값은 `YtoXZ` 다

`Vehicle/AGENTS.md` 의 *"`Axis` 가 `ZtoXY` 로 고정이다"* 는 그쪽이 **설정해 둔 값**이지 기본값이
아니다. 그대로 두었더니 **Y(위아래)가 늘고 X/Z 가 줄고** 있었다 — 실측 `(0.9765, 1.0487,
0.9765)`. 정면 축으로 하려면 `ZtoXY` 로 바꿔야 한다.

**세기를 `PlayFeedbacks(intensity)` 로 넘기면 안 된다.** 그 인자는 `RemapCurveOne` 에
**곱해지므로** 배율이 1 근처인 값에서는 세기를 낮출수록 거꾸로 커진다. **배율 자체를 보간해야
한다.** 실효 피크 = `1 + 1.5 × (RemapCurveOne − 1)`.

세기는 킥이 **실제로 더한 임펄스**(bite 로 깎인 뒤)에 비례시킨다 — 그래서 고속에서 발이
헛돌면 그림도 저절로 안 뜬다. 실측: 킥#1 임펄스 2.250 → Remap 1.0400, 킥#2 1.894 → 1.0337
(0.842 에 정확히 비례), **Z 최대 1.0600, X 최소 0.9713.** 순항에서는 1.014 배까지 약해진다.

**킥 스트레치와 충돌 스쿼시는 같은 `MMF_Player` 를 쓴다.** 한 트랜스폼의 스케일에 `MMF_Player`
를 둘 얹으면 각자 `_initialScale` 을 캡처해 매 프레임 서로 덮어쓴다. 에셋의 `RemapCurveOne`
기본값은 **1(변형 없음)** 로 둔다 — 코드가 매번 덮어쓰므로 값을 구워두면 항상 최대 세기가 된다.

### 충돌 감지가 `Vehicle` 과 다르다

`VehicleImpactRelay` 는 `OnCollisionEnter` 와 `collision.relativeVelocity` 를 쓰지만
`CharacterController` 는 **둘 다 주지 않는다.** 대신 **의도 속도와 `CharacterController.velocity`
의 차이**를 본다. 이 한 가지가 벽·눈덩이·급한 오르막을 전부 잡는다.

실측: 9 m/s 로 벽에 정면 충돌 → 세기 0.96, 속도 8.73 → 2.88. 오검출은 평지 직진 2470 프레임에서
**0 회**(최대 shortfall 1.91, 문턱 2.5). ⚠ **여유가 0.6 뿐이다** — 프레임률이 떨어지거나
경사에서 헛발동하면 `_minShortfall` 을 3.0~3.5 로 올린다.

### ⚠ Feel 검증을 `execute_code` 로 하면 안 된다

Roslyn 컴파일이 메인 스레드를 멈춰 **다음 프레임 `deltaTime` 이 튀고** 0.2초 애니메이션이 한
프레임에 통째로 소비된다. 기본 커브는 양 끝이 배율 1 이라 **아무 변화 없이 끝나고 콘솔에도
아무것도 안 남는다.** `EditorApplication.update` 콜백에서 첫 30 프레임을 버리고 샘플링할 것.

또 이 에디터는 **초당 450 프레임을 넘으므로 프레임 수로 시간을 가늠하면 안 된다** — 300 프레임이
0.66초라 벽에 닿기도 전에 샘플러가 끝난 적이 있다.

### 안 가져온 것

- **오디오** — `Vehicle` 도 안 옮겼다(음원이 기각 상태).
- **충돌 발광(`MMF_Flicker`)** — 펭귄 머티리얼이 벤더 애셋(`Assets/Hosh/…`)이라 루트
  `AGENTS.md` 가 수정을 금지한다. 사본을 떠야 하는 별건이고, 이 씬에 블룸도 없다.
- **차량식 점프 킥 연출** — 슬라이드 점프 물리는 들어왔지만 `Vehicle`처럼 별도 차체 위치 킥을
  한 번 더 얹지는 않았다. 펭귄은 `Swim` 슬라이드 자세와 Rigidbody 포물선만 쓴다.

## 유료 애니메이션 팩으로 전환할 때

무료팩과 **같은 리그인지가 유일한 관건**이다(위 Rigify 본 이름들이 그대로면 컨트롤러·저작
클립·마스크가 전부 살아남는다). 판매자에게 리그 동일 여부와 Root Motion/in-place 여부를
