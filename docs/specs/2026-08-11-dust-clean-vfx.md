# 먼지 청소 VFX — 설계

> **작성일** 2026-08-11 · **브랜치** `/main/dust-clean-vfx` · **피처** `Assets/Game/InGame/Dust/`

닦는 동안 **"지금 빨아들이고 있다"가 보이게** 만든다. 셰이더 브랜치가 청소 *전후*의 대비를
만들었다면, 이번은 청소 *중*을 만든다.

선행: [2026-08-11-dust-surface-shader.md](2026-08-11-dust-surface-shader.md) — 마스크 규약과
지우기 전용 결정이 거기 있다. 그 문서 §9가 이번 작업을 "청소 VFX — 먼지 퍼프, 흡입 궤적"으로
지목해뒀다.

---

## 0. 전제 — 도구가 무엇인가

기존 문서에 없던 정보라 여기 먼저 고정한다. **먼지를 상대하는 도구는 스팀청소기 계열이다.**

- 대걸레처럼 **표면에 붙여서** 밀고 다닌다. 들고 다니다가 바닥에 대고, 켜고, 움직이면 닦인다
- 지워지는 자국은 **방향이 있는 직사각형** — 그림 앱의 사각 브러시에 가깝다
- 메인 기능은 **빨아들이는 것**이다. 밀어내는 게 아니라 흡입이다

이 셋이 이번 VFX의 형태를 전부 결정한다. 퍼프는 사방으로 흩어지는 게 아니라 **패드 안쪽으로
빨려들고**, 밀리는 먼지는 **패드 앞 모서리**에 생기며, 반짝임은 **패드가 지나간 띠**를 따라 남는다.

도구 자체(조작·모델·온오프)는 `InGame/Vacuum/` 소관이고 이번 브랜치에서 만들지 않는다.
`DustMousePainter`가 마우스 히트 지점 + 표면 노멀 + 이동 방향으로 임시 패드를 흉내낸다.

## 2. 붓을 직사각형으로 바꾼다

지금 붓은 월드 공간 **구**다 — `DustPaint.shader:110`의 `distance(positionWS, _BrushPosition)`.

**바꾸는 방법.** 월드 좌표를 패드 로컬로 옮기고 2D 박스 SDF 로 판정한다. 패드 평면은 로컬 XZ,
두께는 로컬 Y.

```hlsl
float3 local = mul(_BrushWorldToPad, float4(positionWS, 1.0)).xyz;
float2 d     = abs(local.xz) - _BrushHalfExtents;
float outside = length(max(d, 0.0)) + min(max(d.x, d.y), 0.0);   // <0 이면 패드 안
outside += (edgeNoise - 0.5) * _BrushNoiseAmount * _BrushFeather;
float falloff = 1.0 - smoothstep(-_BrushFeather, 0.0, outside);
```

**두께 판정이 새로 필요하다.** 구는 거리 하나로 위아래가 자연히 잘렸지만 사각 프리즘은 무한히
길다. `abs(local.y) > _BrushThickness` 를 잘라내지 않으면 **바닥을 닦을 때 아래층 천장까지
지워진다.** 구에는 없던 실패 모드다.

노이즈는 그대로 월드 좌표에서 뽑는다 — `DustPaint.shader:103`의 이유(붓을 따라 무늬가 움직이면
얼룩이 바닥이 아니라 도구에 붙어 보인다)가 사각형에서도 똑같이 성립한다.

**시그니처.** `Paint(위치, 반지름, ...)` → `Paint(패드 포즈, 반쪽 크기, ...)`. 패드 포즈는 도구가
표면에 붙어 있을 때의 트랜스폼 그대로이므로, `Vacuum`이 오면 자기 트랜스폼을 넘기면 된다.

**왜 VFX 뒤로 못 미루나.** 세 VFX 중 둘이 브러시 모양에 직접 의존한다. 밀리는 먼지는 *패드의 앞
모서리*에서 나야 하고 퍼프도 원이 아니라 띠로 난다. 원형 붓으로 VFX 를 맞춰놓으면 사각형으로
바꾸는 순간 전부 다시 만들어야 한다.

## 3. 지운 양을 어디서 얻나

VFX 는 "이번 프레임에 **실제로** 얼마나, **어디가** 지워졌나"를 알아야 한다. 이미 깨끗한 바닥을
문질러도 먼지가 풀풀 나면 "다 닦았다"는 피드백이 사라진다.

### 진짜 문제는 월드→UV 를 누가 하느냐다

지금 그 변환을 **래스터라이저가 공짜로** 하고 있다. `DustPaint.shader:92`의 버텍스 셰이더가 UV 를
클립 좌표로 내보내 메시를 마스크 위에 펼쳐 그리고, 프래그먼트가 그 텍셀의 월드 좌표를 받는다.
CPU 는 이 매핑을 전혀 모른다 — 레이캐스트로 얻는 건 월드 좌표뿐이다.

| 후보 | 월드→UV 를 누가 | 기각 이유 |
|---|---|---|
| CPU 미러 (UV 그리드) | 메시를 CPU 에서 래스터화해 셀마다 월드 좌표를 굽는다 | **메시 Read/Write 필요**, 코드 60줄, 그리고 붓의 노이즈 모양을 재현 못 해 **매끈한 원 안에서만** 파티클이 뜬다 |
| 월드 XZ 그리드 | 안 함 | 처음부터 깨끗했던 자리를 모른다. `T_Dust_Mask_Path` 처럼 길이 그려진 마스크에서 없는 먼지가 난다. 그리고 이 프로젝트는 마스크 설계 때 월드 XZ 투영을 **이미 같은 이유로 기각**했다 (선행 스펙 §1) |
| GPU 에서 세서 스칼라로 Readback | 래스터라이저 | 1~3 프레임 지연. 그리고 스칼라 하나로는 *어디가* 지워졌는지 못 준다 |
| **패드 공간 RT (채택)** | 래스터라이저 | — |

### 채택 — 지운 양을 GPU 에 텍스처로 남긴다

붓질할 때 패스를 **하나 더** 그린다. 마스크에서 빼는 패스는 그대로 두고, 그 앞에 같은 메시를
**패드 공간**에 렌더한다.

```hlsl
// 버텍스: 클립 좌표 = 패드 로컬 XZ 를 반쪽 크기로 정규화
//         → 패드의 발자국이 RT 전체를 채운다
clipXY = mul(_BrushWorldToPad, float4(positionWS, 1.0)).xz / _BrushHalfExtents;

// 프래그먼트: 실제로 지워질 양 = 남아 있던 양과 붓의 양 중 작은 쪽
float prev   = SampleDirt(_DirtMask, uv);
float erased = min(prev, falloff * _BrushStrength * patch);
return float4(positionWS, erased);
```

RT 는 `RGBAFloat` 64×64, **매 프레임 클리어**한다. 그러면 이 텍스처는 정확히 *이번 프레임에
지워진 것*만 담는다. 그게 곧 퍼프의 발생원이다. 블렌드는 끄고 덮어쓴다 — 한 프레임에 스탬프가
겹치는 경우는 위치가 거의 같으므로 마지막 것이 이겨도 무해하다.

**패드 공간에 굽는 것이 UV 공간보다 나은 이유 두 가지.**

1. **낭비가 없다.** UV 공간에 구우면 넓은 바닥에서 패드가 차지하는 면적이 UV 의 1% 도 안 되고,
   VFX Graph 가 랜덤 UV 로 샘플하면 99% 가 빈 텍셀에 떨어져 죽는다. 패드 공간은 모든 텍셀이
   패드 안이다.
2. **RT 가 표면당이 아니라 도구당이 된다.** `Dust/AGENTS.md:19` 가 "마스크가 렌더러당 하나라
   확장이 안 된다"고 열어둔 문제에 한 장을 더 얹지 않는다. 도구 하나당 64×64 RGBAFloat = 64KB
   이고, 패드 아래 표면이 여럿이면 **모두 같은 RT 에 그려 넣는다.**

프레임당 순서:

```
1. 도구의 지운양 RT 클리어
2. 패드 아래의 각 DustPaintTarget → 패드 공간 패스로 지운양 RT 에 기록  (마스크는 읽기만)
3. 같은 대상들 → 기존 UV 공간 패스로 마스크에서 빼기
4. VFX 가 지운양 RT 를 읽는다
```

2 와 3 의 순서가 뒤바뀌면 안 된다. 2 는 *빼기 전* 마스크를 읽어야 "실제로 지워진 양"이 나온다.

### 얻는 것

| | |
|---|---|
| 지연 | **0** — 그린 그 프레임에 읽는다 |
| 메시 Read/Write | **불필요** |
| 8비트 정밀도 문제 | **무관** — 지운 양은 float RT 에 따로 쓴다 |
| 룩 | **퍼프가 붓의 노이즈 모양을 정확히 따라간다** |

마지막이 핵심이다. CPU 경로는 어떻게 해도 매끈한 사각형 안에서만 뿌릴 수 있는데, 붓은
`DustPaint.shader:113`에서 외곽선을 흔들고 안쪽도 얼룩덜룩하게 남긴다. GPU 경로는 **실제로
지워진 그 얼룩덜룩한 자리에** 정확히 먼지가 뜬다. 정확성이 아니라 룩의 문제고, CPU 로는 도달할
수 없는 지점이다.

### 8비트 마스크 정밀도 — 실측 (2026-08-11)

이 결정을 하기 전에 `RenderTextureFormat.R8` 의 양자화가 실제로 어떻게 도는지 실제 `DustPaint`
셰이더와 실제 R8 RT 로 쟀다. 노이즈를 끄면 중심 텍셀의 `src` 가 정확히 `strength` 가 되므로
양자화만 분리해 볼 수 있다.

**법칙: 매 스탬프 `round(strength × 255)` 단계씩 뺀다.**

| `strength` | 이론 (/255) | 실측 (/255) | |
|---|---|---|---|
| 0.001 | 0.255 | **0** | 80 번을 찍어도 255 그대로 |
| 0.002 | 0.51 | 1 | 의도의 1.96 배 |
| 0.004 | 1.02 | 1 | |
| 0.01 | 2.55 | **3** | 의도의 1.18 배 |
| 0.05 | 12.75 | 13 | |
| 0.35 (기본값) | 89.25 | 89 | 오차 0.28% |

기준선으로 같은 붓질을 `RFloat` 마스크에 돌리면 `0.002 × 80 = 0.84000` 이 소수점까지 정확히
나온다. **셰이더 수식에는 오차가 없고 어긋남은 전부 8비트 저장에서 나온다.**

`Dust/AGENTS.md:88-91` 의 기존 서술은 **방향이 반대다.** "약한 붓질은 눈에 띄는 변화를 못 만들
수 있다"고 적혀 있지만 실제로는 두 구간으로 갈린다.

- **`strength < 0.00196`** — 반올림이 0 이라 **영원히 아무 일도 일어나지 않는다.** 인스펙터에서
  아무리 만져도 무효인 구간이 존재한다
- **그 위** — 반올림이 올림 쪽으로 튀어 **의도보다 더 많이** 지워진다

즉 약하게 문지를수록 예상보다 빨리 깨끗해지다가, 어느 선 아래로는 붓이 고장난 것처럼 반응이
없어진다. 손맛을 튜닝할 때 실제로 걸리는 함정이다. `Dust/AGENTS.md` 를 이 실측으로 정정한다.

**이번 설계에 대한 결론: 무관하다.** 실제로 쓰는 `strength = 0.35` 에서 오차는 0.28% 이고 세 번
찍으면 마스크가 0 에 도달한다. 8비트는 이번 결정의 제약이 아니다.

## 4. VFX 세 가지

셋 다 §3 의 지운양 RT 하나에서 나온다. 추가로 CPU 가 주는 스칼라는 **패드 포즈와 이동 방향**
뿐이고, 이건 도구가 이미 알고 있는 값이라 공짜다.

| | 무엇 | 어디서 나오나 |
|---|---|---|
| **퍼프** | 지워진 자리에서 피어올라 **패드 안쪽으로 빨려드는** 먼지 | 지운양 RT 의 `xyz` 를 시작 위치로, 패드 중심을 향하는 속도 |
| **밀림** | 진행 방향 **앞 모서리**에 낮게 깔려 밀리는 먼지 | 같은 RT + 이동 방향. 패드 앞쪽 텍셀만 살린다 |
| **반짝** | 갓 드러난 자리에서 짧게 튀는 스파클 | 같은 RT, 수명 짧게, 위로 |

**색은 먼지 재질에서 가져온다.** `DustSurface` 의 `_DirtColor` 를 그대로 물리면 재질을 바꿔도
파티클이 따라온다. 별도 색 파라미터를 만들면 반드시 어긋난다.

**밀림이 "지우기 전용"의 빚을 갚는다.** 선행 스펙 `:46` 이 총량 보존을 포기하면서 "밀리는 느낌은
파티클이 대신한다"고 적어뒀다. 그 항목이 여기다.

### 생성한 아트 타겟

셰이더 브랜치와 같은 방법으로, 기존 아트 타겟(`dust-target-stroke.png`, `dust-target-grain.png`)을
레퍼런스로 붙여 `gpt-image-1`(`/v1/images/edits`)에 3장을 생성했다. 톤·먼지 재질·타일 색이
이어지도록 조건부 생성이다. **이건 콘셉트 타겟이지 스펙이 아니다** — 맞춰야 할 목표 이미지일
뿐이고, 무언가 만들어졌다는 증거가 아니다.

패드는 **중립적인 사각 실루엣**으로만 그렸다. 도구 디자인은 `Vacuum/` 소관이고 이 이미지가 그것을
규정하지 않는다.

| `vfx-target-sparkle.png` | 반짝임의 **어휘**(사방 십자 글린트)와 크기 편차 | 위치가 틀렸다. 갓 드러난 **경계**에 몰려야 하는데 타일 한가운데 박혔고 수도 적다 |

### 타겟이 드러낸 설계 모순 — 흡입과 밀림은 같이 세면 안 된다

`vfx-target-push.png` 는 요청대로 잘 나왔는데, **그래서 도구가 명백히 "미는 물건"으로 보인다.**
앞에 먼지가 둔덕으로 쌓이는 것은 대걸레의 동작이지 흡입기의 동작이 아니다. §0 이 "메인 기능은
빨아들이는 것"이라고 못박았으므로 이대로 만들면 도구가 무엇을 하는 물건인지 화면에서 모순된다.

**해소**: 밀림은 **넘치는 것**이지 쌓이는 것이 아니다. 흡입이 감당하지 못한 나머지가 앞 모서리로
조금 새어나가는 정도여야 하고, 대부분의 먼지는 패드 안으로 사라져야 한다. 실제 진공청소기도
가장자리에 먼지가 조금 남지 둔덕을 만들지는 않는다.

- 밀림 파티클의 **양과 수명을 퍼프보다 확실히 작게** 잡는다. 둘의 비율이 곧 "이게 흡입기인가
  대걸레인가"를 말한다
- 밀림 파티클은 **바닥에 쌓여 남지 않는다.** 앞으로 밀렸다가 짧게 사라진다. 남으면 지우기 전용
  마스크와도 어긋난다 — 마스크는 이미 지워졌는데 화면에는 먼지가 있는 상태가 된다
- 타겟 이미지의 둔덕 크기는 **과장이다.** 형태 참고용으로만 쓰고 양은 따라가지 않는다

이 항목은 §8 검증 기준 4번의 판정 문구를 바꾼다 — "앞 모서리를 따라온다"가 아니라 **"흡입기로
보이는가"** 가 기준이다.

## 5. VFX Graph 인가 내장 파티클인가

**주력은 VFX Graph.** §3 의 구조가 그걸 요구한다 — 데이터가 GPU 텍스처에 있고, 내장 파티클의
`Emit(EmitParams)` 는 CPU 가 위치를 알아야 하므로 이 데이터를 먹을 수 없다.

**그래도 내장 파티클로 퍼프 1종을 만들어 나란히 본다.** 셰이더 브랜치가 `Granular`/`Film` 을
A/B 해서 결론을 낸 것과 같은 이유다. 여기서 갈리는 건 룩이 아니라 **워크플로**이고, 그건 한 번
써봐야 안다. 결론은 `Dust/AGENTS.md` 에 결정으로 남긴다.

**대가를 명시한다.**

- `.vfx` 는 GUID 가 박힌 JSON 이라 **Plastic 이 병합하지 못한다.** `.shadergraph` 를 기각한 바로
  그 이유다. 씬과 같은 규칙으로 관리한다 — 피처당 하나, 브랜치는 피처별
- **그래프는 에디터에서만 저작된다.** 이번 브랜치는 분담이 셰이더 때와 뒤집힌다: 셰이더·C#·
  프로퍼티 규약은 위임 가능하지만 **그래프는 손으로** 짜야 한다
- 검증되지 않은 가정이 하나 있다 — VFX Graph 가 텍스처를 포지션 맵으로 쓰고 임계값으로 파티클을
  죽이는 패턴이 URP 17.6 / Unity 6000.6.0b7 에서 실제로 도는지. **구현 전에 최소 검증을 먼저
  한다.** 셰이더 브랜치가 파이썬 프리뷰로 수식을 먼저 검증하고 설계를 두 번 고쳤던 것과 같은
  순서다

## 6. 멀티플레이 — 이번엔 코드가 없지만 지금 정해야 하는 것

Fusion 은 설치돼 있지 않고 이번 브랜치는 네트워크 코드를 한 줄도 쓰지 않는다. 그런데 **이번에
만드는 것이 나중에 어느 계층에 앉는지**는 지금 정해야 한다.

> **Fusion 은 이 브랜치 도중 깔았다가 되돌렸다 (2026-08-11).** 위버가 Plastic 에디터 어셈블리를
> 망가뜨려 팀원 전원의 워크스페이스에 영향을 주기 때문이다. 이번 산출물이 전부 클라이언트 로컬
> 이라 Fusion 없이 만들 수 있다는 점이 롤백을 가능하게 했다. 측정 결과와 재설치 시 주의사항은
> 루트 `AGENTS.md` 의 "Read this before installing Fusion again" 에 있다.

### 복제되는 것은 놀랄 만큼 적다

| 계층 | 무엇 |
|---|---|
| **복제** | 도구의 포즈(표면에 붙어 있으므로 회전이 곧 표면 정렬) · 켜짐/꺼짐 · 소유권 · 서버가 계산한 청소도 |
| **클라이언트 로컬** | 마스크 RT · 지운양 RT · VFX · 파티클 · 사운드 |
| **서버 전용** | CPU 커버리지 그리드 → 청소도의 단일 진실 |

도구는 어차피 눈에 보이는 물건이라 트랜스폼은 이미 복제된다. 청소 동기화가 거기에 **추가로**
요구하는 것은 사실상 **bool 하나**다.

**붓질을 이벤트로 보내지 않는다.** 초당 60 개 × 플레이어 수라 대역폭이 아깝고, 하나라도 유실되면
그 클라이언트의 마스크만 영구히 어긋난다. 대신 Fusion 은 틱 기반이라 모든 피어가 같은 틱에 같은
도구 포즈를 본다 — 각 클라이언트가 "패드가 켜져 있고 표면에 닿아 있으면 찍는다"를 스스로
실행하면 된다. **원인을 보내고 결과는 각자 만든다.** 지우기 전용이라 순서가 어긋나도 양쪽 다 0
으로 수렴하므로 성립한다. 선행 스펙 `:46` 이 지우기 전용을 고르며 얻은 이점이 여기서 실현된다.

**붓질은 프레임당 한 번만 적용한다.** Fusion 은 예측이 빗나가면 틱을 되감아 재시뮬레이션하는데
**마스크는 되감기지 않는다.** `FixedUpdateNetwork` 에서 찍으면 재시뮬마다 중복으로 지워져
원래보다 빨리 깨끗해진다. 붓질은 `Render()` 자리에 둔다.

### 이번 브랜치가 지켜야 할 두 줄

1. **VFX 를 "내 입력"이 아니라 "마스크에 실제로 적용된 붓질"에서 뽑는다.** §3 의 지운양 RT 는
   로컬이든 원격이든 구분 없이 그 클라이언트에서 적용된 붓질을 전부 담으므로, **남의 청소도
   공짜로 보인다.** CPU 에서 `Emit()` 하는 방식은 플레이어마다 배선해야 하고, 원격 플레이어의
   붓질에 대해 월드→UV 문제가 다시 살아난다
2. **붓질을 프레임당 한 번 적용하는 자리에 둔다** — 나중에 `Render()` 로 그대로 옮겨간다

이 둘만 지키면 이번 산출물은 Fusion 이 와도 **고칠 게 없다.** 전부 위 표의 "클라이언트 로컬"
칸에 들어가기 때문이다.

### 죽은 계획 — 선행 스펙 §9 의 `AsyncGPUReadback` 집계

> 청소도 집계 (`Cleanliness/`) — 마스크를 다운샘플 체인으로 줄여 `AsyncGPUReadback` 으로 읽는다.

**이 계획은 데디케이티드 서버에서 성립하지 않는다.** 헤드리스(`-batchmode -nographics`)에는
그래픽스 디바이스가 없어서 RT 생성도 셰이더 실행도 안 된다. 즉 **서버는 마스크를 아예 갖지
못한다.**

따라오는 결론:

- **마스크는 권위 상태가 아니라 프레젠테이션이다.** 서버가 권위로 갖는 것은 붓질을 만들어낸
  *도구 상태*뿐이다
- **청소도 집계는 GPU 를 쓸 수 없다.** 서버가 점수를 알아야 하므로 CPU 쪽 커버리지 표현이 따로
  필요하다. `Cleanliness/` 의 숙제이며, 그때 **월드→UV 문제가 CPU 로 돌아온다** — 메시 UV 래스터
  베이크와 Read/Write Enabled 가 거기서 필요해진다. 이번 VFX 가 그 비용을 없앤 게 아니라
  **미룬 것**이다
- **늦게 들어온 플레이어**는 스트로크 히스토리 재생이 불가능하다. 서버의 저해상도 커버리지
  그리드를 스냅샷으로 보내 클라이언트가 마스크 초기값으로 깔면 된다. 서버 그리드가 존재해야 할
  두 번째 이유다

루트 `AGENTS.md` 의 네트워킹 절을 **Host Mode → Server Mode(데디) 우선**으로 바꾼 근거가
이것이다. 호스트는 GPU 가 있어서 위 실수를 조용히 통과시킨다.

6. **VFX Graph 와 내장 파티클 중 어느 쪽인지 결론이 난다**
7. 바닥을 닦을 때 **아래층·반대편이 지워지지 않는다** (§2 의 두께 판정)
8. URP 에서 마젠타 없음, 콘솔 에러 0

## 10. 미해결

- ~~**VFX Graph 의 텍스처 기반 파티클 배치가 실제로 되는가**~~ — **2026-08-11 확인됨.** URP 17.6 /
  Unity 6000.6.0b7 / VFX Graph 17.6.0 에서 된다. 손으로 만든 맵(`rgb` = 월드 좌표, `a` = 중앙 원
  안만 1)으로 프로브를 만들어 확인했고, 파티클이 프로브를 따라 움직이며 원 밖에는 뜨지 않았다.
  - 죽이는 방법은 **Initialize 에서 `Set Lifetime` 에 `Branch(조건, 정상수명, 0)` 을 꽂는 쪽**이
    통했다. `Set Alive` 는 시도하지 않았다 — 밀림·반짝도 같은 방법을 쓴다
  - 배선은 `Random(Vector2)` → `Sample Texture2D` → `Swizzle(xyz)` → `Set Position`,
    그리고 `.w` → `Compare(>=)` → `Branch` → `Set Lifetime`
  - **함정 둘.** `Bounds Mode` 가 `Recorded` 면 파티클이 월드 좌표로 흩어지는 순간 통째로 컬링돼
    화면이 빈다 — `Automatic` 이어야 한다. 그리고 `Compare` 를 `Equal` 로 두면 알파가 0 또는 1
    이라 영원히 참이 되지 않는다
  - 판정 스크린샷에서 배운 것: 파티클 색이 밝으면 **스페큘러 하이라이트 위에서 안 보인다.**
    프로브를 하이라이트 밖으로 옮기고서야 모양이 읽혔다
- **퍼프가 알갱이로 읽히는가** — 아트 타겟이 답하지 못했다(블러로 나왔다). 셰이더 브랜치의 파이썬
  프리뷰도 같은 지점에서 실패했고, 그때 결론은 "밝기 변조로는 깊이가 안 나온다"였다. 파티클에서도
  같은 함정이 있을 수 있으니 **실물로만 판단**한다. 노멀맵 대신 파티클 크기 편차와 개별 입자의
  가독성이 레버가 될 가능성이 높다
- **지운양 RT 해상도** — 64×64 로 시작하되 퍼프가 성기게 보이면 올린다. 실물로 판단
- **도장 보간** — "그렇게까지 빠르게 움직이지 않는다"고 판단해 보류. 걸레 느낌이 뭉개지면 재개
- **패드 아래 표면이 여럿일 때** — 지운양 RT 를 공유하는 구조는 정했지만 실제로 여러 표면에
  걸친 케이스는 테스트 씬에 없다. 맵이 생기면 확인
