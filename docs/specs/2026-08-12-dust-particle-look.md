# 먼지 청소 파티클 룩 — 설계

> **작성일** 2026-08-12 · **브랜치** `/main/dust-particle-look` · **피처** `Assets/Game/InGame/Dust/`

청소 파티클이 **먼지 알갱이로 읽히게** 만든다. 선행 브랜치가 파이프라인을 끝냈고 룩만 남겼는데,
그 룩이 알갱이가 아니라 **구슬로 보인다.**

선행: [2026-08-11-dust-clean-vfx.md](2026-08-11-dust-clean-vfx.md) — 지운 양 RT와 세 이펙트의
구조가 거기 있다. 그 문서 §8.5(3인칭 거리에서 읽힌다)가 유일한 미달이었고, §10에 "퍼프가
알갱이로 읽히는가"가 **미해결로 남아 있었다.**

---

## 0. 전제 — §10의 미해결 항목이 답을 얻었다

선행 스펙 §10은 이렇게 적어뒀다.

> **퍼프가 알갱이로 읽히는가** — 아트 타겟이 답하지 못했다(블러로 나왔다)

에디터에서 직접 보고 답이 나왔다. **안 읽힌다.** 파티클이 구형으로 보이고 그래서 먼지라는
느낌이 없다.

이것은 §8.5의 "약하다"와 **같은 문제의 다른 얼굴일 가능성이 높다.** `Dust/AGENTS.md`는
§8.5의 원인을 "크기와 개수"로 적어뒀는데, 크기·개수는 *양*의 문제고 지금 관찰된 것은 *모양*의
문제다. 구슬을 크게 키우면 큰 구슬이 된다. **이번 브랜치는 원인 진단을 모양 쪽으로 옮긴다.**

**한다**

| | |

## 2. 왜 랩을 따로 만드나 — `.vfx`는 나한테 불투명하다

세 그래프가 **노출하는 파라미터가 4개뿐이다.** 실측:

```
ErasedMap · ErasedThreshold · PadCenter · Travel
```

전부 파이프라인 배선용이고 **크기·개수·색·텍스처는 하나도 없다.** 게다가 `.vfx`는 노드 타입조차
텍스트로 안 읽힌다 — 노드가 전부 스크립트 GUID를 참조하는 `MonoBehaviour`라 `grep`으로는
출력 컨텍스트가 Quad인지 Mesh인지도 안 나온다.

**결론: 지금 구조에서 룩 튜닝은 100% 수동 GUI 작업이다.** 한 번 값을 바꿔 보려면 사람이
그래프를 열고, 노드를 찾고, 슬라이더를 만지고, 플레이하고, 봐야 한다. 후보가 열 개면 그걸 열 번
한다. 이게 §8.5가 "보이지만 약하다"에서 멈춘 실제 이유다 — 진단이 틀려서가 아니라 **반복이
비쌌기 때문이다.**

내장 파티클은 반대다. 전부 컴포넌트의 직렬화 프로퍼티라 Unity CLI로 **값 세팅 → 플레이 →
스크린샷**을 스크립트로 돌릴 수 있다. 후보 열 개가 사람 손을 안 탄다.

### 구현 중 정정 (2026-08-12) — 바로 위 문단은 절반이 틀렸다

`ParticleSystem`을 CLI로 읽어보니 모듈이 전부 불투명하다:

```
InitialModule · ShapeModule · EmissionModule · SizeModule · ColorModule · RotationModule
  = "<unsupported:Generic>"
```

크기·색·개수·모양이 **전부 그 안에** 있어서 `set_component_properties`로는 하나도 못 만진다.
닿는 것은 `lengthInSec`·`looping` 같은 최상위 스칼라뿐이고 그중 룩 노브는 없다. **"전부
직렬화 프로퍼티라 CLI로 돌아간다"는 이 도구에 대해서는 성립하지 않는다.**

**결론은 바뀌지 않는다.** 랩 스크립트(`DustParticleLookLab`)가 노브를 자기 직렬화 필드로
들고 있다가 C# API로 모듈에 밀어넣으면 된다. `float`·`Color`·`enum`은 CLI가 잘 쓰므로 루프는
그대로 성립한다. 한 겹이 더 필요할 뿐이다.

그리고 이 우회가 원래 계획보다 낫다. **랩의 노브 목록이 그대로 VFX Graph에 만들 Exposed
파라미터의 사양이 된다** — §5가 나중에 하려던 일을 랩이 먼저 강제한다.

### 랩은 도구지 후보가 아니다

`Dust/AGENTS.md:142`에 내장 파티클을 **이미 만들었다가 지운 기록**이 있다. 같은 원형 경로로
스윕해서 6바퀴째를 쟀고:

| | 살아있는 파티클 (바닥은 이미 깨끗함) |
|---|---|
| VFX Graph | **1** |
| 내장 파티클 | **2000** (`maxParticles` 포화) |

**그 결론은 여전히 유효하고 이번에 뒤집지 않는다.** 내장 파티클은 마스크가 GPU에 있어서 먼지가
어디 있었는지 모르고, 그래서 깨끗한 바닥에 계속 먼지를 만든다. 선행 스펙 §8.2가 그걸 금지한다.

이번에 내장 파티클을 다시 꺼내는 것은 **채택 후보로서가 아니라 탐색 도구로서다.** 랩은 마스크를
아예 안 본다. 깨끗한 바닥에도 뜨는데, 답하려는 질문이 "알갱이로 읽히는가"라서 상관없다.

그리고 같은 문서가 이렇게 적어뒀다 — **"내장 버전은 룩에서 잃는 게 없다"**(`Emit(EmitParams)`로
위치와 속도를 개별 지정했으므로). 그 문장이 랩의 근거다. 룩에서 잃는 게 없으니 룩을 여기서
찾아도 된다.

**따라서 랩에서 나온 답은 반드시 VFX Graph로 이관된다.** 랩이 이기는 결말은 없다.

## 3. 유력한 원인 — 스프라이트

`Dust/Textures/`에 **파티클용 스프라이트가 하나도 없다.** 있는 것은 오염 알베도·노멀·러프,
마스크 프리셋, 디졸브 노이즈, 바닥 타일뿐이다.

그래서 그래프들이 VFX Graph의 **기본 파티클 텍스처**(부드러운 원형 블롭)를 쓰고 있을 것으로
본다. 그렇다면 구형으로 보이는 게 당연하다.

**이건 추정이지 확인이 아니다.** §2에서 적었듯 텍스트로는 확인이 안 된다. 랩 작업 전에 그래프를
한 번 열어 출력 컨텍스트와 텍스처를 눈으로 확인하고, 이 절을 사실로 정정하거나 기각한다.

**중요한 따름 결과: 파티클 시스템을 바꾸는 것 자체는 구형을 안 고친다.** 내장 파티클도 기본
머티리얼이면 똑같이 동그랗다. 랩의 가치는 "다른 시스템"이 아니라 "빠른 반복"에 있다.

## 4. 랩 구성

### 씬 — `Dust/Tests/Dust_ParticleLook_Test.unity` (신규)

`Dust_Look_Test`를 복제해 바닥·조명·`DustPainter`를 그대로 가져오고, VFX 3개는 끄고 내장
파티클 하나를 붙인다.

**복제하는 이유.** `Dust_Look_Test`는 선행 브랜치 판정(112→1 · 17→1 · 43→0)의 근거 씬이다.
거기 손대면 그 판정과의 비교가 깨진다. 씬은 YAML이라 머지도 안 되므로 분리가 안전하다.
`Dust/Tests/`에는 이미 `Dust_Look_Test`와 `Dust_MaterialVariants_Test` 둘이 있다 — 검증하려는
것이 다르면 씬을 나누는 것이 이 피처의 기존 방식이고, 새 규칙이 아니다.

### 카메라는 실제 청소 리그 수치로 맞춘다

판정 기준이 "**3인칭 거리에서** 읽힌다"이므로 플레이어가 실제로 보는 프레이밍이어야 한다.
`/main/vacuum-cleaning-mode`가 튜닝한 값(cs:83~85)을 그대로 쓴다:

| | |
|---|---|
| 피치 | 50° |
| `FollowOffset` | `(0, 5.362, -4.5)` |
| `LookAtOffset` | `(0, 0.6, 0.8)` |

**바닥의 스페큘러 하이라이트가 프레임 안에 들어와야 한다.** `Dust/AGENTS.md`가 §8.5의 원인
중 하나로 지목했고, 선행 브랜치의 프로브 판정에서도 "파티클 색이 밝으면 하이라이트 위에서 안
보인다"가 실제로 걸렸다. 하이라이트를 피한 프레임에서 잘 보이는 것은 판정이 아니다.

### 스크립트 — `Dust/Tests/DustParticleLookLab.cs`

`DustPadSweep`이 만든 패드 포즈를 읽어 `ParticleSystem`을 그 자리로 옮기고 방출한다.

마스크는 **의도적으로** 안 본다(§2). `Emit(EmitParams)`로 개별 지정하지도 않는다 — 지운 양을
모르는 랩에서는 지정할 값이 없고, 알갱이로 읽히는지는 파티클이 패드 근처에 있기만 하면 답이
나온다.

`Tests/` 아래 두는 이유: 프로덕션 코드가 아니고 검증 씬에서만 쓰인다. 랩은 **남긴다** — 앞으로
파티클 룩을 볼 때마다 쓰는 도구다.

### `DustPadSweep.CurrentPad` — 한 줄 추가

`DustPadSweep`은 `BrushPad`를 `Update` 안의 로컬 변수로만 만들고 밖에 안 내놓는다(`Laps`만
public). 랩이 패드 포즈를 알 방법이 없다.

```csharp
public BrushPad CurrentPad { get; private set; }
```

**대안은 랩이 같은 원 공식을 자체 계산하는 것**이고, 기각한다. 중심·반지름·랩 시간이 두 곳에
적히면 한쪽만 바뀌는 날 파티클이 패드에서 떨어진 채로 판정하게 된다. 코드 규약의 "두 번째
호출자가 확인되면 추상화한다"에도 맞는다 — 소비자가 실제로 생겼다.

## 5. 돌릴 변수, 그리고 이관

랩에서 A/B할 것:

| | 왜 |
|---|---|
| **`renderMode`** | Billboard / StretchedBillboard / Mesh. **가장 의심스럽다** — 늘어뜨리면 구슬 느낌이 바로 죽는다 |
| **스프라이트** | §3의 유력 원인. 알갱이 실루엣 후보 — §7 |
| `startSize` + 분포 | 한 크기로 균일하면 그것만으로 인공적이다 |
| `emissionRate` | §8.5의 "약하다"에 직접 걸린다 |
| `startColor` | 스페큘러 하이라이트와 경쟁하지 않을 것. 색 자체는 먼지 재질에서 온다 |
| `startSpeed` · `gravityModifier` | 빨려드는 궤적이 유지되는지 |
| `startRotation` 랜덤 | 같은 스프라이트라도 회전이 고정이면 도장처럼 보인다 |

**이관할 때 룩 노브를 Exposed로 뺀다.** 이긴 값을 그래프에 손으로 넣는 김에, 같은 값을
파라미터로 노출한다. 그러면 §2에서 적은 "100% 수동 GUI"가 그 시점부터 풀린다 — 다음 튜닝은
그래프를 안 열고 CLI로 돌아간다.

이건 이번 브랜치의 **부수적 산출이 아니라 목적 중 하나다.** 룩을 한 번 고치는 것보다 룩을
고칠 수 있는 상태를 만드는 게 오래 간다.

### 노출할 파라미터 — 확정 (2026-08-13)

세 그래프에 **글자 그대로 같은 이름**으로 만든다. 그래야 한 코드가 셋을 다 만진다.
**언더스코어를 쓰지 않는다** (`Dust/AGENTS.md:55`).

| 이름 | 타입 | 무엇 | 왜 이것인가 |
|---|---|---|---|
| `ParticleRate` | float | **튀는 양** — 스폰 개수 배율 | §8.5 "약하다"에 직결되는 축 |
| `ParticlePower` | float | **튀는 기세** — 초기 속도 배율 | 흡입감. 양과 독립적으로 느껴진다 |
| `ParticleSize` | float | 한 알 크기 배율 | |
| `ParticleGravity` | float | **가라앉는 정도** — 중력/하강력 배율 | 2026-08-13에 실제로 걸렸다. 아래 참조 |
| `ParticleColor` | Color | 색 | 랩에서 판정이 갈렸다 — 밝으면 하이라이트에 묻힌다 |
| `ParticleTexture` | Texture2D | 스프라이트 | 랩에서 **가장** 결정적이었다 (알파의 유무) |

**`ParticleGravity`가 목록에 늦게 들어온 이유 (2026-08-13).** 파티클이 판 아래로 가라앉아 바닥에
초승달로 잘리는 문제가 나왔다. 코드 쪽에서 할 수 있는 것은 `_ErasedLift`를 0.04에서 0.15로 올려
스폰 높이를 벌어주는 것뿐이었고, 그걸로 증상은 사라졌다. 하지만 그건 **시간을 벌어준 것이지
균형을 고친 것이 아니다** — 오래 사는 파티클은 여전히 가라앉는다. 진짜 노브는 그래프 안의
중력이고, 그래서 노출 목록에 넣는다. `DustCleanVfx._nozzleHeight`는 이 문제의 노브가 아니다.
0.9와 1.8로 올려봤지만 흡입 방향만 바뀌고 초승달은 그대로였다.

**절대값이 아니라 배율로 뺀다.** 그래프 안에는 이미 곡선과 랜덤 범위가 들어 있고, 절대값으로
덮으면 그 변화가 죽어 파티클이 도장처럼 보인다. `Multiply` 노드를 하나 끼워 기존 값에 곱하면
구조를 유지한 채 전체가 스케일된다. `ParticleColor`·`ParticleTexture`만 예외로 직접 대입이다.

**개수를 아낀 이유.** 파라미터 하나를 만드는 것이 수동 GUI 작업 한 건이고 세 그래프에 반복된다.
랩에서 실제로 판정이 갈린 축만 넣었다 — 렌더모드는 Billboard로 결론이 났고, 회전 랜덤은
그래프에 이미 있으므로 뺀다.

**두 가지가 공짜로 딸려온다.**

- `DustCleanVfx.Bind`는 자기가 아는 네 이름(`ErasedMap`·`ErasedThreshold`·`PadCenter`·`Travel`)만
  건드린다. 새 파라미터는 코드가 덮어쓰지 않는다
- 노출된 파라미터는 `VisualEffect` 컴포넌트마다 **인스턴스별 오버라이드**가 된다. 대걸레와
  차량이 같은 그래프를 쓰면서 서로 다른 값을 가질 수 있다

**동기가 하나 늘었다 (2026-08-13).** 차량에 VFX를 붙였는데 파티클이 안 뜨는 문제를 쫓을 때,
노출된 `ErasedThreshold`는 CLI로 즉시 바꿔가며 배제할 수 있었지만 나머지는 그래프를 열어야 해서
손을 못 댔다. **노브는 룩 튜닝 도구이기 전에 디버깅 도구다.**

## 6. 도구가 둘이 됐다 — 이번 소관은 아니지만 기록한다

`/main` cs:96·98에서 팀원이 `InGame/Vehicle/`을 올렸고, `VehicleMopPad`가
`DustPaintTarget.Paint(BrushPad)`를 호출한다. **먼지를 지우는 도구가 대걸레와 차량 둘이 됐다.**

다만 `VehicleMopPad`는 `DustCleanVfx`를 부르지 않는다. **차량은 청소하지만 파티클이 안 뜬다.**

이번 브랜치에서 고치지 않는다 — 남의 피처 파일이고, 배선 한 줄이 아니라 차량 쪽 패드 포즈와
`BeginFrame`/`CaptureErased` 순서를 맞추는 일이다. 하지만 §5의 Exposed 파라미터가 **더 가치
있어진다**: 소비자가 둘이면 룩을 그래프 안에 박아두는 비용도 두 배다.

4. **선행 브랜치의 판정 8개가 하나도 안 깨진다** — 특히 §8.2(깨끗한 자리에선 안 난다).

## 9. 미해결

- **랩의 답이 VFX Graph로 1:1 이관되는가.** 내장 파티클과 VFX Graph는 크기·속도의 의미가 다르고
  URP에서 렌더 경로도 다르다. 수치가 아니라 **방향**(예: "늘어뜨려야 한다", "실루엣이 불규칙해야
  한다")이 옮겨간다고 보는 게 안전하다. 이관 후 다시 판정하는 이유
- **§3이 추정이다.** 그래프를 열어보기 전까지 구형의 원인이 스프라이트라는 근거는 없다.
  첫 작업이 이 확인이어야 한다
- **크기·개수와 모양 중 무엇이 §8.5의 주범인지 모른다.** 둘 다 고치면 답이 안 나온다. 랩에서
  모양만 먼저 바꿔 보고, 그것으로 부족할 때 크기·개수를 건드린다
