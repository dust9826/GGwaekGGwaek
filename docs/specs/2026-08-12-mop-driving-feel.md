# 대걸레 주행 필링 — 설계

> **작성일** 2026-08-12 · **브랜치** `/main/mop-driving-feel` · **피처** `Assets/Game/InGame/Mop/`

대걸레를 **탈것**으로 바꾸고, 관성과 드리프트가 있는 아케이드 주행을 넣는다. 목표는 크레이지
택시(Sega, 1999)의 캐주얼 레이싱 손맛이다.

선행: [2026-08-11-mop-cleaning-mode.md](2026-08-11-mop-cleaning-mode.md) — 좌클릭 토글 청소 모드,
탱크 조작, `BrushPad` 규약이 거기 있다. 이 문서는 그 중 **조작만** 갈아엎는다.

## 0. 왜 지금, 왜 따로

### 목표는 "속도가 빠른 것"이 아니다

레퍼런스는 크레이지 택시다. 그 게임에서 손맛을 만드는 부품을 갈라보면 이렇다.

| 부품 | 이번에 넣나 |
|---|---|
| 압도적인 속도, 즉각적인 스로틀 | **넣는다** |
| 헐거운 그립, 큰 드리프트 | **넣는다** |
| 속도에 반응하는 화면·소리 (FOV·카메라 후퇴·엔진 피치) | 다음 단계 |
| 특수기 (Crazy Dash · Crazy Stop) | 그 다음 단계 |
| 부딪혀도 안 멈추고 튕기며 계속 감 | **공짜로 따라온다** — §2 |

**연출을 뺀 1단계만으로는 목표에 도달하지 못한다.** 크레이지 택시 속도감의 절반은 실제 속도가
아니라 FOV와 엔진 피치에서 나온다. 이건 실패가 아니라 예정이고, 순서가 이런 이유는 §3에 있다.

### 팀원의 `InGame/Vehicle/`과 따로 간다

같은 날(2026-08-12) 팀원이 cs:96~98로 차량 청소 프로토타입을 올렸다 — `VehicleController`,
`VehicleCamera`, `VehicleNozzle`, `VehicleVacuum`, `VehicleMopPad`. 설계 문서는 `Assets/Test.md`다.
방향이 이쪽과 같다: 차량이 메인 플레이 주체고 대걸레는 상시 청소한다.

**그런데 그쪽에도 관성이 없다.**

```csharp
// VehicleController.Drive() — 팀원 코드
Vector3 forwardVelocity = transform.forward * _currentForwardSpeed;
Vector3 verticalVelocity = new Vector3(0f, _rigidbody.linearVelocity.y, 0f);
_rigidbody.linearVelocity = forwardVelocity + verticalVelocity;
```

`Rigidbody`인데도 **횡방향 속도를 매 물리 스텝마다 버린다.** 그립이 무한대라 절대 미끄러지지
않고, 충돌이 준 속도까지 같은 줄에서 지워지므로 벽에 부딪혀도 튕기지 않는다. 조향도
`_turnRateDegPerSec = 120f` 고정이라 8 m/s든 16 m/s든 똑같이 돈다.

그쪽을 고치는 대신 **우리 폴더에 처음부터 만든다.** 이유는 소유권이다. `Mop/`은 이쪽이 전부
소유하므로 팀원 파일도 프리팹 충돌도 없고, 무엇보다 **`.prefab`과 `.unity`는 Plastic이 머지하지
못한다.** 팀원이 오늘도 작업 중인 프리팹을 양쪽이 건드리면 한쪽을 통째로 버려야 한다.

두 프로토타입이 나란히 서게 되는 것은 의도한 비용이다. 어느 쪽 주행이 맞는지는 몰아봐야 알고,
합칠 때 한쪽을 고르면 된다. 합치는 방향은 §5에 적어둔다.

### 참고 — `CurrentSpeed01`이 저속에서 죽어 있다

이번 범위는 아니지만 발견한 김에 남긴다. 팀원 코드의

```csharp
CurrentSpeed01 = Mathf.InverseLerp(_baseMaxSpeed, _boostMaxSpeed, Mathf.Abs(_currentForwardSpeed));
```

는 `_baseMaxSpeed`(8) 이하에서 **항상 0**이다. `VehicleCamera`·`VehicleNozzle`·`VehicleVacuum`이
전부 이 값을 구독하므로, Shift를 누르지 않으면 속도 연출이 하나도 걸리지 않는다. 합칠 때
같이 정리한다.

## 2. 주행 모델

### 지금 없는 것은 물리가 아니라 상태다

기존 `MopLocomotion`은 매 프레임 입력에서 속도를 새로 만든다.

```csharp
Vector3 velocity = transform.forward * (move.y * _moveSpeed);   // 관성이 저장될 곳이 없다
```

팀원 `VehicleController`도 형태만 다를 뿐 같다 — 정면 속도 하나(`_currentForwardSpeed`)만 들고
횡방향은 매번 0으로 만든다. **이번 작업의 핵심은 속도를 벡터로 보존하는 것이다.**

### `Rigidbody`의 속도를 덮어쓰지 않고 분해해서 되돌려쓴다

```csharp
Vector3 v = _rigidbody.linearVelocity;
float up = v.y;                                   // 중력·점프는 물리에 맡긴다

float fwd = Vector3.Dot(v, transform.forward);    // 정면 성분
Vector3 lat = v - transform.forward * fwd;        // 횡 성분 (y 제거 후)
lat.y = 0f;

fwd = Mathf.MoveTowards(fwd, targetSpeed, rate * dt);          // 스로틀 / 브레이크
lat = Vector3.MoveTowards(lat, Vector3.zero, grip * dt);       // 그립

_rigidbody.linearVelocity = transform.forward * fwd + lat + Vector3.up * up;
```

이 다섯 줄이 설계 전부다. 팀원 코드와의 차이는 `lat`을 **버리지 않고 감쇠시킨다**는 것 하나뿐이고,
거기서 세 가지가 한꺼번에 나온다.

| 나오는 것 | 어떻게 |
|---|---|
| **드리프트** | 몸이 회전해도 `lat`이 안 따라온다. 그 차이가 미끄러짐이다 |
| **벽 튕김** | 충돌이 `linearVelocity`에 준 횡속도가 살아남아 그립으로 서서히 죽는다 |
| **소품 밀기** | `Rigidbody`끼리의 상호작용을 지우지 않는다 |

크레이지 택시의 "부딪혀도 안 멈춤"이 별도 코드 없이 여기서 나온다. 팀원 코드가 그걸 못 하는
이유도 같은 줄이다 — 덮어쓰기가 충돌 결과까지 지운다.

### 제자리 회전은 분기가 아니라 곡선의 끝점이다

"저속에서만 제자리 회전"을 `if (speed < x)`로 짜면 경계에서 조작이 튄다. 대신 **조향 각속도를
속도의 함수 하나로** 둔다.

| 속도 | 조향 각속도 | 그립 |
|---|---|---|
| 0 | `120°/s` — 제자리 회전 | 높음 (안 미끄러짐) |
| 중간 | `~110°/s` | 중간 |
| 최고속 | `70°/s` — 무거워짐 | 낮음 (후미가 빠짐) |

속도 0에서도 각속도가 살아 있으므로 제자리 회전이 **분기 없이** 나온다.

**제자리 회전은 크레이지 택시에 없다.** 이건 의도한 예외다 — 이 탈것은 바닥을 덮어야 하는
청소 도구고, 제자리 회전이 없으면 구석과 벽에 붙은 자리를 못 닦는다. 레이싱 필링과 청소
커버리지가 부딪히는 유일한 지점이고, 커버리지를 택했다.

### 회전은 `MoveRotation`, 이동은 `linearVelocity`

회전을 토크로 주면 관성 모멘트를 튜닝해야 하고 아케이드 감각과 멀어진다. `MoveRotation`으로
직접 돌리고, 미끄러짐은 속도 쪽에서만 만든다.

### 드리프트 상태는 저장하지 않는다

`Vector3.Angle(_rigidbody.linearVelocity, transform.forward)`로 언제든 읽을 수 있다. 저장하면
진실이 둘이 되고, 2단계의 스퀼·카메라가 어느 쪽을 봐야 하는지 애매해진다. 읽기 전용
프로퍼티 하나로 노출한다.

### 전부 `FixedUpdate`

가변 dt로 적분하면 프레임률마다 가속감이 달라진다. **조작감을 튜닝하는 브랜치에서 튜닝값이
머신마다 다르게 느껴지면 작업 자체가 성립하지 않는다.** Fusion이 오면 `FixedUpdateNetwork`로
그대로 간다(§6).

`MopPad`의 붓질은 `Update`에 그대로 둔다 — 프레임당 한 번이라는 계약이 선행 스펙에 있다.

## 3. 수치 초안

**전부 플레이 모드에서 맞출 값이고, 맞다고 주장하지 않는다.** 특히 그립은 계산으로 안 나온다 —
12 m/s에서 70°/s로 1초 꺾으면 횡속도가 11 m/s까지 뜨는데, 그게 "시원한 드리프트"인지 "제어
불능"인지는 몰아봐야 안다.

| 항목 | 값 | 근거 |
|---|---|---|
| 최고속 | `12 m/s` (43 km/h) | 기존 대걸레 `2.2`의 5.5배. 팀원 `Vehicle`의 기본 `8`보다 빠르다 |
| 후진 최고속 | `4 m/s` | 후진이 느려야 전진이 빨라 보인다 |
| 가속 | `20 m/s²` | 0→최고속 **0.6초**. 기다리는 느낌은 없되 램프는 있다 |
| 브레이크(반대 입력) | `30 m/s²` | 코스팅보다 확실히 빨라야 브레이크로 읽힌다 |
| 코스팅(무입력) | `8 m/s²` | 손 떼면 1.5초간 미끄러져 멈춘다 |
| 조향 (0 → 최고속) | `120 → 70 °/s` | §2 |
| 횡 그립 (0 → 최고속) | `40 → 15 m/s²` | **튜닝 1순위** |

튜닝은 **우리 씬의 인스턴스에서** 하고, 확정된 값은 **코드 기본값으로 구워 넣는다.** 프리팹에
오버라이드를 남기지 않기 위해서다(§0의 머지 이유와 같다).

## 4. 구성

`Assets/Game/InGame/Mop/`에 넷을 더한다. 기존 파일은 지우지 않는다 — `MopMode`·`MopLocomotion`은
도보 청소 모드로 그대로 두고, 이 모델이 통과한 뒤에 운명을 정한다.

| 파일 | 책임 |
|---|---|
| `Scripts/MopVehicle.cs` | 주행 전부 — 속도 분해, 조향 곡선, 그립 곡선. `Rigidbody` 필요 |
| `Scripts/MopDriveProbe.cs` | §8의 기준을 눈이 아니라 로그로 판정하는 계측기. **체크인한다** — `DustPadSweep`을 검증 도구로 남긴 것과 같은 이유로, 튜닝을 반복할 때 같은 조건을 재현하는 장치가 판정의 전제다 |
| `Prefabs/PF_MopVehicle.prefab` | 탈것. `Rigidbody` + `MopVehicle` + `MopPad` + Cinemachine 타겟 |
| `Tests/Mop_Driving_Test.unity` | 직선 60 m + 90° 코너 2개 + `M_Dust` 바닥 패널 |
| `Input/MopControls.inputactions` | 기존 자산. `Cleaning` 맵을 그대로 쓴다 (WASD) |

**입력 맵을 켤 주체가 없다.** 지금은 `MopMode.SetCleaning()`이 `Cleaning` 맵을 `Enable()`하는데,
탈것 프리팹에는 `MopMode`가 없다. 그래서 `MopVehicle`이 자산을 인스턴스로 복제해 자기
`OnEnable`에서 맵을 켜고 `OnDisable`에서 끈다 — `MopMode`가 이미 하는 것과 같은 방식이고,
원본 자산을 직접 `Enable()`하면 씬을 나가도 활성인 채로 남는다는 이유도 같다.

이러면 `MopMode`와 `MopVehicle`이 같은 맵을 각자 켜게 된다. **둘이 한 씬에 같이 있으면 안 된다** —
이번 검증 씬에는 탈것만 둔다(§1). 도보와 탈것을 한 씬에 두는 날 입력 소유권을 다시 정한다.

**타입 이름이 겹치면 안 된다.** 네임스페이스가 `PPack` 하나뿐이라 `VehicleController`·`VehicleCamera`
같은 이름은 이미 팀원이 쓰고 있다. 접두사를 `Mop`으로 통일한다.

카메라는 **Cinemachine을 쓴다.** 선행 스펙이 직접 짠 추적을 버리고 Cinemachine으로 옮긴 기록을
남겼고(`Mop/AGENTS.md`), 그 결론이 여기서도 유효하다. 1단계에서는 리그 설정만 하고 스크립트가
0줄이었고, 2단계에서 렌즈와 오프셋만 미는 컴포넌트를 하나 얹었다(§11) — 추적 자체는 여전히
Cinemachine 이 한다.

## 5. 팀원 `Vehicle`과 합칠 때

두 구현이 다른 곳은 **주행 모델 하나**다. 카메라·노즐·진공·흡입 원뿔은 팀원 쪽이 더 나가 있고
이쪽에 대응물이 없다.

| | 이쪽 (`Mop/`) | 팀원 (`Vehicle/`) |
|---|---|---|
| 횡속도 | 그립으로 감쇠 → 드리프트·튕김 | 매 스텝 0 |
| 조향 | 속도에 따른 곡선 | `120°/s` 고정 |
| 속도 정규화 | 0 ~ 최고속 | `InverseLerp(8, 16)` — 저속에서 죽음 |
| 카메라 | Cinemachine, 속도 반응 없음 | 스크립트 오빗, 속도 반응 있음 |
| 흡입·노즐 | 없음 | 있음 |

**합치는 방향은 "주행만 이식"이다.** 이쪽의 `Drive()` 다섯 줄과 곡선 두 개를
`VehicleController`에 옮기고, `CurrentSpeed01`을 `0 ~ _boostMaxSpeed` 기준으로 고친다. 그러면
팀원의 카메라·노즐·진공이 전부 살아 있는 채로 관성이 붙는다. 이쪽 프리팹과 씬은 그때 버린다.

**뒤집히는 경우**: 몰아보니 도보 캐릭터가 남아야 한다고 판단되면, 그때는 두 프로토타입이 각각
다른 플레이를 담게 되므로 합치지 않는다.

## 6. 멀티 — 이번에도 코드는 없다

`Rigidbody`를 쓰지만 **물리에 맡기는 것은 중력·충돌뿐**이고 속도는 우리가 매 스텝 정한다. 이건
Fusion 예측·재시뮬레이션에서 중요하다 — 상태가 `linearVelocity`와 트랜스폼뿐이라 되감기가
싸다. 이번 산출물이 지켜야 할 것은 두 줄이다.

1. **주행 적분을 `FixedUpdate`에 둔다** — 나중에 `FixedUpdateNetwork`로 그대로 옮긴다
2. **붓질은 `Update`에 남긴다** — `FixedUpdateNetwork`에 두면 재시뮬레이션마다 중복으로 지워진다

선행 스펙 §5의 결론(복제되는 것은 도구 포즈·온오프·소유권뿐)이 그대로 적용된다.

## 7. 알려진 결함 — 이번에 안 고친다

**빠르게 달리면 청소 자국에 줄무늬가 생긴다.** `MopPad`는 진행 방향 길이가 `0.3 m`이고
`Update`당 한 번만 찍힌다.

| | 프레임당 이동 | 결과 |
|---|---|---|
| 기존 2.2 m/s @60fps | 0.037 m | 8겹 |
| **12 m/s @60fps** | 0.2 m | 겹침 0.1 m — 아슬아슬 |
| 12 m/s @30fps | 0.4 m | **구멍** |

**튜닝 중에 이게 보여도 주행 버그가 아니다.** 4단계에서 서브스텝(이동 거리를 패드 길이의 절반
이하로 쪼개 여러 번 찍기)으로 고친다. 지금 정하지 않는 이유는 서브스텝 횟수가 최고속에
달려 있어서다 — 최고속이 안 정해진 상태에서 정하면 튜닝 후 또 고친다.

같은 이유로 **드리프트 중 먼지 밀림 방향도 틀린다.** `MopPad`가 `_vfx.Play(pad, forward)`에
캐릭터 정면을 넘기는데, 미끄러지는 동안은 실제 이동 방향과 다르다. 4단계에서 같이 고친다.

한편 **패드가 정면을 따르는 것 자체는 고치지 않는다.** 드리프트 중 몸이 옆을 보면 패드가 호를
그리며 넓게 쓸고 지나가는데, 이건 결함이 아니라 이 게임에서 레이싱과 청소가 붙는 지점이다 —
빠르게 모는 것이 곧 잘 닦는 것이 된다.

| 드리프트를 별도 상태·버튼으로 | 상태가 늘고 키가 는다. 그립을 속도에 물리면 빠를수록 자연히 미끄러진다 |
| 특수기를 입력 시퀀스로 (크레이지 택시식 S→W) | 원본 손맛이지만 알려주지 않으면 아무도 모른다. 협동 캐주얼 게임에는 전용 키가 맞다. 3단계에서 Shift·Space |
| 속도 연출을 1단계에 같이 | FOV·카메라 거리는 최고속이 확정돼야 붙일 값이 정해진다. 지금 넣으면 두 번 튜닝한다 |

## 11. 2단계 — 속도 연출 (2026-08-12 추가)

§1이 "안 한다"로 미뤘던 것이다. 순서를 앞당긴 이유는 **연출 없이 손맛을 판정하면 미완성인 것을
판정하게 되기 때문**이다 — §0에 "1단계만으로는 목표에 도달하지 못한다"고 이미 적어뒀다.

### 컴포넌트를 둘로 나눈다

| | 어디에 | 왜 |
|---|---|---|
| `MopVehicleCameraFeel` | vcam (씬) | 카메라는 각 클라이언트의 로컬 물건이다. Fusion 이 와도 복제되지 않는다 |
| `MopVehicleAudio` | 차량 프리팹 | 소리는 3D 위치를 가져야 하고, 원격 플레이어의 차 소리가 그쪽 위치에서 나야 한다 |

합쳐두면 Fusion 이 오는 날 갈라야 한다. 둘 다 `Speed01`·`SlipAngle`을 **읽기만** 하고 아무것도
되돌려주지 않는다.

**입력이 아니라 적용된 상태를 읽는다.** 루트 `AGENTS.md`의 *"VFX 를 복제된 상태에서 구동하라,
로컬 입력에서 하지 마라 — 아니면 자기 효과만 보이고 팀원 것은 안 보인다"* 가 그대로 적용된다.

### 값

| | 정지 | 최고속 |
|---|---|---|
| FOV | `60` | `76` |
| 카메라 오프셋 | `(0, 2.6, -7)` | `(0, 3.3, -9.5)` |
| 모터 피치 / 볼륨 | `0.75` / `0.35` | `1.5` / `0.8` |

드리프트는 슬립각 `15° → 30°`를 `0 → 1`로 매핑해 FOV `+6`과 드리프트 레이어 볼륨 `0.6`을 얹는다.

**끝점 30°는 실측에서 왔다.** 처음엔 45°로 뒀는데 이 차가 실제로 내는 최대 슬립각이 30°라 범위의
절반이 죽어 있었다. **연출 곡선의 끝점은 모델이 실제로 만드는 값의 끝에 맞춘다** — 둥근 숫자를
쓰면 가장 격한 순간에도 효과가 절반만 뜬다.

응답 시간은 카메라 `0.35s`, 소리 `0.12s`. `Assets/Test.md`가 카메라를 `0.3~0.5s`로 시험하라고
적었고, 소리가 그만큼 늦으면 가속이 굼떠 들린다.

### 실측

| | 정지 | 최고속 / 슬립 최대 |
|---|---|---|
| FOV | `60` | `75.97` → 슬립 최대에서 `76.90` |
| 모터 피치 | `0.75` | `1.465` |
| 카메라 오프셋 | `(0, 2.6, -7)` | `(0, 3.21, -9.19)` |
| 드리프트 레이어 볼륨 | `0` | `0.225` |

목표값에 살짝 못 미치는 것은 `SmoothDamp`가 수렴 중인 정상 동작이다.

### 알려진 공백

- **전용 스퀼 음원이 없다.** 드리프트 레이어는 `sound/vaccum1/big_prop_clog_vibration.wav`를 임시로 쓴다
- **`AudioSource` 둘 다 2D다.** `spatialBlend`가 커브(`panLevelCustomCurve`)로 직렬화돼 CLI 로 못 건드렸다. **멀티 전에 3D 로 바꿔야 한다** — 안 그러면 모든 차 소리가 리스너에 붙는다
