# 눈 표면 — 설계

> **작성일** 2026-08-14 · **브랜치** `/main/snow-surface` (예정) · **피처** `Assets/Game/InGame/Snow/`

두께가 있는 눈을 바닥에 깔고, 차량이 지나가면 파이고, 이벤트·몬스터 방해로 다시 쌓이게 한다.

먼지(`InGame/Dust/`)는 그대로 살아 있고 눈은 **다섯 번째 오염 종류가 아니다.** 먼지 3종(`M_Dust`·`M_Sand`·`M_GreyDust`)이 셰이더 변경 0으로 돌아간 이유는 "값만 다르고 수식이 같다"였는데, 눈은 두께와 재적설 때문에 수식이 다르다. 눈은 **별 메시·별 셰이더·별 데이터**로 서고, 먼지의 룩이 하나도 변하지 않는 것이 이 작업의 회귀 기준이다.

---

## 1. 확정된 요구

| 항목 | 결정 | 대화에서의 근거 |
|---|---|---|
| 깊이 | **15~30cm**, 차량 바퀴 절반 | 먼 거리에서도 밀린 길과 안 밀린 곳의 단이 읽혀야 한다 |
| 실루엣 | **실제 형상.** 가장자리·그림자가 맞아야 한다 | 시차(POM)만으로는 불가 |
| 게임플레이 | 깊은 눈은 차를 **느리게** 한다. 판정은 **0/1** | 연속 깊이→저항 곡선은 안 만든다 |
| 밀린 눈 | **보존 없음.** 필드에서 감소 + 장벼 앞 임시 더미(연출) | 총량 보존은 요구가 아니다 |
| 재적설 | **이벤트·몬스터 방해로 쌓인다.** 상시 강설이 아니다 | 2026-08-14 정정 — §8 |
| 먼지 | **공존.** 룩 변화 0 | |

**깊이 단계는 16개로 시작한다.** 처음 계획은 4개였고, 게이트에서 부분 적설 구간의 내부 단이 계단으로 보여 올렸다(§7.1). 늘리는 것이 싼 축이라는 계산(§5)이 실제로 값을 정한 첫 사례다. 단계를 늘려도 셰이더는 바뀌지 않는다 — §5 규약 3.

## 2. 렌더링 방식 — 바닥 위 패널 + 정점 변위

세 방식을 비교했다. 셋 다 "도구가 데이터에 쓰고 셰이더가 그것을 읽는다"는 구조는 같고, 다른 것은 **두께를 어디서 만드는가**뿐이다.

| 방식 | 두께의 실체 | 판정 |
|---|---|---|
| 시차(POM) | 픽셀 셰이더가 워프 | **기각.** 실루엣이 안 변하고 차량 바퀴와의 교차가 틀린다. 30cm에서 정면으로 무너진다 |
| **패널 + 정점 변위** | 미리 쪼갠 그리드 메시의 정점 이동 | **채택.** 새로 검증할 미지수가 없다 |
| 하드웨어 테셀레이션 | GPU가 삼각형을 늘림 | **보류.** 정점 예산이 문제가 되면 승격 |

**테셀레이션을 지금 하지 않는 근거는 숫자다.** 권위 격자가 12.5cm이고 정점 간격은 그보다 조대한 25cm로 충분하므로(§5의 세 밴드), 64×64m 스테이지 **전체가 131k 삼각형**이다. `PF_TestMapWithoutCar` 하나가 1.88M인 프로젝트에서 논쟁거리가 아니다. 정점 간격을 12.5cm로 내리면 524k, 6.25cm면 2.1M이 되고 **그 지점이 테셀레이션의 트리거**다. 그림자 패스는 캐스케이드당 한 번 돌므로 실질 부하는 최대 4배로 읽어야 한다.

Batman: Arkham Origins(GDC 2014)와 Santa Monica(GDC 2023)가 둘 다 얕은 눈=시차 / 깊은 눈=테셀레이션 하이브리드로 갔다. 우리가 그 하이브리드를 안 쓰는 이유는 **권위 해상도를 조대하게 잡고 미세 디테일을 픽셀 단계에서 만드는** 선택(§5)이 정점 예산을 애초에 만들지 않기 때문이다.

### 테셀레이션으로 넘어갈 때 싸게 유지하는 규칙 넷

이 넷을 지키면 전환 비용이 **패스별 hull/domain 보일러플레이트 3세트 + 검증 한 판**이고, C#·에셋·필드·VFX는 0이다. 어기면 정점 함수 재작성이 끼어든다.

1. **변위는 include의 순수 함수** — `SnowDisplace(positionOS, normalOS, fieldUV)`. 인터폴레이터나 정점 전용 데이터에 의존하면 domain에서 부를 수 없다.
2. **정점 함수 시그니처를 `Attributes → Varyings`로 유지.** 그러면 domain이 패치 안에서 `Attributes`를 보간해 기존 정점 함수를 **그대로 호출**한다. `DustSurface`의 세 정점 함수가 이미 이 모양이다.
3. **3패스 전부 변위한다.** ForwardLit만 밀면 그림자·깊이가 변위 안 된 평면에 남아 그림자가 눈 표면에서 뜬다. 입력 구조체 확장은 **A 단계의 비용**이며, 미루면 B의 탓으로 오진하게 된다.
4. **높이 샘플은 `SAMPLE_TEXTURE2D_LOD` mip 지정.** 정점 단계와 domain 단계 모두 그래디언트가 없으므로 코드가 양쪽에서 동일하다.

**미검증으로 남는 것**(테셀레이션 스파이크의 실제 내용): Apple Silicon/Metal의 hull·domain 경로, 테셀레이션 셰이더와 SRP Batcher 호환, 그림자 패스 계수를 forward와 다르게 주면 그림자가 표면에서 분리되는 문제, 고정 밀도에서 튠한 자국 선명도가 적응 밀도에서 재현되지 않는 문제(이관이 아니라 **새 설계 항목**이다).

## 3. 네트워크·권위 모델

**먼지의 해법을 그대로 쓸 수 없다.** 먼지는 마스크가 순수 연출이므로 "재시뮬레이션 중복 적용은 붓질을 `Render()`로 빼서 피한다"로 끝났다(`MopPad.cs:134`, `DustMousePainter.cs:98`의 경고). 눈은 깊이를 `VehicleController.FixedUpdate`가 읽어야 하므로 시뮬레이션 밖으로 뺄 수 없다. **회피 대신 중복 적용을 무해하게 만든다.**

### 3.1 `SnowField` — 순수 C#

`UnityEngine` 그래픽 타입을 참조하지 않는다. 헤드리스에서 그대로 돈다.

| | |
|---|---|
| 저장 | 셀당 **`byte depthCm`** 하나. 12.5cm 셀·64×64m에서 **262KB** |
| 좌표 | 세계 좌표 격자. 패널 수와 무관하게 필드는 스테이지당 하나 |
| 연산 | **스탬프 하나뿐** — `ApplyStamp(tick, stampId, area, deltaCm)` |

밀기와 쌓기가 같은 연산이다. 차량 패드는 `deltaCm < 0`, 몬스터·이벤트는 `deltaCm > 0`. 두 경로가 같은 코드를 지나므로 한쪽만 고쳐지는 일이 없다 — 이 프로젝트가 사본으로 두 번 밟은 함정이다.

### 3.2 재시뮬레이션 idempotency는 **스탬프 단위**로 지킨다

적용된 `(tick, stampId)`를 링 버퍼로 기억하고, 이미 적용된 스탬프는 건너뛴다.

- 셀마다 `lastWriteTick`을 두는 방식보다 **셀당 4바이트가 싸다**(5B → 1B).
- 셀 단위 가드는 두 도구가 같은 틱에 같은 셀을 겹쳐 밀 때 **한쪽을 조용히 버린다.** 스탬프 단위는 둘 다 적용한다.
- 한 틱 안의 스탬프는 **결정적 순서**로 적용한다(소유자 id 정렬). 순서가 결과를 바꾸기 때문이다(`max(0, …)` 포화).

### 3.3 이 필드는 롤백 정확하지 않고 **수렴한다**

파괴적 상태는 히스토리 없이 되돌릴 수 없다. 입력 보정으로 경로가 바뀌면 오예측한 셀이 남는다. 교정 수단은 서버의 주기적 동기화이고, 오차의 크기는 12.5cm 셀 몇 개다. **이 한계를 인정하고, "정확하게 만드는 방법"을 찾는 데 시간을 쓰지 않는다.**

### 3.4 동기화 비용은 해상도가 아니라 **불일치량**에 비례한다

전체 필드를 틱마다 보내는 것은 어떤 해상도로도 불가능하다. 대신 블록 해시로 갈라진 데만 보낸다. 64×64m·12.5cm 셀(512×512)·블록 16×16셀(2m) 기준:

| | 크기 |
|---|---|
| 블록 수 | 1,024 |
| 해시 스윕(블록당 32bit) | **4KB** — 틱에 흩어 뿌리면 256B/틱 |
| 불일치 블록 재전송 | **64B** |
| 조인 스냅샷(2bit/셀, 압축 전) | **64KB**, 접속당 1회 |

그래서 **셀을 잘게 만들어도 정상 상태 대역폭은 거의 오르지 않는다.** 해상도가 인질로 잡는 것은 조인 스냅샷 하나이고 그것은 한 번짜리다.

Fusion은 아직 설치되지 않았으므로 복제는 **구현하지 않는다.** 지금 확보하는 것은 API 모양뿐이다: `SnowField`가 **블록 단위 해시와 직렬화를 낼 수 있게** 태어나고, `tick`을 인자로 받고(`Time`을 읽지 않는다), 스탬프를 이벤트로 표현한다. Fusion이 오면 `Runner.Tick`을 넘기고 스탬프를 복제하는 것이 전부다.

### 3.5 서버/클라 분리

| | 서버(헤드리스) | 클라 |
|---|---|---|
| `SnowField` | ✔ 권위 | ✔ 예측 |
| `SnowSurfaceRenderer`(텍스처·패널 머티리얼·VFX) | ✘ | ✔ |

`DustPaintTarget.Awake:55`는 `RenderTexture`를 무조건 만들고 `Shader.Find`를 부른다. **눈에서 반복하지 않는다** — 렌더러는 그래픽 디바이스가 있을 때만 산다.

⚠ **에디터의 Server 모드는 GPU가 있으므로 가짜 통과다.** 검증은 `-batchmode -nographics`로 한다(루트 `AGENTS.md`).

## 4. 품질을 정하는 것은 필드 해상도다 — 세 밴드로 가른다

한 해상도가 세 가지를 동시에 정하고 있던 것이 문제였다. 가르면 각각 다른 값을 줄 수 있다.

| 밴드 | 무엇이 정하는가 | 동기화 |
|---|---|---|
| **A. 밀린 경로의 형상** — 어디가 치워졌나, 자국 폭 | **필드 해상도** | 필요 |
| **B. 경계 누더기·표면 결·알갱이** | 프래그먼트 단계 절차적 생성(월드 좌표 함수) | **불필요** — 클라마다 픽셀 단위로 달라도 아무도 모르고 판정도 안 바뀐다 |
| **C. 얇은 자국** — 바퀴 트랙 20cm, 발자국 10cm | **필드 해상도** | 필요 |

B는 해상도가 공짜다. 그래서 필드가 정하는 것은 A와 C뿐이고, 필드의 오차는 **경계선 ±반 셀 띠 안에** 갇힌다. B의 임무는 그 띠를 직선이 아니라 누더기로 만드는 것이다.

⚠ **B가 격자를 숨기는 정도는 아직 측정되지 않았다.** 스크린샷으로 확인할 항목이며, 그때까지 "숨겨진다"는 것은 추정이다.

## 5. 높이 필드 규약

| 항목 | 값 |
|---|---|
| 권위 셀 | **12.5cm** — 바퀴 트랙(밴드 C)이 표현 가능한 최소. 대가는 CPU 262KB·텍스처 512²·조인 64KB |
| 정점 간격 | **25cm** — 필드와 같을 이유가 없다. 스테이지 전체 131k 삼각형 |
| 픽셀 디테일 | 절차적, 해상도 무제한 |
| 최대 깊이 | **30cm** (`_MaxDepth`) |
| 깊이 단계 | **16** (2026-08-14 게이트 실측으로 4 → 16). 부분만 밀린 자리에서 4단계는 내부 단이 계단으로 보이고 16단계는 안 보인다. 대가는 조인 스냅샷 64 → 128KB(접속당 1회) |
| 한 번 지날 때 제거 | **10cm** |
| 텍스처 | **RG8**. R = `depth01`(권위의 파생물) · G = `freshness01`(**클라 로컬 연출 상태**, §7) |

### 규약

1. **1 = 눈 가득, 0 = 눈 없음.** 정규화해서 올린다.
2. **어떤 판정도 텍스처를 읽지 않는다.** 먼지의 "RT는 권위가 될 수 없다"의 연장. 데디 서버에는 텍스처가 아예 없다.
3. **셰이더는 단계 수를 모른다.** `displacement = height01 * _MaxDepth`. 그래서 단계를 4→16으로 늘리는 작업이 전송 폭 상수 하나로 끝난다.
4. **제거량은 cm로 정의한다.** "레벨 n개"로 정의하면 단계를 늘리는 순간 필요 통과 횟수가 함께 늘어 손맛이 바뀐다.
5. **경계 교란 노이즈는 월드 공간.** UV로 하면 자국이 도구에 붙어 보인다 — 먼지에서 측정된 결론이다.
6. **변위는 원본 깊이가 아니라 벽 프로파일을 통과한 값으로 한다.** `smoothstep(_WallKnee, _WallTop, depth01)`.
   전이를 한 셀 안에 몰아넣지 않으면 벽이 25cm 경사로가 되고 격자축에 정렬돼 계단으로 읽힌다(§7.1).
   `_SnowCutoff`는 그 창 **안**에 두어야 clip이 벽의 중간을 자른다.
7. **필드 조회는 도메인 워프된 좌표로 한다.** 셀 경계의 축 정렬은 높이를 흔들어서는 깨지지 않는다 — 좌표를 흔들어야 깨진다.
   ⚠ **정점 단계와 프래그먼트 단계가 같은 워프 함수를 써야 한다.** 워프·지터 주파수는 정점 간격으로 표현 가능해야 한다.
8. **먼지와 공유하지 않는다.** 다른 텍스처·다른 셰이더·다른 메시. `_DirtMask`와 접점 0.

### 값 해상도는 싸고 공간 해상도는 비싸다

| 단계 수 | 셀당 비트 | 조인 스냅샷 (12.5cm·64×64m = 262,144셀) |
|---|---|---|
| 4 | 2 | **64KB** |
| 16 | 4 | 128KB |
| 256(=연속) | 8 | 256KB |

로그로 자라므로 4→16은 사실상 공짜다. 반면 **셀 25cm→12.5cm는 셀이 4배**다. 두 축을 헷갈리지 않는다.

R8/RG8 반올림은 문제가 되지 않는다 — 먼지의 함정은 **GPU에서 반복 감산을 누적**한 것이고, 눈은 CPU 값을 업로드하므로 오차가 한 번짜리 표시 오차다. 단계 수를 예쁜 약수로 고를 제약이 없다.

⚠ **나이퀴스트**: 12.5cm 필드를 25cm 정점에서 그냥 샘플하면 절반을 건너뛰어 지오메트리가 앨리어싱·팝핑한다. **변위는 저역 통과된(밉) 필드를, 경계 clip과 노멀은 풀 해상도를** 읽는다.

### 조회는 조밀, 갱신은 희소

저장은 조밀 배열이다. 희소(해시)로 하면 (1) 청소 게임은 셀을 결국 다 밟으므로 이득이 사라지는 시점이 필요해지는 시점이고, (2) 미방문 셀도 "가득 쌓임"이라는 값이 있어야 하므로 조회마다 분기가 붙고, (3) 해시 순회 순서는 보장이 없어 결정론이 깨지고, (4) 텍스처는 어차피 조밀하다.

반면 **매 프레임 일은 스탬프가 덮은 셀에만 든다.** 패드 1.8×2.4m는 12.5cm 격자에서 약 **300셀**이고 스테이지 크기와 무관하다. 텍스처 업로드도 스탬프의 바운딩 rect만 올린다.

## 6. 패널·메시

- **`SnowPanelBuilder`**: (크기 m, 정점 간격 m) → 그리드 메시. 16×16m·25cm 간격 = 64×64 quads = **8,192 삼각형**.
- **UV0을 쓰지 않는다.** 필드 UV는 월드 좌표에서 계산한다(`(worldXZ - _FieldOrigin) * _FieldInvSize`). 결과로 `Map/AGENTS.md`의 유니크 언랩 요건이 **무의미해지고**, 패널마다 다른 값을 물려줄 필요가 없어 **메시 한 장과 머티리얼 한 장을 모든 패널이 공유**한다. 패널 추가 비용은 드로우콜 하나이고 SRP Batcher가 묶는다.
- **정점 속성에 아무것도 굽지 않는다.** 높이는 텍스처에서 온다.
- ⚠ **메시 bounds를 최대 깊이만큼 키운다.** 변위가 정점 셰이더에서 일어나므로 원래 bounds로는 컬링에 잘린다. 이 프로젝트는 "완전한 평면 메시의 zero-height AABB"로 이미 한 번 물렸다.
- 배치는 바닥면 위. 패널의 기준면이 바닥이고 정점이 위로 올라간다. 먼지가 `y = 0.72`(바닥 0.70)에 패널을 얹은 사례가 선례다.

## 7. `SnowSurface` 셰이더 — 3패스

`DustSurface`와 같은 구조: **ForwardLit / ShadowCaster / DepthOnly**. `DepthNormals`는 먼지에도 없고 SSAO·데칼을 눈에 쓸 계획이 없으므로 넣지 않는다. 필요해지면 4번째 패스이고, **그때 §2 규칙 3에 따라 그 패스도 변위해야 한다.**

공용 include `SnowSurface.hlsl`:

| 함수 | 역할 |
|---|---|
| `SnowFieldUV(positionWS)` | 월드 XZ → 필드 UV |
| `SampleSnow(uv, lod)` | 변위는 밉 1, 경계·노멀은 밉 0 |
| `SnowDisplace(positionOS, normalOS, uv)` | 순수 함수. 정점(현재)과 domain(나중)이 같은 것을 부른다 |

- ⚠ **`#pragma target`을 3.5 이상으로.** 먼지는 2.0인데 정점 단계 텍스처 페치가 안 된다. 3패스 전부.
- 입력 확장은 **`NORMAL`뿐**이다(`DepthAttributes`에 없다). 필드 UV가 월드 좌표에서 나오므로 uv0은 어느 패스에도 필요 없다.
- 프래그먼트가 하는 일 셋:
  - **경계**: `clip(depth01 * (1 + noise·amp) - _Cutoff)`, 노이즈는 월드 공간.
  - **노멀 교란**: 풀 해상도 필드의 그래디언트(4탭)로 노멀을 꺾는다. **25cm 정점이 12.5cm 데이터처럼 보이게 만드는 장치가 이것이다** — 지오메트리는 조대하고 셰이딩은 세밀하다.
  - **베이스**: `_SnowColor` + 미세 노멀맵 + 스무스니스.
- `freshness01`(G 채널)은 방금 밀린 자국을 다져진·젖은 톤으로 그린다. ⚠ **권위가 아니고 동기화하지 않는다** — §3.1 의 저장은 셀당 `depthCm` 한 바이트뿐이므로 셀마다 "언제 밀렸는지"가 남아 있지 않다. 그래서 신선도는 **최근 스탬프 목록**(수 초 안에 비는 짧은 목록)으로만 유지하고, 값이 0 이 된 셀은 목록에서 빠진다. 전체 격자를 훑지 않는다는 §5 의 성질이 여기서도 유지된다. 밴드 B(클라 로컬 연출)에 속하므로 클라마다 달라도 무해하다.

## 8. 재적설은 이벤트다 (2026-08-14 정정)

**상시 강설로 서서히 회복하지 않는다.** 이벤트와 몬스터 방해가 눈을 쌓는다.

이 정정이 설계를 줄인다:

| | 상시 회복이었다면 | 이벤트 |
|---|---|---|
| 깊이 | `depthAtVisit + (tick - lastVisit)·rate`로 파생 | **저장값 그대로** |
| 셀당 저장 | 5바이트(`uint` + `byte`) | **1바이트** |
| 매 프레임 갱신 | 밀린 셀 전부의 파생값이 변하므로 액티브 셋이 필요 | **스탬프가 덮은 셀만**. 액티브 셋 불필요 |
| 텍스처 업로드 | 액티브 셋의 바운딩 rect | 스탬프의 바운딩 rect **+ 신선도 목록의 rect** — 신선도(§7)는 스탬프가 끝난 뒤에도 몇 초 감쇠하므로 스탬프 rect 만 올리면 다져진 톤이 굳는다 |
| dt 누적 금지 규칙 | 반드시 지켜야 함 | **시간 파생 항이 아예 없다** |

쌓기는 §3.1의 스탬프 하나로 표현된다(`deltaCm > 0`). 밀기와 완전히 같은 경로다.

**가독성이 요구다.** 눈이 다시 찬 자리에는 **그렇게 만든 원인이 화면에 있어야 한다** — 몬스터의 이펙트나 이벤트 연출이 그 자리를 가리켜야 하고, 플레이어가 "왜 다시 더러워졌는지" 모르는 상태가 되면 이 메커니즘은 실패한다.

**연출용 강설과 필드에 쌓이는 눈은 다른 것이다.** 분위기용으로 눈이 내리는 것은 필드를 건드리지 않는다. 둘을 같은 것으로 읽히게 만들면 위 가독성이 깨진다.

## 9. VFX — 좌우로 튀는 스프레이 하나 (2026-08-14 리뷰 반영)

보존이 없으므로 전부 연출이다. **연출은 좌우 스프레이 하나로 시작하고, 그것을 단순하게 만든다.**

### 왜 좌우인가 — 방향이 가시성을 결정한다

카메라는 차 뒤에 있다. 그러므로 방출 방향별로 보이는지가 미리 결정되어 있다.

| 방출 방향 | 카메라에서 | 선례 |
|---|---|---|
| 진행 방향(앞) | **차체가 가린다** | 먼지의 밀림(push) VFX가 이것 때문에 삭제됐다 |
| 위(블레이드 앞 더미) | 차체보다 높이 솟지 않으면 가린다 | 조건부 — 아래로 내렸다 |
| **좌우(차폭 밖)** | **항상 보인다** | 아트 타겟 ④가 보여준 성질이 이것이다 |

아트 타겟 ④에서 실제로 읽힌 것은 "더미가 크다"가 아니라 **"차폭 밖으로 나간 눈은 뒤에서 보인다"** 였다. 그 성질을 더미가 아니라 스프레이로 쓴다. 그러면 가시성이 크기 튜닝에 의존하지 않고 **방향에서 나온다** — 튜닝으로 되돌릴 수 없는 결함을 애초에 만들지 않는 쪽이다.

### 구성

- **방향**: 패드 로컬 ±X(좌우 바깥) + 약간 위. 진행 방향 성분은 넣지 않는다.
- **양**: 이번 프레임에 필드에 **실제로 적용된 제거량**. 로컬 입력이 아니다 — 그래야 원격 플레이어의 스프레이도 보인다(루트 `AGENTS.md`).
- **그래프 수**: **하나.** 퍼프/반짝/밀림 셋으로 갈랐던 먼지와 다르다. 갈라야 할 이유가 생기면 그때 나눈다.
- **깨끗한 바닥에서는 뜨지 않는다.** 제거량이 0이면 방출이 0이다. 먼지에서 이것이 내장 파티클을 기각한 요건이었다(112→1 대 2000).

### 먼지의 구조 한 겹이 사라진다

먼지는 지워진 양을 CPU가 모르기 때문에 `DustErased` 셰이더로 **패드 공간 RT를 GPU에서 굽고** VFX Graph가 그것을 포지션 맵으로 읽었다. 눈은 **CPU가 이미 알고 있다** — 프레임당 약 300셀의 제거량과 좌표가 손에 있다.

- `SnowErased` 셰이더와 그 드로우 패스가 **불필요**하다. CPU가 작은 텍스처를 채워 넘기거나, 스프레이 하나면 방출량·위치 파라미터만으로도 된다.
- 먼지의 "`DustErased`는 `DustPaint`보다 **먼저** 돌아야 한다"는 순서 함정도 함께 사라진다.

### 블레이드 앞 더미는 범위 밖으로 내렸다

최근 제거량에 비례해 크기가 변하는 메시를 두는 안이었다. 기각 사유는 위 표 두 번째 줄이다 — **가시성이 조건부**이고, 그 조건("차체보다 높게 솟는다")은 장난감 차량에서 과장을 요구한다. 스프레이가 같은 정보를 조건 없이 전달한다. 재개 조건은 §12에 적었다.

## 10. 차량 감속

- **재는 곳은 바퀴가 아니라 블레이드 앞이다 (2026-08-14 실측 정정).** 차체 앞 `z = +2.35`에 폭 방향으로
  네 지점을 벌려 깊이를 조회하고, 임계(5cm) 이상인 지점 수로 `covered = n/4`를 만든다. 셀 하나로
  bool을 읽으면 경계에서 떨리므로 네 지점을 쓴다 — 상태를 늘리지 않고 떨림을 없애는 방법이다.
- **왜 바퀴가 아닌가**: 패드를 차폭보다 넓게(4.0 × 2.3 m, 차체 1.8 m) 잡으면 **패드가 축간거리를 덮어
  바퀴가 항상 이미 치워진 자리에 놓인다** — `covered`가 영구히 0이 된다(실측). 물리적으로도 제설차가
  느려지는 이유는 바퀴 침하가 아니라 **블레이드가 눈을 미는 저항**이다. 코드에서는
  `_wheels` → `_samplePoints`(`[FormerlySerializedAs]`로 배선 보존).
- 적용은 `VehicleController.FixedUpdate`의 `grip`/`drive01` 구간(200~202줄 근처)에서 `_baseMaxSpeed`에 `Lerp(1, _snowSpeedFactor, covered)`.
- **범위 제한: 속도만 건드린다.** "눈이 미끄러워야 한다"(횡그립 감소)는 넣지 않는다. 그립 곡선 하나가 저속 정밀 조작과 고속 드리프트를 동시에 정하려다 이미 한 번 실패했고, 거기에 눈을 세 번째 소비자로 얹지 않는다.
- **사본 금지.** 직렬화 필드 하나 + `Lerp` 한 줄. 두 번째 컨트롤러를 만들지 않는다.
- 미해결: `VehicleController`는 `WheelCollider` 없이 직접 속도를 제어하는 Rigidbody 모델이고, 이것이 Fusion 예측과 어떻게 맞물릴지는 **눈과 무관하게 이미 미결**이다. 눈은 그 결정에 깊이를 읽는 소비자로 얹힌다.

## 12. 범위 밖

- **총량 보존**(밀린 눈이 옆에 쌓이는 제설 라인). 요구가 아니다.
- **수거·자원화**(눈을 모아 버리기).
- **블레이드 앞 더미 메시**(2026-08-14 리뷰로 내려옴) — 가시성이 조건부이므로 좌우 스프레이가 먼저다. **재개 조건**: 스프레이만으로 "밀고 있다"가 안 읽히고, 그 원인이 양·속도 튜닝이 아니라 *부피감의 부재*로 판정될 때. 재개하면 차체보다 높게 솟는 조건을 먼저 확인한다(§9).
- **얇은 자국** — 발자국(≈10cm)은 12.5cm 필드의 경계다. 요구로 들어오면 필드를 더 잘게 하는 것이 아니라 **카메라 주변만 따라다니는 로컬 미세 레이어**(동기화 안 함, 판정 안 읽음)를 얹는 것이 맞다.
- **하드웨어 테셀레이션** — §2의 트리거 숫자를 넘을 때.
- **횡그립 감소**(§10).
- **Fusion 복제 구현** — API 모양만 확보한다(§3.4).
- **눈이 쌓이는 이벤트·몬스터 자체** — 이 스펙은 스탬프를 받는 쪽만 정한다.

~~`BrushPad`는 두 번째 소비자가 생기므로 `Core`로 승격한다~~ → **하지 않는다 (2026-08-14 구현 중 정정).**

승격 규칙("promote at the second consumer")이 사는 이유는 **어셈블리 경계를 넘게 하려는 것**인데,
여기서는 넘을 경계가 없다. 눈의 권위 격자는 `SnowStampArea`(순수 C#, `UnityEngine` 미참조)를 입력으로
받아야 헤드리스에서 도는데 `BrushPad`는 엔진 타입을 쓴다. 그래서 실제 두 번째 소비자는 `BrushPad`를
`SnowStampArea`로 바꿔주는 **브리지 컴포넌트**이고, 그것은 `Dust`와 같은 `PPack.InGame` 안에 있다.
승격해도 얻는 것이 없고, `.meta` GUID를 흔드는 자산 이동만 남는다.

**규칙이 발동하는 조건은 "두 번째 소비자"가 아니라 "다른 어셈블리의 두 번째 소비자"다.** `OutGame`이나
헤드리스 전용 코드가 `BrushPad`를 필요로 하는 날 다시 본다.

용어는 `docs/Glossary.md`에 먼저 등록한다.

## 14. 기각한 대안 종합

| 대안 | 기각 이유 |
|---|---|
| 시차(POM)로 두께 | 실루엣이 안 변하고 바퀴와의 교차가 틀린다. 30cm에서 무너진다 |
| 하드웨어 테셀레이션을 지금 | 25cm 정점으로 스테이지 전체 131k면 정점 예산 문제가 없다. 미검증 Metal 게이트를 초기에 끼울 이유가 없다 |
| 눈을 먼지의 다섯 번째 오염 종류로 | 먼지 3종이 공짜였던 이유는 "값만 다르고 수식이 같다". 두께·재적설은 수식이 다르다 |
| 연속 깊이(1바이트) + 깊이→저항 곡선 | 판정이 0/1이면 필요 없다. 단계 4개로 조인 스냅샷이 64KB→16KB |
| 셀당 `lastWriteTick`으로 idempotency | 셀당 4바이트 더 들고, 같은 틱에 겹친 두 도구 중 하나를 조용히 버린다 |
| 희소(해시) 저장 | 청소 게임은 셀을 다 밟는다. 결정론도 깨지고 텍스처는 어차피 조밀하다 |
| 필드를 매 프레임 전체 훑어 업로드 | 스탬프가 덮은 rect만으로 충분하다. §8 정정으로 전체 훑기 이유가 사라졌다 |
| GPU에 `SnowErased` RT를 굽기(먼지 방식) | CPU가 제거량을 알고 있으므로 드로우 패스 하나가 순수 낭비다 |
| 블레이드 앞 더미 메시 | 가시성이 **조건부**다 — 차체보다 높게 솟아야 하고, 장난감 차량에서 그것은 과장을 요구한다. 좌우 스프레이가 같은 정보를 조건 없이 전달한다 |
| VFX 그래프를 셋으로 갈라 시작(먼지 방식) | 먼지는 퍼프·밀림·반짝 셋이었고 그중 하나는 삭제됐다. 갈라야 할 이유가 생길 때 나눈다 |
| UV0 언랩으로 필드 참조 | 월드 좌표로 계산하면 메시·머티리얼을 전부 공유할 수 있다 |

## 15. 미해결·리스크

- **밴드 B가 격자를 얼마나 숨기는지 측정되지 않았다.** 이 스펙에서 가장 큰 룩 리스크다(합격 기준 4).
- **25cm 정점에서 30cm 자국의 벽이 25cm에 걸쳐 기울어진다** — 날카로운 절단면이 아니라 둔덕으로 읽힐 수 있다. 장난감 아트 톤에는 맞을 가능성이 크지만 확인 항목이고, 값싼 강화 수단이 있다(경계 한 셀에서 높이를 급히 떨어뜨리고 clip으로 자르기).
- ~~더미가 차체에 가려질 위험~~ → **해소(2026-08-14 리뷰).** 더미를 §12로 내리고 방출을 좌우로 돌렸다. 가시성이 크기 튜닝이 아니라 **방향**에서 나오므로, 먼지의 밀림 VFX를 죽인 실패 모드가 구조적으로 생기지 않는다. 남은 리스크는 반대쪽이다 — **스프레이만으로 "밀고 있다"는 부피감이 부족할 수 있다**(합격 기준 10, 재개 조건은 §12).
- **필드는 수렴하고 롤백 정확하지 않다**(§3.3). 인정하고 간다.
- **`VehicleController`와 Fusion 예측의 궁합**은 눈과 무관하게 미결이다.
