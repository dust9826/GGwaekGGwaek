# 눈 표면 레이마칭 — 설계

> **작성일** 2026-08-16 · **브랜치** `/main/snow-raymarch-surface` (예정) · **피처** `Assets/Game/InGame/Snow/`

눈의 렌더링을 **바닥 위 패널 + 정점 변위**에서 **프록시 볼륨 + 픽셀 단위 레이마칭**으로 바꾼다. 시뮬레이션·권위·업로드는 건드리지 않는다.

근거는 전부 별 프로젝트(`~/Documents/UnityProjects/AnyTest`)에서의 실측이다. 그 스파이크는 눈 다섯 변종을 만들어 재고 던져버렸고, 기록은 그 폴더의 `Docs/snow-grain-spike/index.html` 과 `v5-how-it-works.html` 에 있다. **이 문서는 그중 렌더러 하나만 옮기는 이야기다.**

---

## 1. 왜 바꾸는가

`2026-08-14-snow-surface.md` §2 는 시차(POM)를 **두 가지 이유로 기각**했다 — "실루엣이 안 변한다"와 "차량 바퀴와의 교차가 틀린다" — 그리고 정점 변위를 골랐다. 그 판단은 **시차에 대해서는 지금도 맞다.**

그런데 **프록시 볼륨 안에서 진짜로 마칭하고 3패스 전부 `SV_Depth` 를 쓰면 실루엣과 교차가 지오메트리가 아니라 깊이에서 나온다.** 실측으로 확인했다: 눈이 블레이드 아랫부분을 정확히 가리고, 실린 짐이 윗변 위로 얹히고, 바닥면과 z-fighting 이 없다. **즉 기각 사유가 이 방식에는 적용되지 않는다.**

### 숫자 (좌측은 이 저장소의 기존 실측, 우측은 스파이크 실측)

| | 정점 변위 (현재) | 레이마칭 |
|---|---|---|
| 삼각형 | 메시 131k → **렌더 658k** (그림자 캐스케이드가 패스를 5번 반복) | **프록시 박스 12개** |
| 정점 간격 25 → 12.5cm | 메시 524k → **렌더 2.6M** = 테셀레이션 트리거 | **변화 없음** |
| 필드 셀을 잘게 하면 | 나이퀴스트 때문에 정점도 같이 잘게 해야 함 | **무관** — 프래그먼트가 필드를 직접 읽는다 |
| 비용의 성질 | **월드 면적**에 비례 | **화면 픽셀**에 비례 |
| 실측 (120 × 110 m 스테이지) | — | **프레임 3.4 ~ 5.1 ms**, 광선당 평균 **10 스텝** |

### 사라지는 제약 넷

`2026-08-14-snow-surface.md` §2 의 "테셀레이션으로 넘어갈 때 싸게 유지하는 규칙 넷"은 **전부 정점 변위가 만든 제약**이고, 이 전환으로 통째로 없어진다.

1. ~~변위는 include 의 순수 함수여야 한다~~ — domain 셰이더가 없다
2. ~~정점 함수를 `Attributes → Varyings` 로 유지~~ — 정점 단계가 표면을 만들지 않는다
3. ~~3패스 전부 변위한다~~ — 3패스가 같은 마칭 코드를 `#include` 하므로 어긋날 여지가 없다
4. ~~메시 bounds 를 최대 깊이만큼 키운다~~ — 프록시 박스가 애초에 볼륨이다

그리고 §5 의 **나이퀴스트 규칙**("변위는 밉, 경계와 노멀은 풀해상도")도 사라진다. 정점이 없으므로 지오메트리 앨리어싱·팝핑이 원천적으로 생기지 않는다.

## 2. 알고리즘

픽셀 하나당:

```
1  광선 = 카메라 → 픽셀,  프록시 박스와 slab 교차 → 진입/이탈점
2  반복 (최대 _MaxSteps):
       상한 = coarseMax(dilate) 샘플            ← 주변 최대 높이의 보수적 상한
       advance = min(안전반경, 여유 / |rd.y|)
       광선이 표면 아래로 내려갔으면 → 3
3  이분법 _RefineSteps 회 → 적중 (오차 ≈ stepM / 2^refine)
4  표면 높이 = 필드(bilinear) + 저주파 노이즈 + fillet
5  노멀 = 필드 기울기(4탭);  밴딩용 매크로 노멀 = 넓은 epsilon 기울기
6  AO·소프트섀도 = 짧은 2차 마칭
7  색 + SV_Depth 기록
```

### 2번이 이 방식의 생사를 가른다

균일 스텝으로 마칭하면 **실패한다**. 8 × 8 m 필드·낮은 카메라에서 57,600 광선 중 **324개(0.56%)가 표면을 뚫고 지나갔다** — 스텝 예산을 코드 길이에 나누면 스텝이 요철보다 커지기 때문이다. 화면에 반점으로 나타나는 결함이고, **셰이더를 짜기 전에 수치 하네스가 먼저 잡았다.**

해법은 **dilate 된 coarse-max 격자**다. 셀마다 "그 주변 안전반경 안의 최대 높이"를 담고, 광선은 `min(안전반경, 여유/|rd.y|)` 만큼 전진한다. 건너뛴 구간 전체에 대해 상한이 성립하고 광선 y 는 단조 감소하므로 **표면을 지나쳐 뛰는 것이 구조적으로 불가능하다.** 대가는 컴퓨트 커널 2개(블록 최대 + dilate)와 작은 RT 하나.

| | 균일 마칭 | coarse-max 스킵 |
|---|---|---|
| 광선당 스텝(평균) | 58.3 | **21.5** (8×8m) / **10.6** (120×110m) |
| 표면 관통 | 324 / 57,600 | **0** (구조적으로 불가) |
| 적중 정확도 | 코드 길이에 좌우 | **1.25 mm** (= 2cm / 2⁴) |

⚠ **fillet 을 넣으면 상한 계산에 그 최대 들림값을 포함해야 한다.** 스파이크에서 fillet 이 평지를 2.5cm 무조건 들어올리는 결함이 있었고, 그것이 상한을 깨면 표면에 구멍이 뚫린다. 지금 형태는 **평지에서 정확히 0, 최대 들림이 공표값 이하**임을 수치로 확인한 saturating 형태다.

## 3. 접합면 — 무엇을 바꾸고 무엇을 안 바꾸는가

현재 `SnowSurface.hlsl` 이 쓰는 전역은 여섯 개다:

```
_SnowField  _SnowFieldOrigin  _SnowFieldInvSize  _SnowFieldCellSize  _SnowFieldTexelSize  _SnowMaxDepth
```

**레이마처가 필요한 입력이 정확히 이 여섯 개다.** 그래서 이 전환은 데이터·업로드·패스 구조를 그대로 두고 지오메트리 전략만 교체하는 일이다.

| 그대로 두는 것 | 바뀌는 것 |
|---|---|
| `SnowField.cs` — CPU 권위, 셀당 1바이트 | `SnowPanelBuilder.cs` — 패널 그리드 메시 → **프록시 박스** |
| `SnowStage.cs` — 틱·스탬프 접점 | `SnowSurface.shader` → **`SnowRaymarch.shader`** (기존 것은 A/B 용으로 **남긴다**) |
| `SnowSurfaceRenderer.cs` 의 RG8 업로드·dirty rect | **추가**: coarse-max + dilate RT 와 그 커널 |
| `SnowVehiclePad` · `SnowVehicleDrag` · `SnowSprayVfx` · `SnowPushAudio` | **추가**: 로브 레이어 — 구운 텍스처 1장 + 커널 1개 (아래) |
| — | 렌더러 선택 스위치(인스펙터) |
| 필드 규약 8개 (§5) — 1=가득, 판정은 텍스처를 안 읽는다 등 | — |

**RG8 정밀도는 충분하다.** 256 단계를 30cm 에 나누면 1.2mm 이고, 마칭 적중 오차(1.25mm)와 같은 자리수다.

### 로브 레이어 — 이것이 "느낌"을 만든다. 셰이딩이 아니다

스파이크에서 A/B 로 밝혀진 것: **레이마처만으로는 눈이 각진 슬래브로 읽힌다.** 같은 필드(1.56cm)를 두 방식으로 그려 비교했다.

| 같은 필드 · 같은 씬 · 같은 42초 | 둔덕이 읽히는 방식 | gpu |
|---|---|---|
| 높이필드 레이마칭만 | 낮고 각진 계단식 슬래브 | 4.33 ms |
| 스크린스페이스 lump 6만 개 | 높고 둥근 로브 — 원하는 그림 | 16.96 ms |

**셀 크기를 아무리 줄여도 레이마처는 각진 슬래브를 낸다.** 그래서 로브를 따로 얹어야 하는데, 스크린스페이스 방식은 **lump 개수와 무관한 약 6 ms 의 전체화면 고정비**(깊이·두께 버퍼 + 블러)를 갖는다 — 6만→6천으로 줄여도 GPU 16.96 → 6.98 ms 에서 멈춘다. 그래서 그 방식은 기각했다.

대신 **구 격자를 높이 기여로 바꿔 필드에 굽는다.**

```
lift(x,z) = 3×3 이웃의 max( sqrt(r² − d²) )      d = 해시 지터된 구 중심까지의 수평거리
h(x,z)    = 필드 + 디테일 + fillet + gate(x,z) · lift(x,z)
```

세 가지가 이 형태의 핵심이고, 셋 다 실측으로 정당화된다:

1. **여전히 높이함수다.** 진짜 3D SDF 합집합으로 하면 오버행이 생겨 `ray.y < h` 판정·coarse-max 스킵·3패스 `SV_Depth` 가 동시에 무너진다.
2. **상한이 정확히 `+r` 이다.** `lift ≤ r` 이 점별로 성립하고 plain max 라 오버슈트가 없다. 진폭이 무한한 노이즈로 형태를 넣으려던 시도는 상한을 뭉개서 `meanSteps 7.4 → 39.5` 로 터졌다.
3. **평가하지 말고 굽는다.** lift 는 **필드의 순수 함수**라 픽셀당 36스텝 재계산할 이유가 없다. 더티 창 컴퓨트로 텍스처에 굽고 렌더는 **바이리니어 탭 1개**를 낸다.

3번이 이 레이어를 감당 가능하게 만든 유일한 요인이다. 실측(스테이지 규모 120×110 m, 각 14샘플):

| | gpu | frame | meanSteps |
|---|---|---|---|
| 로브 끄기 | 6.13 ± 0.14 ms | 3.76 ms | 23.7 |
| 로브 · 스텝마다 해시 9개 | 15.44 ± 0.35 ms | 9.82 ms | 35.6 |
| **로브 · 구운 텍스처 1탭** | **7.83 ± 0.52 ms** | **4.56 ms** | 34.6 |

**증분 +1.70 ms.** 굽기 대상은 필드의 2배 해상도(6.25 cm) R8 한 장 — 이 스테이지에서 1920×1760 = 3.4 MB, 창은 240×240 텍셀 전후에 디스패치 1회.

⚠ `meanSteps` 는 35.6 → 34.6 으로 **거의 안 줄었다.** 상한을 구운 실제 최대값으로 조여도 소용없었다 — 스텝 증가는 `base` ~ `base+r` 밴드를 스치는 광선이 통과하는 **고유한 대가**다. 승리는 상한이 아니라 **스텝당 연산 제거**에서 나왔다. 이식할 때 이 순서를 뒤집지 말 것.

부수 효과 둘. **로브가 충돌면 위가 아니라 충돌면 자체에 있다** — 스크린스페이스 방식은 실루엣을 높이필드보다 27 cm 띄워서 차량 충돌과 어긋난다. 그리고 **게이트가 눈 깊이 0 에서 정확히 0** 이라 맨땅에 로브가 떠다니지 않는다. 이 두 규약은 이식 시 반드시 유지한다.

### 이름 (이 저장소 규칙)

스파이크의 `*V5` 접미사는 **여기서 금지**다(`AGENTS.md` — 버전 접미사 금지). 네임스페이스는 평평한 `PPack`.

```
Snow/Scripts/SnowRaymarchRenderer.cs
Snow/Shaders/SnowRaymarch.shader
Snow/Shaders/SnowMarchCore.hlsl      ← 3패스가 같은 것을 include
Snow/Shaders/SnowCoarseMax.compute
Snow/Shaders/SnowLobeBake.hlsl       ← 굽는 커널과 읽는 마처가 공유. 공식은 한 곳에만
Snow/Shaders/SnowLobeBake.compute
Snow/Shaders/SnowCasualStyle.hlsl    ← 캐주얼 톤(선택)
```

`SnowLobeBake.hlsl` 을 커널과 마처가 **같이 include** 하는 것이 규약이다. 스파이크에서 공식이 두 곳에 있으면 조용히 어긋난다는 게 확인됐다 — 굽는 쪽과 읽는 쪽의 인코딩이 1비트만 달라도 상한이 깨진다.

## 4. 캐주얼 톤은 별 축이다

스파이크에서 장난감 톤이 렌더러와 **독립**임을 확인했다 — 같은 마칭 결과에 톤 함수 하나를 얹는다. 재료 다섯: 확산광 양자화 · 색 있는 그림자(검정 금지) · **정보 억제**(알베도·AO 를 일부만) · 글린트 제거 + 넓은 림 · 둥근 형상.

⚠ **캐주얼은 정보를 빼서 만든다.** 스파이크에서 "너무 하얗다"에 대응해 잔알갱이·AO·알베도를 동시에 올렸다가 **캐주얼이 사라졌다.** 요철은 *작고 많게*가 아니라 **크고 둥글게**, 그리고 밴딩이 보는 **매크로 노멀**에 들어가야 한다.

**로브 레이어는 범위 안이고 아트 톤은 범위 밖이다.** 둘을 구별하는 기준은 "그것 없이 눈이 눈으로 읽히는가"다 — 로브가 없으면 각진 슬래브라 읽히지 않으므로 렌더러의 일부이고, 밴드 수·그림자 색·노출은 아트 결정이라 별 체크인이다. 렌더러 전환과 아트 톤을 같은 체크인에 섞지 않는다.

## 6. 범위 밖

- **캐주얼 아트 톤** — §4. 별 체크인.
- **눈덩이·적재 원장·조작감 결합** — 스파이크 v5/v6 의 내용이고 이건 렌더러만이다.
- **coarse-max 밉 피라미드** — 카메라 4 m 에서 평균 10 스텝이므로 **불필요**. 아주 낮은 시점을 상시로 쓰기로 결정되면 그때.
- **스크린스페이스 스무딩 모드** — 스파이크에서 실측 후 **기각**했다. lump 개수와 무관한 약 6 ms 전체화면 고정비가 있고(6만→6천으로 줄여도 GPU 16.96 → 6.98 ms 에서 멈춘다), 실루엣이 충돌면보다 27 cm 떠서 차량 판정과 어긋난다. §3 의 구운 로브가 이것을 대체한다.
- **경사면 위의 눈** — 마칭도 높이필드라 현재와 같은 제약(`up = +Y`). 회귀도 개선도 아니다.

## 7. 리스크

- **실측이 눈만 있는 씬에서 나왔다.** 로브 끄기 6.13 ms / 켜기 7.83 ms 는 스파이크 씬 값이다. 이 저장소 씬은 이미 드로우콜 631·삼각형 1.24M 이므로 눈이 그만큼 먹으면 과하다. **목표는 로브 포함 4~5 ms** 로 보고, 넘으면 손질 순서는 ① 로브 거리 페이드를 당긴다 ② 거리 LOD(스텝 확대) ③ 로브 반지름을 줄인다 — **반지름이 스텝 밴드 두께에 선형으로 들어가기 때문**이다.
- ⚠ **측정 프로토콜을 지켜야 한다.** 스파이크에서 단일 샘플로는 30% 이내 대안을 순위 매길 수 없었다(같은 설정이 16.49 ms 와 25.26 ms 로 읽혔다 — 필드 상태가 달랐다). **런 내부 연속 14샘플 평균**을 쓰면 gpu 편차가 ±0.14 ms 로 떨어지고 `meanSteps` 는 편차 0 이라 가장 좋은 판별자다.
- **낮은 카메라가 가장 비싸다** — 광선이 볼륨을 *따라* 지나가므로 코드가 길어진다. 실측 1.7배(1.15 m 대 12 m). 카메라 정책이 렌더 예산을 정한다.
- **URP 3패스에서 `SV_Depth` 쓰기**는 스파이크에서 확인됐지만 이 저장소의 URP 버전(17.6)과 렌더러 설정에서 다시 확인해야 한다.
- **그림자 패스 마칭**은 스파이크에서 취약했고 기본 꺼짐이었다. 여기서도 켤지는 측정 후 결정.
- ⚠ **에디터를 열어둔 채 브랜치를 전환하면 전체 리임포트**가 걸린다(`AGENTS.md`). 전환 시점을 사람이 고른다.
